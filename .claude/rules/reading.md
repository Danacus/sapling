# Reading mode

Design doc: `docs/reading-mode.md` (§7 is what this slice deliberately leaves out).

**"Reading mode" is the internal name; the learner-facing section is called Media** — a text here is read, listened to or watched, and the copy says so (`/read` stays the route, `$lib/reading` stays the module, `ReadingText` stays the type). Two doors: *Write one for me* and *Import your own*. The words "bring"/"brought" appear in no user-visible string; a text the learner supplies is **imported**, and a file they hand over is **uploaded**.

- `src/lib/reading/` — **comprehension: a whole text, and what the app knows about every word in it.** Stateless on the same seam as `$lib/conversation`: **nothing here imports `$lib/db`**, the caller passes the vocabulary in and persists what comes out, which is what keeps the module testable in node and every write to the learner's collection going through the repositories that capture sync events. **A stored text is only the text** — `ReadingText.segments`, one `Segment { text, start?, end? }` per subtitle cue or per paragraph, as the source cut them — and carries no readings, translations or glossary; every reading, colour, meaning and translation on screen is derived or asked for at render time. **Three paid envelopes** — generate, look up, translate — mock/real dispatch in `index.ts` on `isMockMode()` exactly as `getBatch` and `startConversation` make it, all pinned with `responseFormat` and re-parsed with zod (`schemas.ts`, mirroring `$lib/conversation/schemas.ts` down to the `strictJsonSchema` pass, `.nullish()` normalized to absent). **Generate** (`generate.ts`) writes a text *out of* the whole collection — vocabulary as terms only (no ids; capped by `MAX_VOCABULARY_TERMS` with a deterministic trim-then-slice), a `focus` list the text must use at least once, `SENTENCES_BY_LEVEL` for the length — and asks for `{title, paragraphs}` and nothing about them: each paragraph becomes one untimed segment, the unit an import stores, so no sentence array is asked for just to have one. The read-generate task mints `id`/`createdAt` from the `ReadingTextDraft` and stores it.

- **Import is not a call and not a task; recognising and cutting it is the Rust core's.** `crates/sapling-import` (`core.md`) holds the subtitle parsers and the paragraph split, and the protocol exposes one method over them, `importSource(text) -> ImportedSource { format?, cues, durationMs, segments }`: subtitles — SRT, VTT, **`json3`** and a copied "Show transcript" panel — are cleaned into cues, de-duplicated (YouTube's rolling auto-captions repeat every line) and become **one timed segment per cue**, never joined or re-cut, so a sentence spread over two cues is two segments with the spans they were on screen; anything else is prose, **one untimed segment per paragraph** (split on blank lines, trimmed, verbatim otherwise). `segments` is `sapling-domain`'s `Segment` itself, so the composer hands it to `addText` untouched. `format` is absent for prose, which is how there is still **one door**: the learner pastes or uploads whatever they have and the page recognises it — and on the desktop host, what yt-dlp fetched (`media.md`) comes through that same door as raw `json3`. The window reaches Rust only through the protocol, so **`$lib/reading` never calls it** (it would have to import `$lib/db`); the composer page and the `captions` task do, through `$lib/db`'s `importSource`. The parsing rules themselves — json3's `segs` joined by nothing, an event with no `dDurationMs` ending where the next starts, a cue's lines joined with a space or nothing between CJK — are documented where they live, in the crate and `docs/reading-mode.md`. The times are `Segment.start`/`end` (milliseconds into the media, both or neither), and what reads them is the reader's **follow view**, through `$lib/media` (`media.md`); nothing in `$lib/reading` does.

- **Two paid calls run *mid-read*, both quick, minimal and never stored, and only a button fires either — never a tap.** Both use whatever model the LLM layer resolves (`ReadingOptions.model`, else the learner's stored model, else `DEFAULT_MODEL`); there is no model setting of their own. **Look up** (`lookup-call.ts`): one word, sent with **the sentence it stands in** — `sentenceAt(segmentText, offset)` in `pages.ts`, the same ICU sentence cut `paginate` uses, found by the word's character offset into its segment (`pieceOffset` plus the tokens before it) and falling back to the whole segment where there is no `Intl.Segmenter` — so a polysemous word comes back in the sense it is being used in. Request `{native, target, level, term, sentence, title?}`, reply `{term, reading, meaning, explanation}` and nothing more — **`meaning` the short gloss a card would carry** (a few words, headword-style, no sentences) and **`explanation` the longer answer** (sense here, nuance, usage or the form's grammar; a few sentences at most, nullable), both native-language, kept apart because the learner files the first and only reads the second — parsed into one `GlossEntry` (TypeScript-only, in `schemas.ts` — nothing stores one; a blank explanation is absent, a blank meaning throws) whose `term` is taken from the **request** rather than the reply (the answer is matched against the token by `wordKey`, and a dictionary form would match nothing). The page keeps it in a `$state` `extraGlossary` it owns and reads it through `lookedUpGloss` for every occurrence of the word for the rest of that open. **Translate** (`translate-call.ts`, `translateLine`): **one segment** into the native language — request `{native, target, text, title?}`, reply `{translation}` — the segment being the unit because it is what the source cut and what the reader already indexes, so an answer belongs to exactly one segment and nothing is aligned. The page keeps answers in a `SvelteMap` keyed by segment index (loading / done / error per segment) and which are *shown* in a separate set, so hiding keeps the answer; both are cleared when a text loads. Following, "Translate line" sits under the current line (and pauses the recording, as a tap does); paged, "Translate" in the header's Listen slot asks for every segment on the page, **one call per segment, three in flight** (`TRANSLATE_CONCURRENCY`), each shown as a block under its segment's last piece on the page — a segment cut across a page break shows it on both — and each failure stays on its own segment; pressing again with all shown hides them, and a failed one is re-asked the next time it is shown.

- **Segmentation.** ICU word boundaries are the base (`segmentWords` in `$lib/text`, `Intl.Segmenter`, no download) and **vocabulary and known terms override them by greedy longest match on top** (`termsFor`), so 自行车 stays one cell where ICU would cut 自行 + 车 once the learner holds it. The tokenizer is the romanizer's `tokenize` when the language has one (`$lib/romanize` — whole-line pinyin sliced per token, the only way polyphones come out right) and `tokenizeByTerms` otherwise; `annotate.ts` accepts either through `TokenizeFn` and never needs to know which it got. **Concatenating every token's `text` reproduces the input exactly** — a caller renders tokens instead of the string and must never have to diff the two. `wordKey` — trimmed, NFC, lower-cased, internal whitespace collapsed — is the one spelling normalization, used on both sides of every lookup; it **is** `termKey` from `$lib/text` under this module's name for it, shared with the lesson resolver, the session engine and the assistant rather than re-implemented. But a spelling is not a word: 长 is `cháng` and 长 is `zhǎng`, so the item lookup in `annotate.ts` — and `lookedUpGloss` over the page's looked-up answers — is spelling → *list*, and the **token's own reading** picks which candidate an occurrence is (`readingKey`, which strips spacing on both sides so a multi-syllable token matches a whole term). No reading anywhere falls back to the first candidate.

- **Three statuses, three acts** (`docs/reading-mode.md` §3 is the reasoning; LingQ is the reference point). A word is `tracked` (in the garden, with an FSRS card), `known` (understood, deliberately not scheduled) or `plain` (nobody has said anything about it — still tappable, with no gloss until the learner looks it up). The acts are kept distinct and must stay so: **tapping is a *lookup*** ("explain this"), which opens the card and records `wordLookedUp` and **does not add the word to the garden** — adding stays an explicit tap, because the garden is what gets scheduled and must not fill up by accident — and on a *tracked* word it is also a lapse, graded `Again` **once per word per day** through `updateItemAfterReview` (the drill's own call, so it is an ordinary ledger review — and per *day* is what unifies the two: a word lost in this morning's drill is not lost again by reading it); **the page's primary button** is the other half — every tracked word on that page read *without* a lookup **on that page** gets `Good`, unless it already has a `Good` today — and it confirms first because it writes a dozen events at once. Nothing else is marked by it. **None of that state is held here**: it is derived from the item's own `recentGrades` (`getAllItems({ withRecentGrades: true })`, last entry, `localDay` equal to today), so it survives a reload and agrees with the drill; the only set the reader keeps is *what was tapped on this page*, cleared on every turn, because a word looked up on page one and read fine on page three is the re-encounter the mode exists for. **Every confirmation lives in the panel** — the slot the word card uses (facing page at ≥48rem, sheet at the foot of a phone), never in the header and never above the text — so the header keeps one shape whatever is being decided; **"I know this" is a status declaration** (`wordMarked`), not a review, and known words stop being highlighted *and are handed to the generator as vocabulary it may use freely* — that union is the whole point of the mark, so a caller building `vocabulary` sends items **plus** `getKnownTerms()`; **"Add to my words" is `add_words`, verbatim** from `$lib/assistant/tools`, which keeps it the one route by which vocabulary enters the collection and therefore the one place the term dedupe lives.

- **The `plain` word's card leads with "What does this mean?"** — the primary button until the learner has a meaning in the field, when Add takes over, and gone once the word has a looked-up answer. Under it, **always editable**: a Meaning field and, for a word whose letters are not Latin script (decided from the word's own characters, not the profile's language name), a Reading field. They open prefilled from what is already known — the token's own reading first (the romanizer's is this occurrence's), then an `extraGlossary` answer from earlier in the open, so re-opening a word costs no call — and a lookup landing fills only fields still empty, only on the card that asked; the Meaning field takes the short `meaning` only. The lookup's `explanation` is **read-only text above the fields** (under the status line, on a looked-up `known` card too), carried in the same `extraGlossary` entry so a reopen shows it, and **display-only**: "Add to my words" files exactly those fields (`meaning`, `romanization` = the Reading field, omitted when blank) and never the explanation. **A lookup never blocks adding**: in flight it disables only its own button, and a failure is an error line on the card with the fields left as they were, empty and editable — a learner who knows the word types it and adds it without spending a call. A `tracked` card shows its item's gloss and no actions; a `known` card shows a looked-up gloss if there is one, and Unmark.

- **A text is immutable; everything adaptive is derived at render time.** `annotate.ts` is pure and deterministic in the house style — `now` passed in, the coin flip an injectable `rng`, no clock, no DB, no preference store — so a text written last month shows this month's knowledge. Reading visibility follows the learner's `RomanizationMode`: `'on'` keeps every reading, `'off'` none, `'adaptive'` hides a `known` word's, keeps a `plain` word's, and fades a `tracked` one against its strength. Readings are per token from `$lib/romanize`; a language with no local romanizer shows none in the prose, since a text stores none. **That roll is memoised per `cardKey` in a `Map` the *caller* owns, created once per text open** — a challenge rolls once because it is one screen, but a word appears in several lines of a text and one that showed its pinyin in line two and hid it in line five reads as a bug. Per *card* and not per spelling, so two cards sharing a term fade on their own strengths; the caller still just hands over an empty `Map` and never learns what the keys are. Keeping the same map across a re-annotation is also what makes "the learner just added a word" cheap: only the new word rolls.

- `src/routes/read/` — **the reader owns every write; the composer stores an import itself and starts a task for a written text.** `+page.svelte` is the library and the composer: two doors as a segmented toggle, `MAX_TOPIC_CHARS` on the topic. *Write one for me* starts `read-generate` in `$lib/tasks`, whose def makes the call **and the save** — minting `id`/`createdAt` and `addText` — so a text lands in the library whether or not the learner stayed to watch; the page opens it only while it is still mounted (a `goto` fired into a session the learner has since started would be worse than none), and otherwise the text is simply in the shelf next visit. **Which outcome it opens is decided from the runner's *records*, never from the promise `startTask` returned** — one `$effect` over `taskStore.tasks` covers both of the page's jobs (`read-generate`, `captions`), acting once on every settled record descending from an id this page started and reading the value out of `taskOutcome`; a Retry pressed in the tray is a new record with a new promise, and awaiting the old one left a text sitting in the library while the composer still showed the failure (`tasks.md`). `busy` is "a `read-generate` task is running" read from `taskStore`. *Import your own* is **no task at all**: `add()` takes the segments `importSource` already produced, mints `id`/`createdAt`, `addText`s them, hands a file recording to `rememberFile`, and `goto`s the text — one local write behind an `adding` flag. The import door ("Import your own") is **one door for prose and for subtitles**, in three parts — what the text is, how much of it there is, what it plays alongside — and a single `plan` behind all of them. **An uploaded file is an object, not a paste**: `uploadFile` reads it and asks `importSource` what it is (its `format`), and anything recognised becomes `sourceFile` (`{ name, text }`) rendered as a card that states what it is — format, cues, duration — with a × that restores the box, while anything else *is* a paste and goes into `pasted` where it can still be edited. The **content decides, never the extension**, so a `.txt` holding an SRT is still subtitles and an `.srt` holding prose is still prose. The two shapes are alternatives and exactly one is on screen; `pasted` is kept underneath a card so removing the file gives back what was typed. `plan` is one `importSource` answer for `sourceFile?.text ?? pasted` — an effect puts the answer in `$state` and drops one whose source has since changed — still **one derivation over one source**, which is what keeps the card, the count, the button's disabled state and `add()` from ever disagreeing. The count line ("214 lines" for subtitles, "3 paragraphs" for prose) sits **under the source whatever the source is**, silent while there is nothing, and a file with nothing readable in it says so there, in red, because a dead control cannot explain itself. **The door carries no other prose**: every control is labelled by what it does, and the only lines are the ones a control cannot say for itself — the legend's note, what is attached, that a file is kept by name alone. The title comes last: it **defaults to the file's name without its extension, or else the text's first line cut to 60 characters**, shown as the field's placeholder so the learner sees it and can type over it. `[id]/+page.svelte` is the reader: it builds the `AnnotateContext` once per load and **re-annotates after every write by reloading items and known terms**, keeping the roll map, so the text recolours in place under an open card that then shows the *new* status — which is why the open word is held as a position into the derived lines and never captured on tap. **It reads a page at a time**: `paginate` (`pages.ts`, pure and tested) turns the segments into **pieces** — a segment that fits in `PAGE_WORDS` (30) is one piece, a longer one is one piece per sentence of it, cut by `Intl.Segmenter` at sentence granularity **only to place page breaks and never stored**, the pieces of a segment concatenating back to it — and packs the pieces greedily, a break only ever *between* pieces, always at least one. Words are counted by ICU's base segmentation (`countWords`), never the annotated tokens, so a break cannot move when the learner adds a word; the current page is `?p=` (1-based, clamped, `page.url` from `$app/state`, written with `goto(url, { replaceState: true, noScroll: true })` and a scroll to the top), and nothing about the position is stored — the library always opens page 1. `lines` stays the annotation of **every** piece because the roll map is text-wide; only `pageLines = lines.slice(start, end)` is rendered, and Listen follows it. Word positions in the markup stay whole-text indices (`pageRange.start + l`), so `selected` still points into `lines`. Pieces of one segment run straight on, two timed segments (cues) are joined by the script's own gap, and two untimed ones (paragraphs) break with a `.para-break`; a piece keeps its own line breaks (`white-space: pre-line`). Words are real `<button>`s (Tab reaches them) wearing no button chrome, and the token loop is written **without whitespace between tokens** for the same reason `RubyText` is: the tokens reproduce the piece character for character and a newline in the template becomes a rendered space between every pair of them. Layout per `layout.md` — the text column is `--measure` whatever the spread allows, and the word card is a facing page at ≥48rem and a sheet at the foot of the phone below it.

- **A text with a recording opens in the follow view, which is a *view* and not a route.** Everything under it is the same: the same `AnnotateContext`, the same `lines` over the whole text, the same whole-text `selected`, the same card. Only the page is cut differently — **following, the page *is* the segment being spoken**: `currentIndex = segmentAt(segments, currentMs)` (from `$lib/media`) — the one segment whose `[start, end)` holds the clock, or else the last to have started, `-1` before the first cue — and `pageRange = piecesOfSegment(pieces, currentIndex)`, the pieces it became (one, for any cue that fits a page). So the whole-text word indices follow the line being spoken without knowing about a video, and "next"/"previous"/replay, auto-pause and the transcript all work per segment. `followable` is **a `media` of either kind** and at least one timed segment; which kind it is decides nothing beyond what the `.stage` mounts — a `<video>` for a file, an empty `<div>` for YouTube's iframe to fill — and both are wrapped as the same `Player`, so the effect, the transport, the auto-pause and the keyboard are written once (`media.md`). `?view=text` is the way to the paged reader and back, `?p=` dropped on the way, so the view is a URL fact like the page number and neither is stored; coming *back* to the follow view also clears a failed YouTube load, which is the retry.

- **The clock turns no grades.** Page grading is the learner saying "I have read this", and a video that keeps playing while they look out of the window says nothing at all — so the finish row, the `Good`s and the receipt are **rendered in the paged view only**. What a *tap* means is unchanged in both, because a tap is real: `recordLookup` still fires and a lookup on a garden word is still `Again`, once per day. A tap also **pauses** the recording, which is what the learner would do themselves one beat later, having lost a line. **Listen is not rendered while following** — the recording is the audio — and neither is the page's Translate, whose job the line's own "Translate line" does there; the header slot simply goes empty rather than reshaping.

- **The reader owns the player, and `$lib/media` owns everything else about it.** `bind:this` whichever element the stage holds, build the matching player in **one** effect — `videoPlayer` for the `<video>`, `youtubePlayer(frame, videoId, { onFail })` for the empty `<div>` — and tear it down in its cleanup; nothing below that line knows which it got. The object URL is its own effect whose cleanup is the revoke, so every replacement lets the previous file go; it and the picker and the session cache are **file-only paths** and a YouTube text touches none of them. `playable` is what the transport is disabled on — a file in hand, or an API that turned up — because "there is a player" is the same question with two answers. A YouTube load that fails puts one line in the picture's place and leaves the text and "Read as text" exactly as they were. `currentMs` is `$state` fed by `onTime`; the previous sample is a plain `let`, because it exists only to ask `crossedEnd` whether a boundary fell between two ticks and nothing renders it. Native `<video controls>` stays **on** — scrubbing, volume and fullscreen are free and better than anything written here — and our buttons add the operations a video does not have: replay the line (seek to its `start`, playing), next line (seek), play/pause, and an **auto-pause at line end that is off by default and never remembered**, since it turns a video into a drill. The keyboard mirrors them (Space, ←, →) and stands down whenever focus is in an `input`, `textarea`, `button`, `video`, `iframe` or anything contenteditable — and on a YouTube text it stops working altogether the moment the learner clicks into the player, which owns the keyboard from then on and is a caveat the transport states rather than one the page fights. **Position is not stored**: a text opens at 0, for the same reason it opens on page 1.

- **The transcript takes the panel's slot, and the card replaces it.** At ≥48rem the facing page shows every segment as a list, the current one highlighted and `scrollIntoView({ block: 'nearest' })`'d as it changes, each line a seek; a word card or a confirmation *replaces* it, so there is still exactly one panel whatever is in it — which is why the transcript wears `.word-card`'s own skin (`--surface`, border, radius) and its sticky heading is painted `--surface` too: a heading in `--bg` reads as a bar laid *over* the panel instead of as the panel's top edge. It is **gated on a `matchMedia('(min-width: 48rem)')` `$state`, not on CSS**: hiding a thousand buttons with `display: none` still builds a thousand buttons, and a phone should build none. The phone base case is untouched — video sticky at the top of the column, the current line under it in the usual `.prose` markup, the previous and next segments faint either side as plain un-tappable text (context and a seek, not reading), then the controls, then the word card as the sheet it always was. Two measurements there are the follow view's own, because its column is a picture and a handful of rows rather than a page: the current line keeps **two lines of room whether or not the caption wraps** (a one-to-two-line flip on every cue otherwise twitches everything under it, and the picture too inside the frame, since the stage is what gives), and the **half-screen the sheet has to be scrolled clear of is reserved only while a sheet is open** (`--tail`, a custom property so the wide frame's `padding-bottom: 0` still wins). The paged view keeps that tail permanently, because a page of prose already scrolls and adding the room on tap would make it scrollable in the same instant; the follow column is shorter than the phone, so a permanent tail is half a screen of nothing under the controls.

- **At ≥48rem the follow view is a frame, not a scroll.** The spread becomes `100dvh` minus the shell's `padding-block` — header row `auto`, content row `minmax(0, 1fr)`, `align-items: stretch` undoing `.spread`'s `start`, `min-height: 0` on both columns — and the transcript scrolls *inside itself* while the window does not scroll at all. The left column is a flex column in which the picture is the only thing that gives: the caption rows are `flex: 0 0 auto`, and `.stage` is `flex: 1 1 auto` with the video sized `height: 100%; width: auto` so the aspect ratio decides its width from the room left over. **The caption matches the picture**, not the column — the video's width cannot be derived from a stylesheet once its height is what sizes it, so it is measured with `bind:clientWidth` into `--film-width` on the column and the rows take `min(100%, max(var(--film-width), var(--measure)))`; the floor keeps a portrait or a small video from squeezing the line into a ribbon, and the `.pick` placeholder and the YouTube frame are measured the same way — one binding each, since a binding shared between two branches is zeroed by whichever unmounts last — so nothing jumps when the recording arrives. YouTube's frame is a bare `<div>` with no intrinsic ratio, so it declares `aspect-ratio: 16 / 9` and takes the same `height: 100%; width: auto` in the frame; its iframe is styled through `:global(iframe)`, because the API creates that element and Svelte's scoping class is never on it. The line goes up a notch at ≥72rem, where it is a caption under a large picture rather than a paragraph on a page. `has-error` names an extra row because the error banner is a `.spread-full` child that comes and goes and would otherwise land the columns in an implicit third row. At ≥72rem the cap comes off entirely — `.shell-follow` on `<main>`, a new class rather than a scoped `.shell` override — and the video column takes the width while the transcript stays `minmax(20rem, 28rem)`. **A recording is the one content width may enlarge; the prose beside it is still measured and centred.** `layout.md` carries the exception.

- **Media attaches at import and never afterwards**, because a text is immutable: the composer offers the recording **two ways and stores one** — a file slot and a YouTube link field on **one row** with "or" between them, **mutually exclusive**, each clearing the other as it is used (the file input is emptied by hand through a `bind:this`, since the browser owns its value and no state assignment reaches it). A link is parsed live by `videoIdFrom` and one line under the row says that it plays from YouTube, or that it is not a YouTube link, while there is still a box to correct; a file stores `{ kind: 'file', name, type }` and hands the `File` to `$lib/media`'s session cache before the `goto`, a link stores `{ kind: 'youtube', videoId }` and hands over nothing. Both are guarded on the segments being timed, because a recording a text has no offsets into is a reference nothing can follow — and that guard is **visible rather than silent**: the pair lives in a `<fieldset>` labelled "Recording" that is **always rendered** and simply `disabled` (one attribute, no per-input bookkeeping), its legend note reading *needs subtitles* while it is off and *optional* once it is live — the note is the whole explanation, and there is no sentence under it. A group that only appears once a paste happens to parse is a feature nobody knows the app has.

- **On a host that can fetch captions the link is also a *source*, and that inverts the fieldset's guard.** `captionsAvailable()` (`$lib/media`, `media.md`) answers `undefined` in a browser — so **nothing about captions renders there at all** — an object with no `ytdlp` on a desktop app that is missing the program, which earns one quiet line naming it (and Deno where that is the one missing), and an object with `ytdlp` on a host that can do it. On that host the recording group is **live from the start**, because pasting a link there is how the timings are *obtained* and waiting for them first would be a door locked from the inside; only the *file* picker keeps the old guard, as the one control with a `disabled` of its own, since a recording with no subtitles to follow is still a reference nothing can use. "Fetch captions" appears once the link names a video, and asks `listCaptions` **directly and not as a task** — one question whose answer is a list to choose from, and a list that arrived in the tray after the learner moved on would be no use — and the pick starts the `captions` task, whose result is dropped into `sourceFile` **as raw `json3`**, exactly as an upload is. That is what keeps `plan` **one derivation over one source**: a parsed cue list handed in beside the text would be a second source of truth for the one thing this composer derives once, and the card, the counter, the button's disabled state and `add()` would be free to disagree. Nothing else changes — the link is still in its field, so `add()` attaches `{ kind: 'youtube', videoId }` with no extra bookkeeping. On every later open a *file* text shows the picker in the video's place with the stored name, the line controls disabled until a file is chosen, and "Read as text" still working; a *YouTube* text needs nothing from the learner and only the network. `textAdded`'s payload struct has to name `Segment.start`/`end` and `media` explicitly — see `data.md`.
