# The challenge union

Stored side + presentation. Adding a type is a procedure — the `add-challenge-type` skill has it.

- `src/lib/challenges/` — the **stored side** of the challenge union: everything the app knows about a challenge once it exists. One module per stored type in `challenges/types/<type>.ts` bundling its stored zod `schema`, its grading rule (`check`), its difficulty tier (`demand`) and its four presentation facts (`correctAnswerText`, `answerIsTargetLanguage`, `answerReading`, `spokenAnswerFor`) — contract and doc in `types/def.ts`, shared zod pieces (`nonEmpty`, `directionSchema`, `storedBase`) in `types/primitives.ts`. `types/index.ts` is the registry, and it is a **mapped type over `ChallengeType`** (`{ [T in ChallengeType]: StoredTypeDef<…> }`), so a seventh member of the union fails `pnpm check` *at the registry*, naming the type with no module — one error for every fact at once, where the old exhaustive switches gave four separate ones and grading gave none. `demand` (0 recognition / 1 constrained production / 2 free production, dispatched by `demandOf` in `challenges/demand.ts`) is deliberately **not** consulted by `check`: grading stays type-blind because a verdict is FSRS's evidence about the *word*, so what difficulty shapes is the question stream (`$lib/session/progression`), never what an answer is worth. Everything downstream is a projection: `$lib/llm/schemas` composes `challengeSchema` from `storedChallengeSchemas` (union order pinned in `STORED_TYPE_ORDER`, membership parity-checked against `ChallengeType`) and re-exports the six stored schemas under their old names; `display.ts` and `check.ts` are one-lookup dispatchers through `storedDefFor` that keep every public signature (`spokenAnswerFor` is still re-exported from `$lib/session/engine`). `checkChallenge` lives in `$lib/challenges/check`, not `$lib/validate`: the string matchers underneath (`normalize`, `validateAnswer`, `checkAnswer`, used directly by the typing components) stay a **leaf** so the defs can import them without a cycle. Def modules may import zod, `$lib/types` and `$lib/validate` and nothing else — asserted in `types/registry.test.ts`, which also pins registry↔union order and the def→schema keying. `props.ts` is the `ChallengeProps<C>` contract every challenge component types its `$props()` with; `keyboard.ts` is the shared digit-select/Enter rule. Dispatch lives in `src/routes/learn/ChallengeHost.svelte` — an `{#if}` chain (a component map would lose the narrowing) whose `{:else}` is `unhandledChallenge(challenge: never)`. The **UI building blocks** the six components are composed from live in `src/routes/learn/blocks/`: `PromptHeader` (kicker + prompt + reading + speaker), `TapOption` (every tappable answer — three sizes, five states, wearing `.tap` from `app.css`), `TapRow`, `CheckButton`, and `answer-lock.svelte.ts` (the `locked`/`shownAt` pair and the reset keyed on `challenge.id`). A challenge component should be logic plus composition; anything that looks like a shared skin belongs in a block, not in a scoped override, because scoped overrides are exactly how the six drifted apart before. **Adding a challenge type** end to end is four registrations, each caught by a different gate when forgotten — the `add-challenge-type` skill has the procedure.
