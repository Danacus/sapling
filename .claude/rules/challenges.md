# The challenge union

Rust decides, TypeScript presents. Adding a type is a procedure — the `add-challenge-type` skill has it.

- **`crates/sapling-challenges` is the union and every decision about a challenge once it exists** — its stored shape, grading, difficulty, what a word can bear, what a served one shows, the free match round, and the two planners over the pool (`session.md`). No database and no model call (`core.md` places it in the stack): a host hands in the pool and the words and gets decisions back. The numbers are data — rung floors, serve ladders, the reading ramp and the listening share in `data/ladders.json`, the difficulty bases and scales in `data/difficulty.json`, each wire type's stored shape and plan in `data/kinds.json` — and every module's cases are `cargo test`s beside it.
  - **`challenge.rs` is the stored union, and Rust is its only source.** One struct per type, each carrying its own `type` literal (so a generated `ClozeChallenge` still has `type: "cloze"`), `Challenge` an untagged union with a hand-written `Deserialize` that dispatches on `type` — an unknown type is an error by name, never a guess. ts-rs generates the TypeScript (`pnpm core:types`) and `$lib/types` re-exports it (`data.md`). Parsing is **lenient on purpose**, because every row ever written must keep reading: an optional field may be absent or `null`, unknown fields are ignored, an index JavaScript printed as `1.0` reads as `1` — so the stored shape only ever gains **additive optional fields**. `check_shape` is the strict half — what a freshly resolved or locally built challenge must satisfy (filled strings, four options and an index inside them, two tiles, three tokens, a multi-cloze of 2–4 gaps each with its own item, every `___N___` marker exactly once and a bank of at least gaps + 2, as the resolver builds it) — and runs in `sapling-llm`'s resolver, never over a stored row. `ChallengeType::ALL` and the exhaustive `match`es over `Challenge` are the Rust gate: a new variant does not compile until every rule names it. `STORED_TYPES` is the pool's allow-list, which `sapling-db`'s materializer reads.
  - **Grading is `grade.rs` over the string matchers in `matcher.rs`, and it is type-blind.** The matchers know nothing of challenges: `normalize` (NFC, lowercase, `\p{P}`/`\p{S}` to spaces except an apostrophe or hyphen between two letters, JavaScript's whitespace collapsed), Damerau (optimal string alignment) edit distance over code points, a typo threshold by the accepted answer's UTF-16 length (up to 3: none; to 7: one; to 12: two; then three), and `validate_answer` → `AnswerMatch {verdict, closestAccepted, distance?}` — `correct` for an exact normalized match, `almost` for a diacritic-folded one or a typo within the threshold, and the nearest accepted answer whatever decided it. `check` per type: a typed answer (cloze, typed translation, multiple choice's option text) is fuzzy, a tapped one (word-order's assembled sentence, spot-error's *wrong* word, a match pair as `a::b`) exact; a multi-cloze is graded gap by gap (`grade_multi_cloze`: the worst verdict overall, and each gap's own for its word's review) from the `"1: Yo · 2: bebo"` form the component logs — `serializeMultiClozeAnswers` writes it on the TypeScript side, so that format is a contract across the seam. **Demand is never consulted by grading**: a verdict is FSRS's evidence about the *word*, so what difficulty shapes is the question stream, never what an answer is worth.
  - **`difficulty.rs`: the demand tier and, within it, how hard this row reads.** `demand_of` is 0 recognition (multiple choice either way, spot-error, match pairs, typed translation `toNative`), 1 constrained production (word-order, multi-cloze, a cloze with a bank), 2 free production (a bankless cloze, typed translation `toTarget`). `difficulty_of` scales `within_tier` — purely structural: a prompt's word count, a passage's gap placements (they grow as gaps! does) and length, a tile tray's own tiles, a pair count; never the bank or the distractors, which every generated row carries in full — into the tier's span of the strength axis (tier 0 is band 1, tier 1 bands 2–3, tier 2 bands 4–5, the floors bearability gates serving on), so a lower-demand row never outranks a higher-demand one. The number is compared **across** types for one word, so every prose length reads on one scale (1 to 12 words, `length_knob`) and each format starts from its `base` (`with_base`): multiple choice and match pairs 0 < typed translation 0.25 < spot-error 0.45 in recognition; banked cloze and word-order level at 0.2; multi-cloze 0.45. **A word count is the host's**: Chinese and Japanese write no spaces, so counting words is a dictionary lookup — the wasm host lends `Intl.Segmenter` (`$lib/text`'s `segmentWords`) as a callback, and without one (native callers, `cargo test`) Rust counts the way `segmentWords`' own fallback does, one word per character in a no-space script. Cloze splits its `___` out before counting: a segmenter reads a lone blank as a word and glues a mid-word one to its neighbours.
  - **`ladder.rs`: what a word can bear.** `Word` is the part of a `KnowledgeItem` the layer reads. Strength (the core's `srs.strength`, 0 for a word never scheduled) is cut into five rungs on four floors (0.15, 0.3, 0.45, 0.7); `level_band` states their spans and `level_band_centre` the middle of each; `demand_for_level` reads a rung as a tier (1 → 0, 2–3 → 1, 4–5 → 2) and `maturity_for_strength` at coarser resolution (new, young, solid). A challenge is judged by its **weakest** word, and an id that no longer resolves is the weakest there is. `bearable` compares `served_demand` — `demand_of`, except a banked cloze at the rung where its served bank is empty is answered typed, so reads 2 — with what the weakest word bears.
  - **`serve.rs`: what a served challenge shows**, decided from the weakest word's rung because a row outlives the rung it was written at — the native hint through rung 2 (a step, not a roll), a cloze's bank off an absolute ladder (3, 4, 5, 6, 0 — typed at the top), a multi-cloze's as its gaps plus that rung's distractors (0, 0, 0, 1, 2), a word-order's distractor tiles (0, 0, 1, 2, 3), each capped at what is stored and each most supportive at rung 1. `visible_bank`/`visible_tiles` pick *which* entries: the answers where they sit, then the first others in stored order, as positions so an index-aligned reading array slices the same way. `plan_readings` rolls once at serve time: the whole-challenge roll from the weakest word, then one per known word in id order from its own strength, linear between hiding nothing at 0.35 and everything at 0.85. `is_listening` takes a `toNative` multiple choice whose id hashes (FNV-1a over UTF-16 units) under the share. `presentation_for` folds the four.
  - `match_pairs.rs` builds the free round (`session.md`); `kinds.rs` is the kinds a challenge is written as — `WireType`, each one's stored shape and, while it is generated, its demand and rungs, and `kind_of` back from a stored row; `rng.rs` is the one random source, which `sapling-llm` shares.

- **The seam is `src/lib/challenges/core.ts`**: `callChallenges(method, args)`, **synchronous**, over the wasm build's `challenges` export and `sapling-protocol`'s `challenges!` table (`core.md`), whose TypeScript (`Challenges`, `CHALLENGE_METHODS`, `SESSION_LENGTH`) is generated into `challenges.ts`. It lends `countWords`, and `asWords` slims each item to a `Word` before it crosses. Because the calls are synchronous the wasm must already be instantiated: the root layout's `load` awaits `loadWindowCore()` (`$lib/db/window-core`, shared with `callLlm`) before the first page renders, and vitest's setup file (`src/lib/db/wasm.setup.ts`) instantiates it for every test file. Over it, thin wrappers under the names callers import: `./check` (`checkChallenge`, `validateAnswer` — what the typing components grade with as they commit — and `gradeMultiClozeAnswers`), `./serve` (`presentationFor`, which turns the readings' `byTerm` into a `Map`; `visibleBank`, `visibleTiles`, `isListeningChallenge`, `maturityOf`, `hideReadingProbability`; and `resolvedPresentation`, the bare-render defaults — hint on, the whole stored bank and tray, `ALL_READINGS` — which are this side's), and `./readings` (`applyPlan`, `rubyFor`, `storedReading`, `termReading`, `readingSlot`: a served plan applied to the romanizer's tokens, a per-slot lookup that stays beside the tokens rather than crossing for each one). Their vitest tests are thin, over the seam; the cases are Rust's.

- **Presentation stays TypeScript.** One module per stored type in `challenges/types/<type>.ts` — its two session facts (`reviewsSrs`, `pooled`: false only for match pairs) and its five presentation facts (`correctAnswerText`, `answerIsTargetLanguage`, `answerReading`, `spokenAnswerFor`, `audioTexts`) — contract and doc in `types/def.ts`. `types/index.ts` is the registry, a **mapped type over `ChallengeType`** — `Challenge['type']` of the generated union — so a member added in Rust fails `pnpm check` *at the registry*, naming the type with no def. Defs are leaves: they import `$lib/types` and `./def` and nothing else, asserted in `types/registry.test.ts`. `display.ts` is the one-lookup dispatcher through `storedDefFor` (`spokenAnswerFor` is re-exported from `$lib/session/engine`). `props.ts` is the `ChallengeProps<C>` contract every challenge component types its `$props()` with; `keyboard.ts` is the shared digit-select/Enter rule. Dispatch lives in `src/routes/learn/ChallengeHost.svelte` — an `{#if}` chain (a component map would lose the narrowing) whose `{:else}` is `unhandledChallenge(challenge: never)`. The **UI building blocks** the challenge components are composed from live in `src/routes/learn/blocks/`: `PromptHeader` (kicker + prompt + reading + speaker), `TapOption` (every tappable answer — three sizes, five states, wearing `.tap` from `app.css`), `TapRow`, `CheckButton`, and `answer-lock.svelte.ts` (the `locked`/`shownAt` pair and the reset keyed on `challenge.id`). A challenge component should be logic plus composition; anything that looks like a shared skin belongs in a block, not in a scoped override, because scoped overrides are exactly how the six drifted apart before. **Adding a challenge type** end to end is a handful of registrations, each caught by a different gate when forgotten — the `add-challenge-type` skill has the procedure.
