# The challenge union

Rust decides, TypeScript presents. Adding a type is a procedure — the `add-challenge-type` skill has it.

- **`crates/sapling-challenges` is the union and every decision about a challenge once it exists** — its stored shape, grading, the help levels a row can be shown at, how hard it is for which word (one learned scale), what a served one shows, the free match round, and the two decisions over the pool — the practice stream's next pick and the top-up, both read off one list (`session.md`). No database and no model call (`core.md` places it in the stack): a host hands in the pool, the words and the learned numbers and gets decisions back. The numbers are data — the model's starting values, rates, aims and window in `data/model.json`, each wire type's stored shape and length range in `data/kinds.json` — and every module's cases are `cargo test`s beside it.
  - **`challenge.rs` is the stored union, and Rust is its only source.** One struct per type, each carrying its own `type` literal (so a generated `ClozeChallenge` still has `type: "cloze"`), `Challenge` an untagged union with a hand-written `Deserialize` that dispatches on `type` — an unknown type is an error by name, never a guess. ts-rs generates the TypeScript (`pnpm core:types`) and `$lib/types` re-exports it (`data.md`). Parsing is **lenient on purpose**, because every row ever written must keep reading: an optional field may be absent or `null`, unknown fields are ignored, an index JavaScript printed as `1.0` reads as `1` — so the stored shape only ever gains **additive optional fields**. `check_shape` is the strict half — what a freshly resolved or locally built challenge must satisfy (filled strings, four options and an index inside them, two tiles, three tokens, a multi-cloze of 2–4 gaps each with its own item, every `___N___` marker exactly once and a bank of at least gaps + 2, as the resolver builds it) — and runs in `sapling-llm`'s resolver, never over a stored row. Every type but match pairs carries an optional `length` — the length the row was asked to be written at, stamped by `sapling-llm` when it fills a want (`set_asked_length`), absent on older rows. `ChallengeType::ALL` and the exhaustive `match`es over `Challenge` are the Rust gate: a new variant does not compile until every rule names it. `STORED_TYPES` is the pool's allow-list, which `sapling-db`'s materializer reads.
  - **Grading is `grade.rs` over the string matchers in `matcher.rs`, and it is type-blind.** The matchers know nothing of challenges: `normalize` (NFC, lowercase, `\p{P}`/`\p{S}` to spaces except an apostrophe or hyphen between two letters, JavaScript's whitespace collapsed), Damerau (optimal string alignment) edit distance over code points, a typo threshold by the accepted answer's UTF-16 length (up to 3: none; to 7: one; to 12: two; then three), and `validate_answer` → `AnswerMatch {verdict, closestAccepted, distance?}` — `correct` for an exact normalized match, `almost` for a diacritic-folded one or a typo within the threshold, and the nearest accepted answer whatever decided it. `check` per type: a typed answer (cloze, typed translation, multiple choice's option text) is fuzzy, a tapped one (word-order's assembled sentence, spot-error's *wrong* word, a match pair as `a::b`) exact; a multi-cloze is graded gap by gap (`grade_multi_cloze`: the worst verdict overall, and each gap's own for its word's review) from the `"1: Yo · 2: bebo"` form the component logs — `serializeMultiClozeAnswers` writes it on the TypeScript side, so that format is a contract across the seam. **Difficulty is never consulted by grading**: a verdict is FSRS's evidence about the *word* and the difficulty model's evidence about the row, so what difficulty shapes is the question stream, never what an answer is worth.
  - **`word.rs`: the part of a word the layer reads.** `Word` is a `KnowledgeItem` slimmed for the crossing — id, term, meaning, reading, `srs`, and the model's `skill` (absent until an answer names the word, which reads as the starting skill). `memory()` is FSRS's retrievability, or the model's new-word memory for a word FSRS has no curve for. Two facts here are **display only** and decide nothing served: `maturity_for_strength` (new/young/solid off the strength bar, at 0.15 and 0.45 — the home page's garden and the reader's colours) and `hide_reading_probability` (the reader's per-word reading ramp, 0.35 to 0.85).
  - **`serve.rs`: a help level as a screen.** `presentation_for(challenge, help)` is a pure function of the row and the help level serving picked: `pick-4` shows four bank entries and the native hint, `pick-6` six and no hint, `typed` none; a multi-cloze's `answers` its gaps, `extra-2` two more; a word-order's `tiles` its own tiles with the native line, `extra-2` two distractors without it; `plain` the row as stored, hint included — each capped at what the row stores. The reading is shown or hidden as a whole (`ReadingPlan.sentence`; `byTerm` stays empty), `listening` is the listening level, and `shown` is the level's id, which the answer records. `visible_bank`/`visible_tiles` pick *which* entries: the answers where they sit, then the first others in stored order, as positions so an index-aligned reading array slices the same way.
  - **`help.rs`: help levels** — one version of a stored row with more or less help on screen, named by one stable string an answer records as `shown` (`ChallengeResult.shown`, additive) and the shared difficulty numbers are keyed by. A **step** from a short list per type (`plain`; a cloze `pick-4` · `pick-6` · `typed`; a multi-cloze `answers` · `extra-2`; a word-order `tiles` · `extra-2`), `-hidden` where the row stores a reading and it is hidden, or `listening`. `steps_of` lists only the steps a row's stored content can tell apart (a bankless cloze is only `typed`); `help_level_of` reads a screen's sizes back as a level (what `legacy.rs` reconstructs old answers through). Which combinations exist for a row is `fits.rs`' `help_levels`: every step with its reading shown, the hardest step with it hidden too, and listening where the row is a recognize-style multiple choice and the device can speak — bounded by the readings setting (`off` hides every reading, `on` never does).
  - **The difficulty model (`model.rs`), learned from answers** (`docs/challenge-difficulty.md`): `chance = memory × sigmoid(skill − difficulty)` on a logit scale, `difficulty = base(kind, help level) + slope(kind) × length + correction(row)`. Memory is FSRS retrievability just before the answer (a never-reviewed word reads `newWordMemory`); several words multiply their memories and combine skills by `MULTI_WORD` (`average`, what the first real log chose; `lowest` is the other candidate). Each answer moves every word's skill **up** and every difficulty part **down** by its rate × `outcome − chance` (the slope by its length in tens). Starting values, rates, aims and the window are `data/model.json`; the aims are on the chance given the word is remembered (Easier/Normal/Harder → 0.97/0.89/0.78, the 88/80/70% a learner experiences at FSRS's 0.9 memory) and the window is aim −17 to +4 points; the starting skill is derived — a one-word recognize-mc lands on `newWordChance`. **A row's length is the one it was asked for** (`length_of` reads the stored `length` first), so a row written as asked is judged exactly as its writer meant and the row's correction learns how far the writing drifted; a row from before that was recorded is measured, and **measuring is `words_in`, never the host's segmenter**: a spaced word counts one, a no-space character half, because a learned number is derived data every device (and the Worker, which has no segmenter) must reproduce exactly.
  - **`replay.rs` turns a log into observations** — the one path both callers use. Answers replay in `(at, event id)` order, not arrival order, so every device derives the same numbers; memory comes from folding each word's reviews strictly before the answer; an answer is skipped when its challenge is unknown or a match round, a word it names is gone, or its `shown` is an id this build cannot read. An answer with no `shown` is reconstructed once by `legacy.rs`, from the weakest word's strength at the time through a **frozen** copy of the old serve ladders (never listening; the reading hidden where the old roll favoured hiding). `input_from_events` folds an export the way the merge rules do — an overturned answer (`resultOverturned`) at the verdict it was overturned to, wherever the overturn sits — for the calibration command.
  - **`calibrate.rs` and `src/bin/calibrate.rs` measure the tuning**: replay a log predicting each answer before learning from it, and report mean log loss (with the always-guess-the-average baseline), both multi-word combinations, and a predicted-band table; `--search` tries a grid of rates, `--seeds N` averages the grid over N simulated learners (how the rates in `model.json` were chosen). `cargo run -p sapling-challenges --bin calibrate -- export.json` reads the profile page's export; `--simulated` runs `sim.rs`, a learner with known skills and difficulties that writes a real export envelope, steered by the model with its own fixed rates and aim so the fixture does not move when the tuned ones do. Its tests are the fixture: the model beats the baseline, big bands are honest to 12 points, `MULTI_WORD` is the better-scoring combination and the rates are the grid's best within 0.005.
  - **`fits.rs`: the one check** serving and refill both ask, through the one predicate (`stream.rs`' `available`). A row fits a word at a help level when the chance *given the words are remembered*, `sigmoid(skill − difficulty)`, sits inside the window around the aim — memory picks which word comes up and never which row it gets, so an overdue word is judged exactly as it would be on time; `chance_of` is the whole prediction, memory included, for scoring alone. The window is **widened per skill just far enough to take in the nearest writable row** (`window_for`: every active kind at each help level a row written now will be served at — `written_levels`, the same `levels` rule `help_levels` reads off a stored row, over the kind's written steps, `Serving.readings` and whether the kind can be heard — at every length in its range, correction 0), so "too hard" never applies to the easiest row there is and "too easy" never to the hardest — every word always fits something a writer can produce, which is what lets serving wait on its head word. `topup.rs`' `length_for` solves the same function backwards over the same levels, so a row written as asked fits — under readings off too, where a row with readings is served only at its `-hidden` levels. A row's fit does not depend on which of its words it is served for: several words are judged by their combined skill, and `fits_fresh` is that check on a row just written, which `sapling-llm`'s filler asks before counting a row about several words as a want filled (`llm.md`). `invariants.rs` (tests only) pins the whole loop, for a language without readings and one with them under every readings setting (and listening): rows written as requested — passages pairing their word with another, kept only when they fit — are served and want nothing more at every skill and aim, and over a simulated learner whose model learns as it answers, with the writing drifting in length and a word never asked for twice before something of it is served, a blocked head is always one not asked for yet and is unblocked by one refill, every pick is the head of the list refill reads, and a head with something is never passed. `best_fit` is the help level inside the window closest to the aim. `Serving` is everything besides the pool and the words a pick is made against: the learned `parts`, the learner's `aim` (a profile setting, `normal` when absent), the readings setting and whether listening is possible (`$lib/session/serving`'s `deviceServing`), and `readings` — whether a row written now carries readings, the target language's (`servingFor`), absent read as `false`.
  - `match_pairs.rs` builds the free round (`session.md`), a fixed five pairs, three at least, which `stream.rs`' `match_round` draws from the early words; `kinds.rs` is the kinds a challenge is written as — `WireType`, each one's stored shape and, while it is written, its length range and `written_steps`, and `kind_of` back from a stored row; `rng.rs` is the one random source, which `sapling-llm` shares.

- **The seam is `src/lib/challenges/core.ts`**: `callChallenges(method, args)`, **synchronous**, over the wasm build's `challenges` export and `sapling-protocol`'s `challenges!` table (`core.md`), whose TypeScript (`Challenges`, `CHALLENGE_METHODS`, `MATCH_PAIRS_EVERY`) is generated into `challenges.ts`. It lends `countWords` (which nothing reads any more: difficulty measures length with the model's own `words_in`, identical in the Worker and on every device), and `asWords` slims each item to a `Word`, `skill` included, before it crosses. Because the calls are synchronous the wasm must already be instantiated: the root layout's `load` awaits `loadWindowCore()` (`$lib/db/window-core`, shared with `callLlm`) before the first page renders, and vitest's setup file (`src/lib/db/wasm.setup.ts`) instantiates it for every test file. Over it, thin wrappers under the names callers import: `./check` (`checkChallenge`, `validateAnswer` — what the typing components grade with as they commit — and `gradeMultiClozeAnswers`), `./serve` (`presentationFor(challenge, shown)`, which turns the readings' `byTerm` into a `Map`; `visibleBank`, `visibleTiles`, `maturityOf`, `hideReadingProbability`; and `resolvedPresentation`, the bare-render defaults — hint on, the whole stored bank and tray, `ALL_READINGS`, not listening — which are this side's), and `./readings` (`applyPlan`, `rubyFor`, `storedReading`, `termReading`, `readingSlot`: a served plan applied to the romanizer's tokens, a per-slot lookup that stays beside the tokens rather than crossing for each one). Their vitest tests are thin, over the seam; the cases are Rust's.

- **Presentation stays TypeScript.** One module per stored type in `challenges/types/<type>.ts` — its two session facts (`reviewsSrs`, `pooled`: false only for match pairs) and its five presentation facts (`correctAnswerText`, `answerIsTargetLanguage`, `answerReading`, `spokenAnswerFor`, `audioTexts`) — contract and doc in `types/def.ts`. `types/index.ts` is the registry, a **mapped type over `ChallengeType`** — `Challenge['type']` of the generated union — so a member added in Rust fails `pnpm check` *at the registry*, naming the type with no def. Defs are leaves: they import `$lib/types` and `./def` and nothing else, asserted in `types/registry.test.ts`. `display.ts` is the one-lookup dispatcher through `storedDefFor` (`spokenAnswerFor` is re-exported from `$lib/session/engine`). `props.ts` is the `ChallengeProps<C>` contract every challenge component types its `$props()` with; `keyboard.ts` is the shared digit-select/Enter rule. Dispatch lives in `src/routes/learn/ChallengeHost.svelte` — an `{#if}` chain (a component map would lose the narrowing) whose `{:else}` is `unhandledChallenge(challenge: never)`. The **UI building blocks** the challenge components are composed from live in `src/routes/learn/blocks/`: `PromptHeader` (kicker + prompt + reading + speaker), `TapOption` (every tappable answer — three sizes, five states, wearing `.tap` from `app.css`), `TapRow`, `CheckButton`, and `answer-lock.svelte.ts` (the `locked`/`shownAt` pair and the reset keyed on `challenge.id`). A challenge component should be logic plus composition; anything that looks like a shared skin belongs in a block, not in a scoped override, because scoped overrides are exactly how the six drifted apart before. **Adding a challenge type** end to end is a handful of registrations, each caught by a different gate when forgotten — the `add-challenge-type` skill has the procedure.
