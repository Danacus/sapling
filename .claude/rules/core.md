# The Rust core

The persistence core is a stack of crates, one job each, and the dependencies only point down it:

- **`sapling-srs`** — the scheduler: a function of a card, a grade and a time. It knows no events and no SQL.
- **`sapling-domain`** — the event log as a contract: the event and payload schemas (`events.rs`), the domain types they and the reads carry (`types.rs`), the `LocalDay` calendar seam (`day.rs`) and `PROFILE_ID`. serde only; it knows nothing of SQL, so anything that reads, writes or ships events can depend on it alone.
- **`sapling-db`** — the database: the `Sql` trait (`sql.rs`), the DDL and read-table constants (`schema.rs`), the merge rules (`materialize.rs`) and `Core`, every `Backend` method (`core.rs`). It never opens a database and never mentions rusqlite.
- **`sapling-protocol`** — the `Backend` protocol by name: `METHODS`, `dispatch` and `dispatch_json`, a method name and a JSON argument array in, JSON out, over `Core`.
- **`sapling-wasm`** wraps db and protocol for a JavaScript host; that build runs inside the database Worker in the browser and in-process in node tests. **`sapling-store`** is the native host: `Core` over a SQLite file in a directory through its own `rusqlite_sql` (the only crate that links rusqlite), with the device id, clock and time zone an OS lends (`desktop.md`), Tauri-free so anything native opens the same database the same way.

There is no TypeScript implementation any more, and `src/lib/db/` keeps only the protocol, the transport and the host glue. A hosted instance would run the same crates over a different `Sql`.

- **It never opens a database.** Everything is written against the `Sql` trait in `sql.rs` — `exec` and `query`, synchronous, parameters as `Param`, rows as `Row` — and a host hands the crate a database: `sapling-store`'s `rusqlite_sql.rs` is the adapter native hosts and `sapling-db`'s own tests use; `sapling-wasm`'s `JsSql` borrows the browser's sqlite-wasm through two callbacks. Nothing in the crate may depend on which. `sapling-db` reaches rusqlite only through a dev-dependency on `sapling-store`, which depends on it in turn — a cycle cargo allows for `tests/` alone, so a test that needs a real SQLite is an integration test (`tests/golden.rs`, `tests/pending.rs`), never a unit test under `src/`, where it would link a second copy of the crate and the types would stop matching. A `Row` names its columns once for a whole result and every row of that result shares the list (`Row::with_names`; `Row::new` is the one-off), so a thousand-row page costs one header and not a `String` per cell. `rusqlite_sql` compiles each parameterised statement once and keeps it (`prepare_cached`, capacity 128 — comfortably over the ~70 shapes the core issues, so a widening `IN (?, …)` never evicts a hot one) and binds text by reference; SQLite re-prepares a cached statement itself when the schema under it moves, which is what makes `open_schema`'s drop-and-rebuild safe. The parameterless `exec` stays `execute_batch`, because that path is where a whole script arrives — the DDL, `BEGIN`, a `DELETE` — and a prepared statement is only ever the first one. A number binds as sqlite-wasm binds a JavaScript `number`: integral as `INTEGER`, otherwise `REAL` (`Param::number`), and an integral JSON number read back is an `INTEGER` for the same reason.

- **The host lends four runtime facts and one boundary** (`src/lib/db/host.ts`). `openCore(db, { deviceId, clock?, ids? })` gives the wasm `WasmCore` its `exec`/`query` over sqlite-wasm's `oo1` API, `localDay` from `day.ts` (the *only* place a time zone exists — `sapling-domain`'s `Utc` is what fixtures pin), the clock and the id generator, and the constructor applies the schema, replaying the log if the read tables are stale. `directOf(core)` turns `dispatch(method, argsJson)` back into the `Direct<Backend>` that `protocol.ts`'s `dispatch`/`promised` wrap. JSON strings cross in both directions and `undefined` is "no string": a `void` method and a read of a missing row both come back `undefined`, never `null`, because the TypeScript signatures say so. An argument the caller left out arrives as `null` and `sapling-protocol` reads it as absent.

- **`sapling-protocol` is the other end of `protocol.ts`, and the two are gated against each other.** `METHODS` must equal `BACKEND_METHODS`; its `cargo test` reads `src/lib/db/protocol.ts` and compares, and a second test calls every listed name so an arm cannot be missing. Adding a method is therefore three edits — the interface, the list, the arm — and forgetting any one fails `pnpm check` or `pnpm core:test`.

- **JSON goes out through serde_json, and how a number prints is not a contract.** Cards, payloads, `recentGrades`, challenge content and the export file are `serde_json::to_string` (`to_string_pretty` for the export), so an `f64` field prints as `1.0` where the old JavaScript core wrote `1`; every reader — `JSON.parse`, serde, SQLite's `json_extract` — reads the same value either way, and rows written the old way still parse. `preserve_order` is on so objects keep the key order they arrived with. **The one place a printed number is an identity is `review_key`** (`itemId|at|device`, the cross-device key of a review): it formats `at` with `f64`'s `Display`, which prints a whole millisecond without a fraction, exactly as the rows already on every device have it, and `schema.rs` pins that. The pull cursor in `meta` is formatted the same way. Anything else that ever turns a number into an identity or a SQL text parameter must do the same.

- **Payload structs are the schemas now, optional fields included** (`sapling-domain`'s `events.rs`, `types.rs`); `src/lib/db/events.ts` is the type-only mirror the TypeScript compiles against. Serde strips unknown fields exactly as zod did, so a struct that forgets an optional field loses it on every device the event arrives at. Every optional field is `#[serde(default, deserialize_with = "absent_or", skip_serializing_if = "Option::is_none")]`: absent is `None`, `null` is a parse error (zod's `.optional()` was not `.nullable()`), and `None` is omitted on the way out (`JSON.stringify` drops `undefined`). The `parse_event(raw) == raw` test in `events.rs` lists one payload per type with every optional field present; a new field goes there, in the TypeScript type, or that test is what fails. `parse_event` is the gate for every row off sync or out of a backup file, and a local `commit` never goes through it. **The gate costs a row its merge rule, never its place in the log**: `parse_envelope` reads the envelope alone and keeps the payload as it arrived, `typed_event` is the half that needs a schema, and `pending_events`/`export_data` read rows through `raw_from_row` without asking either — push and export carry log rows verbatim, only materialization interprets a payload, and a row it cannot read is skipped, never dropped. So `pending_events(limit)` is the first `limit` unpushed rows with no gaps, and a row a newer build wrote survives a round trip through an older device. `CHALLENGE_TYPES` in `materialize.rs` is the pool's allow-list: a new challenge type goes there or its challenges are written to the log and skipped on the way into the pool.

- **The SRS is `crates/sapling-srs`: the `fsrs` crate's model inside this app's card state machine.** It is a crate of its own so it stays a function of a card, a grade and a time — it knows nothing of events, SQL or the schema, `sapling-domain` and `sapling-db` depend on it and never the other way, and it carries the `fsrs` dependency and the `getrandom` `wasm_js` workaround the wasm build needs. The `fsrs` crate owns the model — FSRS-6, `DEFAULT_PARAMETERS` (the 21 FSRS-6 weights, pinned by a test), `desired_retention` 0.9, and `next_states(memory, retention, days_elapsed)` for the four grades' memory states and intervals. `sapling-srs` owns everything around it, because the crate has no opinion on any of it: the New/Learning/Review/Relearning machine, learning steps `1m`/`10m` and relearning `10m`, `reps`, `lapses`, `elapsed_days`, `scheduled_days`, `due`, the [1, 36500] clamp, the hard < good < easy ordering rule and the `FsrsCardState` JSON, whose `stability` and `difficulty` are the model's own `f32`s (a card stored with longer `f64` numbers still reads). The model's floats differ slightly between the native and wasm builds, so every test compares them with a tolerance, never for equality. `next_states` reads no clock and no RNG (the crate's randomness is all in its optimizer), so the "every function takes `now`" rule holds; a negative elapsed time reads as zero days. **`sapling-srs` also owns the reading side, because the frontend has no FSRS at all.** `current_retrievability` is the crate's forgetting curve at `now` (whole floored elapsed days, never negative, and 0 for a card the model has never seen), `word_strength` is log-stability × retrievability against `MATURE_STABILITY_DAYS`, and `item_srs` bundles the two with the card's `due` into `ItemSrs`, which `core.rs`'s `item_from` attaches to every item `getAllItems` and `getItem` return (`get_all_items` reads the clock once for the whole batch). A card too malformed to parse simply carries no `srs`: a read must not fail over a display number. `src/lib/srs/` keeps only grades, the opaque `FsrsCardState` type, `isDue` as a `due <= now` comparison and `selectSessionItems`; a test that wants a card must read it back from the store. Changing what a review folds to means bumping `DERIVED_SCHEMA_VERSION`, or devices carry a mix of old and new cards item by item.

- **The wasm build is generated, never committed.** `pnpm core:wasm` compiles `sapling-wasm` for `wasm32-unknown-unknown` and runs `wasm-bindgen --target web` into `src/lib/db/wasm/` (gitignored); `pnpm dev|build|check|test` each run it first, so a clean checkout works and a stale artefact cannot outlive an edit to the crate. The Worker loads the `.wasm` by URL (`?url`), node tests `initSync` the same bytes from disk (`backend.testing.ts`). The `wasm-bindgen` crate version in `crates/sapling-wasm/Cargo.toml` is pinned `=` to the `wasm-bindgen-cli` the flake ships — a mismatch is a hard error at bindgen time — and the target links with `lld`, which the flake provides because nixpkgs' rustc does not bundle `rust-lld`. Only the release profile is used for wasm; it is tuned for size (`opt-level = "s"`, LTO, `panic = "abort"`).

- **The fixtures are the acceptance test, twice** (`sapling-db`'s `tests/golden.rs` and `src/lib/db/golden.test.ts`). Both discover `src/lib/db/fixtures/*`, probe every read exactly as the fixtures README describes, and run the same idempotence, export/import, log round-trip and reverse-arrival checks — the Rust one natively over rusqlite, the TypeScript one over the wasm build through the browser-shaped path. They compare **values, not text**: `golden.rs` canonicalises every whole-valued number to an integer before comparing, because `expected.json` is written by JavaScript and serde_json keeps `1` and `1.0` apart. A value that does not match is a finding about the core, never a reason to edit a fixture. **One exception:** the four numbers that come out of the `f32` model — a card's `stability` and `difficulty`, and the `srs.retrievability` and `srs.strength` derived from them — are compared with a `1e-4` relative tolerance (`MODEL_FLOATS` in both files), because they differ slightly between the native and wasm builds. Everything else, `due`, `srs.due` and `scheduled_days` included, still matches exactly. `pnpm core:test` runs the Rust suite; `pnpm core:check` is clippy with warnings denied plus rustfmt. Nix flakes only see staged files — `git add` a new source file before `nix develop` or the toolchain will not see it either.
