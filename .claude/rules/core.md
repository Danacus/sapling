# The Rust core

The persistence core is a stack of crates, one job each, and the dependencies only point down it:

- **`sapling-srs`** — the scheduler: a function of a card, a grade and a time. It knows no events and no SQL.
- **`sapling-domain`** — the event log as a contract: the event and payload schemas (`events.rs`), the domain types they and the reads carry (`types.rs`), the `LocalDay` calendar seam (`day.rs`) and `PROFILE_ID`. serde only; it knows nothing of SQL, so anything that reads, writes or ships events can depend on it alone.
- **`sapling-challenges`** — the challenge union and every decision about a challenge once it exists: the stored shape (`challenge.rs`, the source of the TypeScript union), grading over the string matchers (`grade.rs`, `matcher.rs`), the words it reads (`word.rs`), the one check serving and refill ask (`fits.rs`), what a served challenge shows (`serve.rs`), the free match round (`match_pairs.rs`), help levels (`help.rs`), the learned difficulty model with its replay and calibration command (`model.rs`, `replay.rs`, `legacy.rs`, `calibrate.rs`, `sim.rs`, `src/bin/calibrate.rs`), the kinds a challenge is written as (`kinds.rs`, `data/kinds.json`), and the practice stream and top-up planner over the pool (`stream.rs`, `topup.rs`, `pool.rs`) — `challenges.md` and `session.md` are its contract. It depends on `sapling-domain` (the `Verdict`) and `sapling-srs` (a word's `ItemSrs`) and on nothing above; no SQL, no `Core`, no model call. Its numbers are data (`data/*.json`, `include_str!`), its one random source is `rng.rs`'s SplitMix64 (seeded by a caller that wants a replay, from `getrandom` otherwise), and a length is its own (`model.rs`' `words_in`, never the host's segmenter, because the model's learned numbers are derived data every device and the Worker must reproduce exactly). The one binary, `calibrate`, replays an export or the simulated learner through the model natively (`cargo run -p sapling-challenges --bin calibrate -- export.json`).
- **`sapling-db`** — the database: the `Sql` trait (`sql.rs`), the DDL and read-table constants (`schema.rs`), the merge rules (`materialize.rs`) and `Core`, every `Backend` method (`core.rs`). It never opens a database and never mentions rusqlite.
- **`sapling-import`** — the reading import, whole: subtitle detection and parsing (SRT, VTT, json3, a copied transcript panel) into **one timed segment per cue** — never joined, never re-cut into sentences — and prose into **one untimed segment per paragraph**. Its output is `sapling-domain`'s `Segment` itself (its one workspace dependency), so what `importSource` answers is what `addText` stores. A plain library beside the stack rather than in it — no SQL, no `Core`, no I/O, a function of the text alone — exposed as `importSource`, the one method in the table that ignores `core`. The CJK test that decides whether a cue's lines join with a space is Unicode block ranges, not script data, to keep a table out of the wasm build.
- **`sapling-llm`** — the model calls, stateless: the OpenRouter chat client (`client.rs`: error kinds, tool calling, usage, one retry without `response_format` when an endpoint rejects structured outputs, a progress sink), strict reply schemas from `schemars` derives (`json.rs`), and the calls: `reading.rs`, `lesson.rs` (a top-up), `escalation.rs`, `word_batch.rs` (the word-check grid), over `kinds.rs` (each wire type's lesson spec; the kinds themselves are `sapling-challenges`') and `wire.rs` (wire structs and resolvers, whose output must parse as `sapling-challenges`' `Challenge` and pass its `check_shape`) — `llm.md` is their contract — and the tool-calling ones: `tools.rs` (the `ToolContext` trait, the four word-list tools, the shared loop), `chat.rs` and `conversation.rs` — `assistant.md` is theirs. **Prompts, per-type specs, tool descriptions and mock fixtures are data** (`prompts/*.txt`, `lessons/<type>.json`, `fixtures/*`, `include_str!`); mock mode is `Llm` with no `Endpoint`, and a mock reply goes through the same parser as a live one (`complete_or` lets a mock call tools, so the tool mocks run the real loop). The HTTP POST is a `Transport` and the word list a `ToolContext` the host injects — tests use fakes and `MemoryTools`, the wasm build the window's `fetch` and repositories. `text.rs` restates the few `$lib/text` rules a resolver or tool needs (term and reading keys, `same_card`, the loose `same_romanization`, script-aware token joining) and re-exports what it shares with grading from `sapling-challenges` (label keys, diacritic folding, the block-range script test, the RNG for challenge ids and shuffles). A want (`Want`, `WantItem`, `ChallengeKind`) is `sapling-challenges`' too. No SQL, no `Core`.
- **`sapling-sync`** — the sync client, host-agnostic: the pairing phrase (`phrase.rs`: normalise, validate, mint from host-drawn bytes, format; `BAD_PHRASE`), and in `lib.rs` one cycle against the relay (`run`: push pending events in pages of 500, stamp what was acknowledged, pull pages of 1000 from the cursor, apply each before advancing the cursor), the liveness probe (`probe`) and pairing (`pair`: one cycle, then whether a profile came down the log — it never writes one). **Every failure is an outcome value** (`SyncOutcome`, `SyncProbeResult`, `PairOutcome`, each with its learner-facing text), never an `Err`. The HTTP request is a `Transport` (method, URL, headers, optional body; `Err` is no response at all) and the database a `SyncStore` (`pending_events`, `mark_pushed`, `apply_remote`, the pull cursor, `has_profile`), both injected; the relay's URL and the phrase are arguments and the crate reads no configuration. It depends on `sapling-domain` (`RawEvent`, `parse_envelope`) alone — no SQL, no `Core`. `relay.rs`'s `MemoryRelay` speaks `worker/`'s wire protocol in memory, for tests of the cycle here and of a store elsewhere. `fixtures/phrases.json` is the language-neutral phrase cases `phrase.rs`' tests and `worker/phrase.test.ts` both run (`deploy.md`). Joining a cycle already running is the host's.
- **`sapling-protocol`** — the `Backend` protocol by name: the `backend!` method table, the `dispatch` and `dispatch_json` it expands into (a method name and a JSON argument array in, JSON out, over `Core`), and the generator of the TypeScript wire types. Beside it, `llm.rs`'s `llm!` table: the model calls by name, async, one argument object each, over an `Llm` and an optional `ToolContext` rather than `Core` (an entry that runs tools asks for it with `needs(tools)?`); `dispatch_llm_json` answers `{result, usage?}` and fails with the `LlmError` as JSON, or plain text for a malformed call or a store failing under a tool. It generates `llm.ts` (`Llm`, `LLM_METHODS`, the prompt caps, `REQUEST_ITEMS`). And `challenges.rs`'s `challenges!` table: the challenge decisions by name, **synchronous**, one argument object each, over nothing but the host's word counter — grading, what a served challenge shows, the planners (a seed, where a method takes one, replays its draws); `dispatch_challenges_json` answers the JSON and fails with plain text. A pool argument is read row by row, and a row that does not parse keeps its place as nothing, so a plan's positions still index the host's array. It generates `challenges.ts` (`Challenges`, `CHALLENGE_METHODS`, `MATCH_PAIRS_EVERY`). And `sync.rs`'s `sync!` table: the sync client by name, async, one `SyncArgs` (`{url, phrase}`) each, over a `Transport` and an optional `SyncStore` (`needs(store)?` for the two that touch the log); `dispatch_sync_json` answers the outcome as JSON — a failed cycle is an answer — and fails with plain text only for a malformed call. It generates `sync.ts` (`Sync`, `SYNC_METHODS`, `PHRASE_LENGTH`, `BAD_PHRASE`).
- **`sapling-wasm`** wraps db and protocol for a JavaScript host; that build runs inside the database Worker in the browser and in-process in node tests. Its free `llm(method, argsJson, endpointJson?, post, progress?, tools?)` export (`tools` a `ToolHost`: the `ToolContext` as JS methods, items as JSON) needs no database of its own and runs on the **window** thread (`src/lib/llm/core.ts`): the settings it needs live in `localStorage`, and the desktop shell has no Worker to send it to. So does `challenges(method, argsJson, countWords?)`, synchronously (`src/lib/challenges/core.ts`, lending `segmentWords`' count): the window instantiates the build once, before the first page renders (`src/lib/db/window-core.ts`, awaited by the root layout and shared with `callLlm`). So does `sync(method, argsJson, request, store?)` (`src/lib/sync/core.ts`): `request(requestJson)` is the window's `fetch`, `{method, url, headers, body?}` in and `{status, body}` out, and `store` a `SyncHost` — the `SyncStore` as JS methods over the window's `Backend`, events as JSON — beside four synchronous phrase exports (`normalizePhrase`, `isValidPhrase`, `mintPhrase(bytes)`, `formatPhrase`). **`sapling-store`** is the native host: it opens `Core` over a SQLite file in a directory through its own `rusqlite_sql` (the only crate that links rusqlite), with the device id, clock and time zone an OS lends (`desktop.md`), and hands it out on its own thread through `CoreHandle::run` — a closure gets the `Core` itself. It speaks no protocol: `sapling-desktop` calls `sapling-protocol` inside that closure, and a CLI would call `Core` methods directly. `CoreHandle` is also a `sapling-sync` `SyncStore` (`sync.rs`), so a native frontend syncs with `sapling_sync::run` over it and a transport of its own; `tests/sync.rs` runs two devices through `MemoryRelay` that way. Tauri-free so anything native opens the same database the same way.

There is no TypeScript implementation any more, and `src/lib/db/` keeps only the protocol, the transport and the host glue. A hosted instance would run the same crates over a different `Sql`.

- **It never opens a database.** Everything is written against the `Sql` trait in `sql.rs` — `exec` and `query`, synchronous, parameters as `Param`, rows as `Row` — and a host hands the crate a database: `sapling-store`'s `rusqlite_sql.rs` is the adapter native hosts and `sapling-db`'s own tests use; `sapling-wasm`'s `JsSql` borrows the browser's sqlite-wasm through two callbacks. Nothing in the crate may depend on which. `sapling-db` reaches rusqlite only through a dev-dependency on `sapling-store`, which depends on it (and on `sapling-domain`) and on nothing above it — a cycle cargo allows for `tests/` alone, so a test that needs a real SQLite is an integration test (`tests/golden.rs`, `tests/pending.rs`), never a unit test under `src/`, where it would link a second copy of the crate and the types would stop matching. A `Row` names its columns once for a whole result and every row of that result shares the list (`Row::with_names`; `Row::new` is the one-off), so a thousand-row page costs one header and not a `String` per cell. `rusqlite_sql` compiles each parameterised statement once and keeps it (`prepare_cached`, capacity 128 — comfortably over the ~70 shapes the core issues, so a widening `IN (?, …)` never evicts a hot one) and binds text by reference; SQLite re-prepares a cached statement itself when the schema under it moves, which is what makes `open_schema`'s drop-and-rebuild safe. The parameterless `exec` stays `execute_batch`, because that path is where a whole script arrives — the DDL, `BEGIN`, a `DELETE` — and a prepared statement is only ever the first one. A number binds as sqlite-wasm binds a JavaScript `number`: integral as `INTEGER`, otherwise `REAL` (`Param::number`), and an integral JSON number read back is an `INTEGER` for the same reason.

- **The host lends four runtime facts and one boundary** (`src/lib/db/host.ts`). `openCore(db, { deviceId, clock?, ids? })` gives the wasm `WasmCore` its `exec`/`query` over sqlite-wasm's `oo1` API, `localDay` from `day.ts` (the *only* place a time zone exists — `sapling-domain`'s `Utc` is what fixtures pin), the clock and the id generator, and the constructor applies the schema, replaying the log if the read tables are stale. `directOf(core)` turns `dispatch(method, argsJson)` back into the `Direct<Backend>` that `protocol.ts`'s `dispatch`/`promised` wrap. JSON strings cross in both directions and `undefined` is "no string": a `void` method and a read of a missing row both come back `undefined`, never `null`, because the TypeScript signatures say so. An argument the caller left out arrives as `null` and `sapling-protocol` reads it as absent.

- **Rust is the single source of the wire's TypeScript types, generated at build time and never committed.** Every struct and enum that crosses the protocol derives `ts_rs::TS` beside serde (`sapling-domain`'s `types.rs` and `events.rs`, `sapling-srs`'s `FsrsCardState`/`ItemSrs`, `sapling-db`'s `ReviewOutcome`/`ExportEnvelope`/`LanguageProfile`, `sapling-protocol`'s option and argument structs, `sapling-import`'s `ImportedSource`, `sapling-challenges`' stored union, `PoolRow` and the decisions' answers, and `sapling-sync`'s outcomes). `pnpm core:types` (`sapling-protocol`'s `typescript` test) rewrites the gitignored `src/lib/db/generated/`: ts-rs's own export, one file per type, integers as `number` (`Config::with_large_int`), plus hand-emitted files — `backend.ts` (`Backend`, `BACKEND_METHODS`, `EXPORT_VERSION` from the method table), `llm.ts`, `challenges.ts` and `sync.ts` (from theirs), `Payloads.ts` (an exhaustive `match` over `EventType`, so a new event type does not compile until it names its payload) and `index.ts`. `pnpm dev|build|check|test` run it right after `core:wasm`, like the wasm build: there is no staleness gate because nothing stale can exist. A field serde skips when `None` carries `#[ts(optional)]` and reads `field?: T`; an `Option` serde writes as `null` stays `T | null`; a `serde_json::Value` whose shape TypeScript owns names the hand-written type (`#[ts(type = "unknown")]`, or `as "Array<Challenge>"` in the method table). A payload struct is `<Name>Payload` in TypeScript, `RawEvent` is `LogRow`.

- **The method table is one list.** `backend!` in `sapling-protocol/src/lib.rs` gives each method its doc comment, its name, its typed arguments (those after a `;` are optional: `Option<T>` in the body, `name?: T` in TypeScript), its return type (`-> T`, `-> T | undefined` for a read of a row that may not exist, nothing for `void`) and the `Core` call that answers it. The same entry expands into the `dispatch` arm — which parses each argument as its declared type and pins the body's result to the declared return type, so the TypeScript signature cannot claim what the Rust does not return — and, under `cargo test`, into the TypeScript method. **Adding a method** is one entry in the table (and the `Core` method it calls); `repositories.ts` forwards it under a name if the app wants one.

- **JSON goes out through serde_json, and how a number prints is not a contract.** Cards, payloads, `recentGrades`, challenge content and the export file are `serde_json::to_string` (`to_string_pretty` for the export), so an `f64` field prints as `1.0` where the old JavaScript core wrote `1`; every reader — `JSON.parse`, serde, SQLite's `json_extract` — reads the same value either way, and rows written the old way still parse. `preserve_order` is on so objects keep the key order they arrived with. **The one place a printed number is an identity is `review_key`** (`itemId|at|device`, the cross-device key of a review): it formats `at` with `f64`'s `Display`, which prints a whole millisecond without a fraction, exactly as the rows already on every device have it, and `schema.rs` pins that. The pull cursor in `meta` is formatted the same way. Anything else that ever turns a number into an identity or a SQL text parameter must do the same.

- **Payload structs are the schemas now, optional fields included** (`sapling-domain`'s `events.rs`, `types.rs`); `src/lib/db/events.ts` re-exports the TypeScript generated from them. Serde strips unknown fields exactly as zod did, so a struct that forgets an optional field loses it on every device the event arrives at. Every optional field is `#[serde(default, deserialize_with = "absent_or", skip_serializing_if = "Option::is_none")]`: absent is `None`, `null` is a parse error (zod's `.optional()` was not `.nullable()`), and `None` is omitted on the way out (`JSON.stringify` drops `undefined`). The `parse_event(raw) == raw` test in `events.rs` lists one payload per type with every optional field present; a new field goes there, or that test is what fails. A new event type also names its payload in `typescript.rs`'s `payloads`. `parse_event` is the gate for every row off sync or out of a backup file, and a local `commit` never goes through it. **The gate costs a row its merge rule, never its place in the log**: `parse_envelope` reads the envelope alone and keeps the payload as it arrived, `typed_event` is the half that needs a schema, and `pending_events`/`export_data` read rows through `raw_from_row` without asking either — push and export carry log rows verbatim, only materialization interprets a payload, and a row it cannot read is skipped, never dropped. So `pending_events(limit)` is the first `limit` unpushed rows with no gaps, and a row a newer build wrote survives a round trip through an older device. The pool's allow-list is `sapling-challenges`' `STORED_TYPES`, which `materialize.rs` reads: a challenge of a type this build's union does not have is written to the log and skipped on the way into the pool.

- **The SRS is `crates/sapling-srs`: the `fsrs` crate's model inside this app's card state machine.** It is a crate of its own so it stays a function of a card, a grade and a time — it knows nothing of events, SQL or the schema, `sapling-domain` and `sapling-db` depend on it and never the other way, and it carries the `fsrs` dependency and the `getrandom` `wasm_js` workaround the wasm build needs. The `fsrs` crate owns the model — FSRS-6, `DEFAULT_PARAMETERS` (the 21 FSRS-6 weights, pinned by a test), `desired_retention` 0.9, and `next_states(memory, retention, days_elapsed)` for the four grades' memory states and intervals. `sapling-srs` owns everything around it, because the crate has no opinion on any of it: the New/Learning/Review/Relearning machine, learning steps `1m`/`10m` and relearning `10m`, `reps`, `lapses`, `elapsed_days`, `scheduled_days`, `due`, the [1, 36500] clamp, the hard < good < easy ordering rule and the `FsrsCardState` JSON, whose `stability` and `difficulty` are the model's own `f32`s (a card stored with longer `f64` numbers still reads). The model's floats differ slightly between the native and wasm builds, so every test compares them with a tolerance, never for equality. `next_states` reads no clock and no RNG (the crate's randomness is all in its optimizer), so the "every function takes `now`" rule holds; a negative elapsed time reads as zero days. **`sapling-srs` also owns the reading side, because the frontend has no FSRS at all.** `current_retrievability` is the crate's forgetting curve at `now` (whole floored elapsed days, never negative, and 0 for a card the model has never seen), `word_strength` is log-stability × retrievability against `MATURE_STABILITY_DAYS`, and `item_srs` bundles the two with the card's `due` into `ItemSrs`, which `core.rs`'s `item_from` attaches to every item `getAllItems` and `getItem` return (`get_all_items` reads the clock once for the whole batch). A card too malformed to parse simply carries no `srs`: a read must not fail over a display number. `src/lib/srs/` keeps only grades, the opaque `FsrsCardState` type, `isDue` as a `due <= now` comparison and `selectSessionItems`; a test that wants a card must read it back from the store. Changing what a review folds to means bumping `DERIVED_SCHEMA_VERSION`, or devices carry a mix of old and new cards item by item.

- **The wasm build is generated, never committed.** `pnpm core:wasm` compiles `sapling-wasm` for `wasm32-unknown-unknown` and runs `wasm-bindgen --target web` into `src/lib/db/wasm/` (gitignored); `pnpm dev|build|check|test` each run it first, so a clean checkout works and a stale artefact cannot outlive an edit to the crate. The Worker loads the `.wasm` by URL (`?url`), node tests `initSync` the same bytes from disk (`backend.testing.ts`). The `wasm-bindgen` crate version in `crates/sapling-wasm/Cargo.toml` is pinned `=` to the `wasm-bindgen-cli` the flake ships — a mismatch is a hard error at bindgen time — and the target links with `lld`, which the flake provides because nixpkgs' rustc does not bundle `rust-lld`. Only the release profile is used for wasm; it is tuned for size (`opt-level = "s"`, LTO, `panic = "abort"`).

- **The fixtures are the acceptance test, twice** (`sapling-db`'s `tests/golden.rs` and `src/lib/db/golden.test.ts`). Both discover `src/lib/db/fixtures/*`, probe every read exactly as the fixtures README describes, and run the same idempotence, export/import, log round-trip and reverse-arrival checks — the Rust one natively over rusqlite, the TypeScript one over the wasm build through the browser-shaped path. They compare **values, not text**: `golden.rs` canonicalises every whole-valued number to an integer before comparing, because `expected.json` is written by JavaScript and serde_json keeps `1` and `1.0` apart. A value that does not match is a finding about the core, never a reason to edit a fixture. **One exception:** the four numbers that come out of the `f32` model — a card's `stability` and `difficulty`, and the `srs.retrievability` and `srs.strength` derived from them — are compared with a `1e-4` relative tolerance (`MODEL_FLOATS` in both files), because they differ slightly between the native and wasm builds. Everything else, `due`, `srs.due` and `scheduled_days` included, still matches exactly. `pnpm core:test` runs the Rust suite; `pnpm core:check` is clippy with warnings denied plus rustfmt. Nix flakes only see staged files — `git add` a new source file before `nix develop` or the toolchain will not see it either.
