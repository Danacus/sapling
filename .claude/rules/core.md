# The Rust core

`crates/sapling-core` **is** the persistence core: the event log and its merge rules, the SRS they call, and every `Backend` method. `crates/sapling-wasm` wraps it for a JavaScript host, and that build runs inside the database Worker in the browser and in-process in node tests — there is no TypeScript implementation any more, and `src/lib/db/` keeps only the protocol, the transport and the host glue. A Tauri shell or a hosted instance would run the same crate over a different `Sql`.

- **It never opens a database.** Everything is written against the `Sql` trait in `sql.rs` — `exec` and `query`, synchronous, parameters as `Param`, rows as `Row` — and a host hands the crate a database: `rusqlite_sql.rs` (behind the `sqlite` feature) is the adapter native hosts and the crate's own tests use; `sapling-wasm`'s `JsSql` borrows the browser's sqlite-wasm through two callbacks. Nothing in the crate may depend on which. A `Row` names its columns once for a whole result and every row of that result shares the list (`Row::with_names`; `Row::new` is the one-off), so a thousand-row page costs one header and not a `String` per cell. `rusqlite_sql` compiles each parameterised statement once and keeps it (`prepare_cached`, capacity 128 — comfortably over the ~70 shapes the core issues, so a widening `IN (?, …)` never evicts a hot one) and binds text by reference; SQLite re-prepares a cached statement itself when the schema under it moves, which is what makes `open_schema`'s drop-and-rebuild safe. The parameterless `exec` stays `execute_batch`, because that path is where a whole script arrives — the DDL, `BEGIN`, a `DELETE` — and a prepared statement is only ever the first one. A number binds as sqlite-wasm binds a JavaScript `number`: integral as `INTEGER`, otherwise `REAL` (`Param::number`), and an integral JSON number read back is an `INTEGER` for the same reason.

- **The host lends four runtime facts and one boundary** (`src/lib/db/host.ts`). `openCore(db, { deviceId, clock?, ids? })` gives the wasm `WasmCore` its `exec`/`query` over sqlite-wasm's `oo1` API, `localDay` from `day.ts` (the *only* place a time zone exists — the crate's `Utc` is what fixtures pin), the clock and the id generator, and the constructor applies the schema, replaying the log if the read tables are stale. `directOf(core)` turns `dispatch(method, argsJson)` back into the `Direct<Backend>` that `protocol.ts`'s `dispatch`/`promised` wrap. JSON strings cross in both directions and `undefined` is "no string": a `void` method and a read of a missing row both come back `undefined`, never `null`, because the TypeScript signatures say so. An argument the caller left out arrives as `null` and `dispatch.rs` reads it as absent.

- **`dispatch.rs` is the other end of `protocol.ts`, and the two are gated against each other.** `METHODS` must equal `BACKEND_METHODS`; `cargo test` reads `src/lib/db/protocol.ts` and compares, and a second test calls every listed name so an arm cannot be missing. Adding a method is therefore three edits — the interface, the list, the arm — and forgetting any one fails `pnpm check` or `pnpm core:test`.

- **What JavaScript would print is the contract.** Cards, payloads, `recentGrades`, challenge content and the export file are stored or shipped as JSON text made the way `JSON.stringify` makes it, and the fixtures diff them. `js.rs` is therefore the only way this crate writes a number or a document: `number_to_string` is `Number::toString` (`1` for `1.0`, `1e+21` past twenty-one digits), `stringify`/`stringify_pretty` are `JSON.stringify` with and without an indent, `round` is `Math.round` (halves towards `+∞`, and not `floor(x + 0.5)`), `round_to` is ts-fsrs's `roundTo`. serde_json's own formatting is never used for output; `preserve_order` is on so objects keep the key order JavaScript gave them.

- **Payload structs are the schemas now, optional fields included** (`events.rs`, `types.rs`); `src/lib/db/events.ts` is the type-only mirror the TypeScript compiles against. Serde strips unknown fields exactly as zod did, so a struct that forgets an optional field loses it on every device the event arrives at. Every optional field is `#[serde(default, deserialize_with = "absent_or", skip_serializing_if = "Option::is_none")]`: absent is `None`, `null` is a parse error (zod's `.optional()` was not `.nullable()`), and `None` is omitted on the way out (`JSON.stringify` drops `undefined`). The `parse_event(raw) == raw` test in `events.rs` lists one payload per type with every optional field present; a new field goes there, in the TypeScript type, or that test is what fails. `parse_event` is the gate for every row off sync or out of a backup file, and a local `commit` never goes through it. `CHALLENGE_TYPES` in `materialize.rs` is the pool's allow-list: a new challenge type goes there or its challenges are written to the log and skipped on the way into the pool.

- **The SRS is the `fsrs` crate inside ts-fsrs's scheduler shape** (`srs.rs`). The crate owns the model — FSRS-6, `DEFAULT_PARAMETERS` (asserted to be the 21 weights `generatorParameters()` gives ts-fsrs), `desired_retention` 0.9, and `next_states(memory, retention, days_elapsed)` for the four grades' memory states and intervals. `srs.rs` owns everything around it, because the crate has no opinion on any of it: the New/Learning/Review/Relearning machine, learning steps `1m`/`10m` and relearning `10m`, `reps`, `lapses`, `elapsed_days`, `scheduled_days`, `due`, the [1, 36500] clamp, the hard < good < easy ordering rule and the `FsrsCardState` JSON. Widen the crate's `f32` and `round_to(x, 8)` on the way into a card — that boundary is the only rounding rule left, and `roundTo` operation-order parity with ts-fsrs is not a goal any more. `next_states` reads no clock and no RNG (the crate's randomness is all in its optimizer), so the "every function takes `now`" rule holds; a negative elapsed time reads as zero days. **`srs.rs` also owns the reading side, because the frontend has no FSRS at all** — `ts-fsrs` is gone from `package.json`. `current_retrievability` is the crate's forgetting curve at `now` (ts-fsrs's `get_retrievability`: whole floored elapsed days, never negative, and 0 for a card the model has never seen), `word_strength` is log-stability × retrievability against `MATURE_STABILITY_DAYS`, and `item_srs` bundles the two with the card's `due` into `ItemSrs`, which `core.rs`'s `item_from` attaches to every item `getAllItems` and `getItem` return (`get_all_items` reads the clock once for the whole batch). A card too malformed to parse simply carries no `srs`: a read must not fail over a display number. `src/lib/srs/` keeps only grades, the opaque `FsrsCardState` type, `isDue` as a `due <= now` comparison and `selectSessionItems`; a test that wants a card must read it back from the store. Changing what a review folds to means bumping `DERIVED_SCHEMA_VERSION`, or devices carry a mix of old and new cards item by item.

- **The wasm build is generated, never committed.** `pnpm core:wasm` compiles `sapling-wasm` for `wasm32-unknown-unknown` and runs `wasm-bindgen --target web` into `src/lib/db/wasm/` (gitignored); `pnpm dev|build|check|test` each run it first, so a clean checkout works and a stale artefact cannot outlive an edit to the crate. The Worker loads the `.wasm` by URL (`?url`), node tests `initSync` the same bytes from disk (`backend.testing.ts`). The `wasm-bindgen` crate version in `crates/sapling-wasm/Cargo.toml` is pinned `=` to the `wasm-bindgen-cli` the flake ships — a mismatch is a hard error at bindgen time — and the target links with `lld`, which the flake provides because nixpkgs' rustc does not bundle `rust-lld`. Only the release profile is used for wasm; it is tuned for size (`opt-level = "s"`, LTO, `panic = "abort"`).

- **The fixtures are the acceptance test, twice** (`tests/golden.rs` and `src/lib/db/golden.test.ts`). Both discover `src/lib/db/fixtures/*`, probe every read exactly as the fixtures README describes, and run the same idempotence, export/import, log round-trip and reverse-arrival checks — the Rust one natively over rusqlite, the TypeScript one over the wasm build through the browser-shaped path. A value that does not match is a finding about the core, never a reason to edit a fixture. **One exception, and only in `tests/golden.rs`:** the four numbers that come out of the `f32` model — a card's `stability` and `difficulty`, and the `srs.retrievability` and `srs.strength` derived from them — are compared with a `1e-5` relative tolerance (`MODEL_FLOATS`), because `expected.json` is blessed from the wasm build and the FSRS model computes in `f32`, where `exp`/`powf` differ by an ulp or two between the host's libm and wasm's — a seventh-significant-digit difference that no merge rule or scheduler decision can be wrong by. Everything else, `due`, `srs.due` and `scheduled_days` included, still matches character for character. The same divergence means a browser and a desktop host holding the same log can hold cards that differ that far; nothing downstream reads a card that closely. `pnpm core:test` runs the Rust suite; `pnpm core:check` is clippy with warnings denied plus rustfmt. Nix flakes only see staged files — `git add` a new source file before `nix develop` or the toolchain will not see it either.
