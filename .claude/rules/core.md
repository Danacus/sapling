# The Rust core

The persistence core is a stack of crates, one job each, and the dependencies only point down it:

- **`sapling-srs`** — the scheduler: a function of a card, a grade and a time. It knows no events and no SQL.
- **`sapling-domain`** — the event log as a contract: the event and payload schemas (`events.rs`), the domain types they and the reads carry (`types.rs`), content objects (`objects.rs`: `object_hash` — `sha256:<64 lowercase hex>` over the exact bytes, `sha2` its one dependency beyond serde — `is_object_hash`, `ContentObject { hash, bytes }`, `TextContent { segments }` whose compact serde_json is an object's bytes and is pinned by a test vector, `MAX_OBJECT_BYTES` (1 MiB, the Worker's cap), and **`object_refs(&RawEvent) -> ObjectRefs { owner, objects, retire }`**, the one function that derives an event's envelope fields for the relay, `docs/content-objects.md` §4, owner `text:<profileId>:<textId>`, `profileEvent` unwrapped, a row this build cannot type declaring nothing), the `LocalDay` calendar seam (`day.rs`: a timestamp's local day and the start of its local hour) and `PROFILE_ID`. serde only; it knows nothing of SQL, so anything that reads, writes or ships events can depend on it alone.
- **`sapling-challenges`** — the compile-time challenge plugin registry and every decision about a challenge once it exists. `types/mod.rs` generates stored, screen and answer unions and dispatch; each `types/<type>/` plugin owns its shapes, grading, serving, feedback, kinds and lesson data. Shared matching, help levels, help-id parsing, the difficulty model (`ratings.rs`: ratings with margins, the roll serving and writing pick by), replay, stream and top-up machinery stays generic; `research/` is the calibration command's — scoring the app's `Ratings` on an export (`calibrate.rs`, the same `learn` fold `learned.rs` keeps), the simulated learner's truth and the synthetic rows tests build pools from (`sim.rs`), and the closed loop that practises it with `stream::head` and `topup::plan_top_up` (`closed_loop.rs`) — which the app never calls and the wasm build leaves out (`#[cfg(not(target_arch = "wasm32"))]`). `generation.rs` supplies the shared resolver boundary used by `sapling-llm`. It depends on `sapling-domain` and `sapling-srs` and on nothing above; no SQL, no `Core`, no model call. Global numbers — the aims' targets and the ratings' starting values — are `data/model.json`; plugin data is included from each type folder. Its random source (`rng.rs`, the roll's normal draws included) and length measurement remain deterministic across hosts.
- **`sapling-db`** — the database: the `Sql` trait (`sql.rs`), the DDL and read-table constants (`schema.rs`, `READABLE_TEXTS` and `MISSING_OBJECTS` among them), the merge rules (`materialize.rs`) and `Core`, every `Backend` method (`core.rs`). It never opens a database and never mentions rusqlite. The local `objects` table is **not** in `DERIVED_TABLES`: a rebuild (a schema bump, an import, a profile switch) keeps it and only `resetData` clears it; `put_objects` keeps an object only if it verifies and is JSON.
- **`sapling-import`** — the reading import, whole: subtitle detection and parsing (SRT, VTT, json3, a copied transcript panel) into **one timed segment per cue** — never joined, never re-cut into sentences — and prose into **one untimed segment per paragraph**. Its output is `sapling-domain`'s `Segment` itself (its one workspace dependency), so what `importSource` answers is what `addText` stores. A plain library beside the stack rather than in it — no SQL, no `Core`, no I/O, a function of the text alone — exposed as `importSource`, the one method in the table that ignores `core`. The CJK test that decides whether a cue's lines join with a space is Unicode block ranges, not script data, to keep a table out of the wasm build.
- **`sapling-llm`** — the stateless model calls and orchestration: client, strict JSON handling, lesson batching, escalation, reading, word batches and assistant flows. Challenge wire shapes, schemas, resolvers and lesson specs belong to registered plugins in `sapling-challenges`; this crate asks the registry for them. Shared prompts and non-challenge fixtures remain here. Mock replies traverse the same parser and resolver path as live replies. HTTP and word-list access are injected; no SQL and no `Core`.
- **`sapling-sync`** — the sync client, host-agnostic: the pairing phrase (`phrase.rs`: normalise, validate, mint from host-drawn bytes, format; `BAD_PHRASE`), and in `lib.rs` one cycle against the relay (`run`: first `follow_room(room_key(url, phrase))` — the stamps and the cursor are positions in one room's log, so a cycle against a different room, or a device with none recorded, clears both and resends and re-pulls everything, which the union by id at both ends makes harmless; then push pending events in pages of 500, stamp what was acknowledged, pull pages of 1000 from the cursor, apply each before advancing the cursor, then fetch content objects), the liveness probe (`probe`) and pairing (`pair`: one cycle, then whether a profile came down the log — it never writes one). **Content objects ride beside the log** (`docs/content-objects.md` §6): before each push page the cycle derives every row's `object_refs`, asks `POST /objects/missing` for the named hashes (none named, nothing asked — so a page without objects pushes to an old relay as before), `PUT`s each missing one the store holds (one it does not hold does not hold the page back), and attaches `owner`/`objects`/`retire` to the wire envelope only — never to the local row; a `404` on `/objects/missing` fails the cycle with `NO_OBJECT_STORE` and the page is not pushed. After pulling it `GET`s every hash `missing_objects` names, verifies each against its name and stores the good ones; a `404` is "not uploaded yet", re-asked next cycle (the set is re-derived from the texts, never queued), and a mismatch or no answer fails the cycle after the events landed. **Every failure is an outcome value** (`SyncOutcome`, `SyncProbeResult`, `PairOutcome`, each with its learner-facing text), never an `Err`. The HTTP request is a `Transport` (`Method` GET/POST/PUT, URL, headers, optional body sent as those exact bytes; `Err` is no response at all) and the database a `SyncStore` (`pending_events`, `mark_pushed`, `apply_remote`, the pull cursor, `has_profile`, `follow_room`, and `objects`, `put_objects`, `missing_objects`), both injected; the relay's URL and the phrase are arguments and the crate reads no configuration. It depends on `sapling-domain` (`RawEvent`, `parse_envelope`, `objects`) alone — no SQL, no `Core`. `relay.rs`'s `MemoryRelay` speaks `worker/`'s wire protocol in memory, object endpoints and the edge/retired sets included (`without_objects()` is a relay that predates them), for tests of the cycle here and of a store elsewhere. `fixtures/phrases.json` is the language-neutral phrase cases `phrase.rs`' tests and `worker/phrase.test.ts` both run (`deploy.md`). Single flight and when to run a cycle are the host's (`$lib/remotes`, below).
- **`sapling-taal`** — the Taal client, built like `sapling-sync`: the connect code (`parse_code`: `^[A-Za-z0-9]{20}\.[A-Za-z0-9]{32}$` after trim, split into link id and secret), the mapping of the core's `StudySession` onto Taal's modes (`input` → `input` minutes, `output` → `output` minutes, `practice` → `cards = answers × CARDS_PER_ANSWER`, a tunable `pub const`; never `study`/`review`; ids prefixed `{profile id}-`), and `commit_request` — **Taal's `sendToTaal()` request field for field**, because Taal's security rules accept exactly that shape: one Firestore `:commit` writing the secret to `appInbox/{linkId}` and the sessions to `appSources/{linkId}` as `sessions.<id>` map fields (`updateMask` paths backtick-quoted), both with the `REQUEST_TIME` stamp, whole numbers as string `integerValue`s and the rest `doubleValue`s. `push` reads `studySessions(since)` with `since = max(now − 120 days, watermark − 48 h)`, sends oldest first in commits of 100, and answers the new watermark (`now`) only when every batch landed; 403 is `refused` (any rule rejection, so never a latch), anything else `failed`. **Every failure is a `TaalOutcome`.** The HTTP POST is a `Transport` and the read a `TaalStore`, both injected; the code, profile, clock and watermark are arguments. It depends on `sapling-domain` alone. `sapling-protocol`'s `taal.rs` (`taal!`: `pushTaal`) generates `taal.ts`; `sapling-wasm`'s `taal(method, argsJson, request, store)` takes the same `request` as `sync` and a `TaalHost` (`studySessions` as JSON), beside `isTaalCode`. `src/lib/taal/` keeps the code and the watermark (per code and per profile) in `localStorage`; Settings pushes on saving a code.
- **`src/lib/remotes/`** — the host's *when*, for both clients: sync and Taal are two members of one registry (`REMOTES`, keyed by `RemoteId`, so an unlisted one fails `pnpm check`), each a `Remote` (`pulls`, `configured()`, `run()` → `RemoteOutcome`) whose adapter maps its crate's outcome (`sapling-sync`'s as is; Taal's `sent` → `pushed`, `refused`/`failed`/`invalid` → `ok: false`). Every trigger — boot after the render gate, the tab hidden **or** shown, a practice summary, leaving a text — calls `syncRemotes()` and names no service: configured pullers run first, then the send-only ones whether or not anything came down (so another device's study time reaches Taal on the same trigger); unconfigured ones cost nothing, one failing costs only itself, and it never throws. `flight.ts`'s `singleFlight` — run now, or queue exactly one run behind the current one that later calls join — wraps `syncRemotes`, `runSync` and `pushTaal` alike; pairing still waits behind a running cycle on sync's own exclusive chain. Settings ("Sync now", connecting Taal) and the layout's pull for a device with no profile yet call one remote directly. `$lib/sync` and `$lib/taal` never import each other.
- **`sapling-captions`** — a YouTube video's caption tracks (`innertube.rs`: the list, and one track as raw `json3` for `sapling-import`), over an injected `Transport` that carries no headers (a POST body is `text/plain`); `native` adds a ureq transport for native hosts (`desktop.md`, `media.md`). No SQL, no `Core`, no caption parsing.
- **`sapling-protocol`** — the `Backend` protocol by name: the `backend!` method table, the `dispatch` and `dispatch_json` it expands into (a method name and a JSON argument array in, JSON out, over `Core`), and the generator of the TypeScript wire types. Beside it, `llm.rs`'s `llm!` table: the model calls by name, async, one argument object each, over an `Llm` and an optional `ToolContext` rather than `Core` (an entry that runs tools asks for it with `needs(tools)?`); `dispatch_llm_json` answers `{result, usage?}` and fails with the `LlmError` as JSON, or plain text for a malformed call or a store failing under a tool. It generates `llm.ts` (`Llm`, `LLM_METHODS`, the prompt caps, `REQUEST_ITEMS`). And `challenges.rs`'s `challenges!` table: the challenge decisions by name, **synchronous**, one argument object each, over nothing but the host's word counter — grading, what a served challenge shows, the planners (a seed, where a method takes one, replays its draws); `dispatch_challenges_json` answers the JSON and fails with plain text. A pool argument is read row by row, and a row that does not parse keeps its place as nothing, so a plan's positions still index the host's array. It generates `challenges.ts` (`Challenges`, `CHALLENGE_METHODS`, `MATCH_PAIRS_EVERY`). And `sync.rs`'s `sync!` table: the sync client by name, async, one `SyncArgs` (`{url, phrase}`) each, over a `Transport` and an optional `SyncStore` (`needs(store)?` for the two that touch the log); `dispatch_sync_json` answers the outcome as JSON — a failed cycle is an answer — and fails with plain text only for a malformed call. It generates `sync.ts` (`Sync`, `SYNC_METHODS`, `PHRASE_LENGTH`, `BAD_PHRASE`). And `captions.rs`'s `captions!` table: a YouTube video's captions by name, async, one argument object each (`listCaptions({videoId})`, `fetchCaptions({videoId, track})`), over `sapling-captions`' `innertube::Transport`; `dispatch_captions_json` answers the JSON and fails with plain text written for the learner. It generates `captions.ts` (`Captions`, `CAPTION_METHODS`).
- **`sapling-wasm`** wraps db and protocol for a JavaScript host; that build runs inside the database Worker in the browser and in-process in node tests. Its free `llm(method, argsJson, endpointJson?, post, progress?, tools?)` export (`tools` a `ToolHost`: the `ToolContext` as JS methods, items as JSON) needs no database of its own and runs on the **window** thread (`src/lib/llm/core.ts`): the settings it needs live in `localStorage`, and the desktop shell has no Worker to send it to. So does `challenges(method, argsJson)`, synchronously and lent nothing (`src/lib/challenges/core.ts` — no word counter: a length the difficulty model reads is `model.rs`' own `words_in`): the window instantiates the build once, before the first page renders (`src/lib/db/window-core.ts`, awaited by the root layout and shared with `callLlm`). So does `sync(method, argsJson, request, store?)` (`src/lib/sync/core.ts`): `request(requestJson)` is the window's `fetch`, `{method, url, headers, body?}` in and `{status, body}` out, and `store` a `SyncHost` — the `SyncStore` as JS methods over the window's `Backend` (`getObjects`, `putObjects`, `missingObjects` among them), events and objects as JSON — beside four synchronous phrase exports (`normalizePhrase`, `isValidPhrase`, `mintPhrase(bytes)`, `formatPhrase`). So does `captions(method, argsJson, request)` (`src/lib/media/captions.ts`): the same `request` shape without headers — a POST body is `text/plain` — lent the sandboxed-frame relay to YouTube (`media.md`). **`sapling-store`** is the native host: it opens `Core` over a SQLite file in a directory through its own `rusqlite_sql` (the only crate that links rusqlite), with the device id, clock and time zone an OS lends (`desktop.md`), and hands it out on its own thread through `CoreHandle::run` — a closure gets the `Core` itself. It speaks no protocol: `sapling-desktop` calls `sapling-protocol` inside that closure, and a CLI would call `Core` methods directly. `CoreHandle` is also a `sapling-sync` `SyncStore` (`sync.rs`), so a native frontend syncs with `sapling_sync::run` over it and a transport of its own; `tests/sync.rs` runs two devices through `MemoryRelay` that way. Tauri-free so anything native opens the same database the same way.

There is no TypeScript implementation any more, and `src/lib/db/` keeps only the protocol, the transport and the host glue. A hosted instance would run the same crates over a different `Sql`.

- **It never opens a database.** Everything is written against the `Sql` trait in `sql.rs` — `exec` and `query`, synchronous, parameters as `Param`, rows as `Row` — and a host hands the crate a database: `sapling-store`'s `rusqlite_sql.rs` is the adapter native hosts and `sapling-db`'s own tests use; `sapling-wasm`'s `JsSql` borrows the browser's sqlite-wasm through two callbacks. Nothing in the crate may depend on which. `sapling-db` reaches rusqlite only through a dev-dependency on `sapling-store`, which depends on it (and on `sapling-domain`) and on nothing above it — a cycle cargo allows for `tests/` alone, so a test that needs a real SQLite is an integration test (`tests/golden.rs`, `tests/pending.rs`), never a unit test under `src/`, where it would link a second copy of the crate and the types would stop matching. A `Row` names its columns once for a whole result and every row of that result shares the list (`Row::with_names`; `Row::new` is the one-off), so a thousand-row page costs one header and not a `String` per cell. `rusqlite_sql` compiles each parameterised statement once and keeps it (`prepare_cached`, capacity 128 — comfortably over the ~70 shapes the core issues, so a widening `IN (?, …)` never evicts a hot one) and binds text by reference; SQLite re-prepares a cached statement itself when the schema under it moves, which is what makes `open_schema`'s drop-and-rebuild safe. The parameterless `exec` stays `execute_batch`, because that path is where a whole script arrives — the DDL, `BEGIN`, a `DELETE` — and a prepared statement is only ever the first one. A number binds as sqlite-wasm binds a JavaScript `number`: integral as `INTEGER`, otherwise `REAL` (`Param::number`), and an integral JSON number read back is an `INTEGER` for the same reason.

- **The host lends four runtime facts and one boundary** (`src/lib/db/host.ts`). `openCore(db, { deviceId, clock?, ids? })` gives the wasm `WasmCore` its `exec`/`query` over sqlite-wasm's `oo1` API, `localDay` and `localHour` from `day.ts` (the *only* place a time zone exists — `sapling-domain`'s `Utc` is what fixtures pin), the clock and the id generator, and the constructor applies the schema, replaying the log if the read tables are stale. `directOf(core)` turns `dispatch(method, argsJson)` back into the `Direct<Backend>` that `protocol.ts`'s `dispatch`/`promised` wrap. JSON strings cross in both directions and `undefined` is "no string": a `void` method and a read of a missing row both come back `undefined`, never `null`, because the TypeScript signatures say so. An argument the caller left out arrives as `null` and `sapling-protocol` reads it as absent.

- **Rust is the single source of the wire's TypeScript types, generated at build time and never committed.** Every struct and enum that crosses the protocol derives `ts_rs::TS` beside serde (`sapling-domain`'s `types.rs` and `events.rs`, `sapling-srs`'s `FsrsCardState`/`ItemSrs`, `sapling-db`'s `ReviewOutcome`/`AnswerRecord`/`AnswerFiled`/`ExportEnvelope`/`LanguageProfile`/`Clip`, `sapling-protocol`'s option and argument structs, `sapling-import`'s `ImportedSource`, `sapling-challenges`' stored union, `PoolRow` and the decisions' answers, and `sapling-sync`'s outcomes). `pnpm core:types` (`sapling-protocol`'s `typescript` test) rewrites the gitignored `src/lib/db/generated/`: ts-rs's own export, one file per type, integers as `number` (`Config::with_large_int`), plus hand-emitted files — `backend.ts` (`Backend`, `BACKEND_METHODS`, `EXPORT_VERSION` from the method table), `llm.ts`, `challenges.ts` and `sync.ts` (from theirs), `Payloads.ts` (an exhaustive `match` over `EventType`, so a new event type does not compile until it names its payload) and `index.ts`. `pnpm dev|build|check|test` run it right after `core:wasm`, like the wasm build: there is no staleness gate because nothing stale can exist. A field serde skips when `None` carries `#[ts(optional)]` and reads `field?: T`; an `Option` serde writes as `null` stays `T | null`; a `serde_json::Value` whose shape TypeScript owns names the hand-written type (`#[ts(type = "unknown")]`, or `as "Array<Challenge>"` in the method table). A payload struct is `<Name>Payload` in TypeScript, `RawEvent` is `LogRow`.

- **The method table is one list.** `backend!` in `sapling-protocol/src/lib.rs` gives each method its doc comment, its name, its typed arguments (those after a `;` are optional: `Option<T>` in the body, `name?: T` in TypeScript), its return type (`-> T`, `-> T | undefined` for a read of a row that may not exist, nothing for `void`) and the `Core` call that answers it. The same entry expands into the `dispatch` arm — which parses each argument as its declared type and pins the body's result to the declared return type, so the TypeScript signature cannot claim what the Rust does not return — and, under `cargo test`, into the TypeScript method. **Adding a method** is one entry in the table (and the `Core` method it calls); `repositories.ts` forwards it under a name if the app wants one.

- **JSON goes out through serde_json, and how a number prints is not a contract.** Cards, payloads, `recentGrades`, challenge content and the export file are `serde_json::to_string` (`to_string_pretty` for the export), so an `f64` field prints as `1.0` where the old JavaScript core wrote `1`; every reader — `JSON.parse`, serde, SQLite's `json_extract` — reads the same value either way, and rows written the old way still parse. `preserve_order` is on so objects keep the key order they arrived with. **The one place a printed number is an identity is `review_key`** (`itemId|at|device`, the cross-device key of a review): it formats `at` with `f64`'s `Display`, which prints a whole millisecond without a fraction, exactly as the rows already on every device have it, and `schema.rs` pins that. The pull cursor in `meta` is formatted the same way. Anything else that ever turns a number into an identity or a SQL text parameter must do the same.

- **Payload structs are the schemas now, optional fields included** (`sapling-domain`'s `events.rs`, `types.rs`); `src/lib/db/events.ts` re-exports the TypeScript generated from them. Serde strips unknown fields exactly as zod did, so a struct that forgets an optional field loses it on every device the event arrives at. Every optional field is `#[serde(default, deserialize_with = "absent_or", skip_serializing_if = "Option::is_none")]`: absent is `None`, `null` is a parse error (zod's `.optional()` was not `.nullable()`), and `None` is omitted on the way out (`JSON.stringify` drops `undefined`). The `parse_event(raw) == raw` test in `events.rs` lists one payload per type with every optional field present; a new field goes there, or that test is what fails. A new event type also names its payload in `typescript.rs`'s `payloads`. A payload whose fields are each optional but constrained together — `textAdded`'s `segments` *or* `content`, never both or neither, and `textRevised`'s well-formed hash — is checked in `parse_payload` after serde, so a payload that breaks the constraint costs its rule like one that will not parse. `parse_event` is the gate for every row off sync or out of a backup file, and a local `commit` never goes through it. **The gate costs a row its merge rule, never its place in the log**: `parse_envelope` reads the envelope alone and keeps the payload as it arrived, `typed_event` is the half that needs a schema, and `pending_events`/`export_data` read rows through `raw_from_row` without asking either — push and export carry log rows verbatim, only materialization interprets a payload, and a row it cannot read is skipped, never dropped. So `pending_events(limit)` is the first `limit` unpushed rows with no gaps, and a row a newer build wrote survives a round trip through an older device. The pool's allow-list is `sapling-challenges`' `STORED_TYPES`, which `materialize.rs` reads: a challenge of a type this build's union does not have is written to the log and skipped on the way into the pool.

- **The SRS is `crates/sapling-srs`: the `fsrs` crate's model inside this app's card state machine.** It is a crate of its own so it stays a function of a card, a grade and a time — it knows nothing of events, SQL or the schema, `sapling-domain` and `sapling-db` depend on it and never the other way, and it carries the `fsrs` dependency and the `getrandom` `wasm_js` workaround the wasm build needs. The `fsrs` crate owns the model — FSRS-6, `DEFAULT_PARAMETERS` (the 21 FSRS-6 weights, pinned by a test), `desired_retention` 0.9, and `next_states(memory, retention, days_elapsed)` for the four grades' memory states and intervals. `sapling-srs` owns everything around it, because the crate has no opinion on any of it: the New/Learning/Review/Relearning machine, learning steps `1m`/`10m` and relearning `10m`, `reps`, `lapses`, `elapsed_days`, `scheduled_days`, `due`, the [1, 36500] clamp, the hard < good < easy ordering rule and the `FsrsCardState` JSON, whose `stability` and `difficulty` are the model's own `f32`s (a card stored with longer `f64` numbers still reads). The model's floats differ slightly between the native and wasm builds, so every test compares them with a tolerance, never for equality. `next_states` reads no clock and no RNG (the crate's randomness is all in its optimizer), so the "every function takes `now`" rule holds; a negative elapsed time reads as zero days. **`sapling-srs` also owns the reading side, because the frontend has no FSRS at all.** `current_retrievability` is the crate's forgetting curve at `now` (whole floored elapsed days, never negative, and 0 for a card the model has never seen), `word_strength` is log-stability × retrievability against `MATURE_STABILITY_DAYS`, and `item_srs` bundles the two with the card's `due` into `ItemSrs`, which `core.rs`'s `item_from` attaches to every item `getAllItems` and `getItem` return (`get_all_items` reads the clock once for the whole batch). A card too malformed to parse simply carries no `srs`: a read must not fail over a display number. `src/lib/srs/` keeps only grades, the opaque `FsrsCardState` type, `isDue` as a `due <= now` comparison and `selectSessionItems`; a test that wants a card must read it back from the store. Changing what a review folds to means bumping `DERIVED_SCHEMA_VERSION`, or devices carry a mix of old and new cards item by item.

- **The wasm build is generated, never committed.** `pnpm core:wasm` compiles `sapling-wasm` for `wasm32-unknown-unknown` and runs `wasm-bindgen --target web` into `src/lib/db/wasm/` (gitignored); `pnpm dev|build|check|test` each run it first, so a clean checkout works and a stale artefact cannot outlive an edit to the crate. The Worker loads the `.wasm` by URL (`?url`), node tests `initSync` the same bytes from disk (`backend.testing.ts`). The `wasm-bindgen` crate version in `crates/sapling-wasm/Cargo.toml` is pinned `=` to the `wasm-bindgen-cli` the flake ships — a mismatch is a hard error at bindgen time — and the target links with `lld`, which the flake provides because nixpkgs' rustc does not bundle `rust-lld`. Only the release profile is used for wasm; it is tuned for size (`opt-level = "s"`, LTO, `panic = "abort"`).

- **The fixtures are the acceptance test, twice** (`sapling-db`'s `tests/golden.rs` and `src/lib/db/golden.test.ts`). Both discover `src/lib/db/fixtures/*`, store a fixture's `objects.json` (hash → bytes) with `putObjects` after applying its log, probe every read exactly as the fixtures README describes (`missingObjects` included), and run the same idempotence, export/import, log round-trip and reverse-arrival checks — the Rust one natively over rusqlite, the TypeScript one over the wasm build through the browser-shaped path. They compare **values, not text**: `golden.rs` canonicalises every whole-valued number to an integer before comparing, because `expected.json` is written by JavaScript and serde_json keeps `1` and `1.0` apart. A value that does not match is a finding about the core, never a reason to edit a fixture. **One exception:** the four numbers that come out of the `f32` model — a card's `stability` and `difficulty`, and the `srs.retrievability` and `srs.strength` derived from them — are compared with a `1e-4` relative tolerance (`MODEL_FLOATS` in both files), because they differ slightly between the native and wasm builds. Everything else, `due`, `srs.due` and `scheduled_days` included, still matches exactly. `pnpm core:test` runs the Rust suite; `pnpm core:check` is clippy with warnings denied plus rustfmt. Nix flakes only see staged files — `git add` a new source file before `nix develop` or the toolchain will not see it either.
