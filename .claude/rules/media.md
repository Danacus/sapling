# Media, and following the clock

Design doc: `docs/reading-mode.md` (the follow view; §7 is what is still left out).

- `src/lib/media/` — **playing the recording a text was subtitled from.** Stateless on the same seam as `$lib/reading` and `$lib/conversation`: **nothing here imports `$lib/db`**, and nothing here is a fact about the learner. One idea holds the area together — **the player is a seam.** `Player` (`player.ts`) is five verbs and a clock (`currentTime`, `seek`, `play`, `pause`, `paused`, `onTime`, `destroy`); `videoPlayer` (`video.ts`) is that over a `<video>` element and `youtubePlayer` (`youtube.ts`) is the same five verbs over YouTube's IFrame API. There is a **third**, `framedYouTubePlayer` (`youtube-framed.ts`), which is the same five verbs over a hosted copy of `youtube.ts` driven by `postMessage` — the only way the desktop shell can play YouTube at all (below) — and `youtubePlayerForHost` (`youtube-host.ts`) is what the reader calls, so the choice is this area's and not the page's. The reader is written against the interface and never learns which one it got — the only thing it decides is what to mount in the stage, which is what kept the second and third implementations new files rather than rewrites of the page. Audio files go through `videoPlayer` too — `<video>` plays one without complaint and a second element would be a second set of listeners for no behavioural difference.

- **Milliseconds everywhere above the implementations, seconds only inside them.** `ReadingSentence.start`/`end` are milliseconds because a subtitle file's are; a media element's `currentTime` is seconds because the DOM's is, and so are YouTube's `getCurrentTime`/`seekTo`. That conversion lives at exactly those two boundaries and appears nowhere else — a player that hands out seconds is a bug the follow logic cannot see, because both numbers are plausible.

- **`follow.ts` is pure and holds everything that could be subtly wrong**, in the house style: no element, no clock of its own, sentences and a position in, an index out — so a test can hold the clock still. Five rules, each forced by the shape of a real subtitle file. **A gap stays on the last line that started**: cues do not tile a recording, and a highlight that blinked off in every silence would flicker through a whole conversation, so `end` never decides *which* line — only whether one is over. **`start` is inclusive**, because a player asked to seek to a line reports that number straight back and landing one line early is the first bug a learner would see. **A sentence with no timings is skipped and never landed on** (the importer gives both offsets or neither, and a prose sentence spliced into a transcript must not swallow its neighbours). **Before the first timed sentence there is no current line** — `-1`, which is also the answer for a text with no timings at all. **Sentences cut from one cue share its span and follow as one line** — the importer honestly assigns each sentence the `start`/`end` of the cue its characters came from, so two sentences in one cue have the same `start`; `sentenceRangeAt` widens to the contiguous run sharing that `start`, and the page follows that *range* rather than a single index, so the reader sees the group and "next line" steps past it. `crossedEnd(sentences, i, prevMs, ms)` is the auto-pause question and is asked **between two samples** rather than against the present: `timeupdate` fires every 200-odd milliseconds, so "is the clock past the end" is true for every sample until the next line starts and would pause again the instant the learner pressed play, while a boundary falls between two samples exactly once. `nextTimed`/`prevTimed`/`firstTimed`/`startOf` are the same skipping walk the line controls need.

- **`video.ts`, `youtube.ts`, `youtube-framed.ts` and `embed/youtube.ts` are thin on purpose and stay untested beyond `pnpm check`** — node has no media element and no iframe, and everything worth testing was moved into the pure modules beside them: `follow.ts`, `youtube-url.ts`, `youtube-error.ts` and `embed-protocol.ts`. (`embed/` is typechecked by `tsc -p embed/tsconfig.json` inside `pnpm check`, and built by `pnpm embed:build` in CI, because svelte-check's project covers `src/**` only.) Its one non-obvious piece is *which* events feed `onTime`: `timeupdate` alone fires only while playing, so `seeking`/`seeked`, `play`, `pause` and `ratechange` are listened to as well and the callback fires the moment the position becomes something else, whatever caused it. `onTime` also fires once on subscribe, so a subscriber never renders a frame against a position it has not been told. `play()` swallows its rejection (autoplay policy, teardown mid-promise): the learner still has the native controls, which is why those are left on.

- **`youtube.ts` is the same interface over an API that gives none of it away**, and every non-obvious line in it is one of three differences from a media element. **The API arrives late**: `https://www.youtube.com/iframe_api` is injected **once per page and only on demand** (a module-level promise resolved from the global `onYouTubeIframeAPIReady`, any pre-existing callback called through; a page that never opens a YouTube text never fetches it), so `youtubePlayer` stays *synchronous* and **queues** what it is asked before the iframe exists — a `play()` during the load is a learner who wants this playing, and `paused()` answers from that wish rather than lying. A `Promise<Player>` was the alternative and would have put an `await` in the reader's effect with a torn-down player on the other side of it. **There is no `timeupdate`**: the clock is polled at `POLL_MS` (250) **only while the video is playing**, and every `onStateChange` — pause, buffer, end, cue — announces once, so a seek moves the highlight immediately and a paused video burns no timer. Playing-or-not is mirrored from the state the API *pushes* rather than read back with `getPlayerState()`, which throws before ready like every other method — hence the `ready` flag every call is gated on, and why the queue is ours rather than the API's. `onTime` fires once on subscribe like `videoPlayer`'s, reporting 0 before ready. **The host is `youtube-nocookie.com`**, native `controls` stay on for the same reason `<video controls>` do, and the types are six hand-written signatures at the top of the file rather than `@types/youtube`. The API *replaces* the element it is handed, so it is given a child created here and never the caller's node — a Svelte-owned element swapped out underneath Svelte is a bug waiting for the next re-render, and it is why the reader binds an empty `<div>`. A load that fails (`onerror`, or `LOAD_TIMEOUT_MS` = 10 s for a blocker that fires no error) rejects, **clears the cached promise so a later open retries**, and reaches the reader through `onFail` — one line in the picture's place, the text still readable. **`onError` takes that same road and must stay wired**: a player that errors simply stops, with no state change and no exception, so before it was wired a disallowed embed or a dead video was indistinguishable from a slow one — a black rectangle that never filled. The code becomes a sentence in `youtube-error.ts` (pure and tested, like `youtube-url.ts`, because the message is the only part of the failure path that can be wrong): 2 unrecognised, 5 unplayable, 100 gone, 101/150 embedding disallowed by the owner, 153 **the configuration refusal below**, and a numbered fallback for anything else.

- **YouTube will not play for the desktop shell, so the desktop shell frames a hosted copy of `youtube.ts`.** The IFrame API refuses to configure a player for a document with no valid HTTP(S) referer, and a browser sends none for a custom scheme — so every embed served from `tauri://localhost` answers error **153** and never fills (upstream: tauri-apps/tauri#14422; `useHttpsScheme` is Windows/Android only, and `tauri-plugin-localhost` would serve the app over real HTTP at the cost of the IPC the database rides on). The fix is that **one document** — the one that talks to YouTube — is fetched over a genuine network connection to a real HTTPS host: `embed/youtube.html`, a separate tiny Vite project deployed to **its own Pages origin** (`deploy.md`), which imports the *real* `youtubePlayer` out of `src/lib/media/youtube.ts` so there is one IFrame-API implementation in this repo and not a copy that drifts. It is **not** in `static/`, and that is load-bearing twice over: `static/` is precached by the service worker and copied into the desktop bundle, so the page would ship inside the app *and* run on the app's own origin — the one holding the learner's OPFS database, and the very origin the page exists to escape. A page designed to be framed by anything belongs on a throwaway origin.

- **What is bridged is `Player`, not the IFrame API** (`embed-protocol.ts`, pure and tested). Three commands down — `play`, `pause`, `seek {ms}` — and three events up: `ready`, `time {ms, playing}`, `fail {message}`. So a change to YouTube's API is a change to `youtube.ts` and to nothing on the wire, and **the parent never polls across the boundary**: the page keeps `youtube.ts`'s own 250 ms poll and its announce-on-every-state-change, and posts what it hears. `ready` means "the document loaded and will honour commands", *not* "YouTube is ready" — the page's player queues what it is asked before its own iframe answers, so the app's queue drains into the page's and both are correct; what `ready` really buys is the only way to notice a page that never loaded, hence the same `LOAD_TIMEOUT_MS` = 10 s and the same sentence a failed script gets, because to a learner it is the same event. Every message carries `EMBED_PROTOCOL` (a namespace **and a version**, bumped rather than extended: the two sides deploy separately and a mismatch that is simply ignored is a video that does not play, which is visible, while a half-understood message is not), because `message` is a channel shared with every frame and extension on the page. The app posts with the page's origin as `targetOrigin` and accepts only `event.source === iframe.contentWindow` **and** `event.origin === origin`; the page accepts only `event.source === window.parent` and posts with `'*'`, which is unavoidable and safe — `tauri://localhost` cannot be named as a `targetOrigin`, and what crosses is a video id the learner chose and where it is up to. The id reaches the page as `?v=`, is put through `isVideoId` again on arrival (the id rule is `youtube-url.ts`'s, exported, never a second regex) and is passed only as a `videoId`, never into markup.

- **`youtube-framed.ts` is a proxy and not a second player**, and `youtube-host.ts` is the one place in this area that asks `inTauri()` — so the reader still calls one factory (`youtubePlayerForHost`) and stays host-blind, exactly as it is player-blind. Four things the boundary costs, and nothing else is in that file: the clock is the **last position the page reported** rather than a reading (a synchronous question cannot cross a frame, and the page announces on `youtube.ts`'s schedule so it is never staler than the direct poll); the **same queue one frame further out**, seek-then-play drained on `ready`, `paused()` honest from the wish before then; a **timeout**, because a cross-origin iframe has no `onerror` worth trusting; and the **two-part check** on every message. `destroy()` removes the iframe *and* the window listener. The gate is `inTauri()` and **not a platform test** even though the refusal is only seen on Linux and macOS today — one desktop path that is always exercised (`pnpm desktop:dev` takes it too) beats a second path only some machines run. A desktop build with **`VITE_YOUTUBE_EMBED_URL` unset** fails fast through `onFail` with a message naming the variable, and a build-time failure is reported **asynchronously** (`queueMicrotask`) like every other failure here, because the reader calls the factory from inside the effect that renders the element the failure would unmount. `deadPlayer()` (`player.ts`) is what those paths return: a `Player` that never plays, so failure is reported in one way — through `onFail` — rather than two, and the effect needs no branch for it.

- **Once the iframe has focus, the keyboard is YouTube's.** A click inside the player hands its own document the keystrokes; Space and the arrows then work YouTube's shortcuts and this app never sees the events. That is **accepted, not fought** — taking focus back from a player somebody just clicked on is worse than the on-screen transport, which always works — and the reader says so in a line under the controls. The keyboard handler stands down on a focused `IFRAME` as belt and braces.

- **`youtube-url.ts` is the one place a link becomes an id**, pure and tested (`videoIdFrom`): `watch?v=`, `youtu.be/`, `shorts/`, `embed/`, `live/`, `v/`, on `www.`/`m.`/`music.`/`-nocookie`, with or without a scheme, any surrounding whitespace, and a bare 11-character id — which is the one non-URL a learner might reasonably paste. The host test is an **exact match against a set, never a suffix**: `endsWith('youtube.com')` would take `youtube.com.example.net`, and the id it yielded would be loaded into an iframe. It returns `undefined` rather than throwing, because "not a link yet" is the ordinary state of a box someone is halfway through pasting into.

- **Nothing but a *reference* is ever stored** — a video id, or a file's *name*. A recording is routinely hundreds of megabytes; the events log syncs to every paired device and OPFS is the learner's own quota, so a video belongs in neither and `ReadingMedia` (`$lib/types`) is a *reference* — a YouTube id, or a local file's name and MIME type. The consequence for the file variant is that the `File` handle can only ever come from a picker the learner clicked, and `files.ts` closes the one gap that would make that feel broken: a module-level `Map` remembers the file across the *one* navigation from the composer to the reader, so the open straight after an import does not ask for a file chosen two seconds ago. A session cache and not persistence — it is a plain in-memory map, it dies with the tab, and every later open shows the picker. Deliberately not `sessionStorage` (a `File` does not serialise) and deliberately not the store. `takeFile` **reads without removing**, because the reader mounts more than once for one text. A chosen file whose name differs from the stored one is **accepted anyway**: the learner may have renamed or re-encoded it, and refusing would be the app being certain about the one thing it deliberately did not keep. `objectUrl` returns the url and its `revoke` together, because they are one thing — an object URL pins the file until revoked, and the caller runs the revoke on destroy and before every replacement.
