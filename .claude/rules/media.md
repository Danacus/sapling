# Media, and following the clock

Design doc: `docs/reading-mode.md` (the follow view; §7 is what is still left out).

- `src/lib/media/` — **playing the recording a text was subtitled from.** Stateless on the same seam as `$lib/reading` and `$lib/conversation`: **nothing here imports `$lib/db`**, and nothing here is a fact about the learner. One idea holds the area together — **the player is a seam.** `Player` (`player.ts`) is five verbs and a clock (`currentTime`, `seek`, `play`, `pause`, `paused`, `onTime`, `destroy`); `videoPlayer` (`video.ts`) is that over a `<video>` element and `youtubePlayer` (`youtube.ts`) is the same five verbs over YouTube's IFrame API. The reader is written against the interface and never learns which one it got — the only thing it decides is what to mount in the stage, which is what kept the second implementation a new file rather than a rewrite of the page. Audio files go through `videoPlayer` too — `<video>` plays one without complaint and a second element would be a second set of listeners for no behavioural difference.

- **Milliseconds everywhere above the implementations, seconds only inside them.** `ReadingSentence.start`/`end` are milliseconds because a subtitle file's are; a media element's `currentTime` is seconds because the DOM's is, and so are YouTube's `getCurrentTime`/`seekTo`. That conversion lives at exactly those two boundaries and appears nowhere else — a player that hands out seconds is a bug the follow logic cannot see, because both numbers are plausible.

- **`follow.ts` is pure and holds everything that could be subtly wrong**, in the house style: no element, no clock of its own, sentences and a position in, an index out — so a test can hold the clock still. Five rules, each forced by the shape of a real subtitle file. **A gap stays on the last line that started**: cues do not tile a recording, and a highlight that blinked off in every silence would flicker through a whole conversation, so `end` never decides *which* line — only whether one is over. **`start` is inclusive**, because a player asked to seek to a line reports that number straight back and landing one line early is the first bug a learner would see. **A sentence with no timings is skipped and never landed on** (the importer gives both offsets or neither, and a prose sentence spliced into a transcript must not swallow its neighbours). **Before the first timed sentence there is no current line** — `-1`, which is also the answer for a text with no timings at all. **Sentences cut from one cue share its span and follow as one line** — the importer honestly assigns each sentence the `start`/`end` of the cue its characters came from, so two sentences in one cue have the same `start`; `sentenceRangeAt` widens to the contiguous run sharing that `start`, and the page follows that *range* rather than a single index, so the reader sees the group and "next line" steps past it. `crossedEnd(sentences, i, prevMs, ms)` is the auto-pause question and is asked **between two samples** rather than against the present: `timeupdate` fires every 200-odd milliseconds, so "is the clock past the end" is true for every sample until the next line starts and would pause again the instant the learner pressed play, while a boundary falls between two samples exactly once. `nextTimed`/`prevTimed`/`firstTimed`/`startOf` are the same skipping walk the line controls need.

- **`video.ts` and `youtube.ts` are thin on purpose and stay untested beyond `pnpm check`** — node has no media element and no iframe, and everything worth testing was moved into `follow.ts` and `youtube-url.ts`, which are pure. Its one non-obvious piece is *which* events feed `onTime`: `timeupdate` alone fires only while playing, so `seeking`/`seeked`, `play`, `pause` and `ratechange` are listened to as well and the callback fires the moment the position becomes something else, whatever caused it. `onTime` also fires once on subscribe, so a subscriber never renders a frame against a position it has not been told. `play()` swallows its rejection (autoplay policy, teardown mid-promise): the learner still has the native controls, which is why those are left on.

- **`youtube.ts` is the same interface over an API that gives none of it away**, and every non-obvious line in it is one of three differences from a media element. **The API arrives late**: `https://www.youtube.com/iframe_api` is injected **once per page and only on demand** (a module-level promise resolved from the global `onYouTubeIframeAPIReady`, any pre-existing callback called through; a page that never opens a YouTube text never fetches it), so `youtubePlayer` stays *synchronous* and **queues** what it is asked before the iframe exists — a `play()` during the load is a learner who wants this playing, and `paused()` answers from that wish rather than lying. A `Promise<Player>` was the alternative and would have put an `await` in the reader's effect with a torn-down player on the other side of it. **There is no `timeupdate`**: the clock is polled at `POLL_MS` (250) **only while the video is playing**, and every `onStateChange` — pause, buffer, end, cue — announces once, so a seek moves the highlight immediately and a paused video burns no timer. Playing-or-not is mirrored from the state the API *pushes* rather than read back with `getPlayerState()`, which throws before ready like every other method — hence the `ready` flag every call is gated on, and why the queue is ours rather than the API's. `onTime` fires once on subscribe like `videoPlayer`'s, reporting 0 before ready. **The host is `youtube-nocookie.com`**, native `controls` stay on for the same reason `<video controls>` do, and the types are six hand-written signatures at the top of the file rather than `@types/youtube`. The API *replaces* the element it is handed, so it is given a child created here and never the caller's node — a Svelte-owned element swapped out underneath Svelte is a bug waiting for the next re-render, and it is why the reader binds an empty `<div>`. A load that fails (`onerror`, or `LOAD_TIMEOUT_MS` = 10 s for a blocker that fires no error) rejects, **clears the cached promise so a later open retries**, and reaches the reader through `onFail` — one line in the picture's place, the text still readable.

- **Once the iframe has focus, the keyboard is YouTube's.** A click inside the player hands its own document the keystrokes; Space and the arrows then work YouTube's shortcuts and this app never sees the events. That is **accepted, not fought** — taking focus back from a player somebody just clicked on is worse than the on-screen transport, which always works — and the reader says so in a line under the controls. The keyboard handler stands down on a focused `IFRAME` as belt and braces.

- **`youtube-url.ts` is the one place a link becomes an id**, pure and tested (`videoIdFrom`): `watch?v=`, `youtu.be/`, `shorts/`, `embed/`, `live/`, `v/`, on `www.`/`m.`/`music.`/`-nocookie`, with or without a scheme, any surrounding whitespace, and a bare 11-character id — which is the one non-URL a learner might reasonably paste. The host test is an **exact match against a set, never a suffix**: `endsWith('youtube.com')` would take `youtube.com.example.net`, and the id it yielded would be loaded into an iframe. It returns `undefined` rather than throwing, because "not a link yet" is the ordinary state of a box someone is halfway through pasting into.

- **Nothing but a *reference* is ever stored** — a video id, or a file's *name*. A recording is routinely hundreds of megabytes; the events log syncs to every paired device and OPFS is the learner's own quota, so a video belongs in neither and `ReadingMedia` (`$lib/types`) is a *reference* — a YouTube id, or a local file's name and MIME type. The consequence for the file variant is that the `File` handle can only ever come from a picker the learner clicked, and `files.ts` closes the one gap that would make that feel broken: a module-level `Map` remembers the file across the *one* navigation from the composer to the reader, so the open straight after an import does not ask for a file chosen two seconds ago. A session cache and not persistence — it is a plain in-memory map, it dies with the tab, and every later open shows the picker. Deliberately not `sessionStorage` (a `File` does not serialise) and deliberately not the store. `takeFile` **reads without removing**, because the reader mounts more than once for one text. A chosen file whose name differs from the stored one is **accepted anyway**: the learner may have renamed or re-encoded it, and refusing would be the app being certain about the one thing it deliberately did not keep. `objectUrl` returns the url and its `revoke` together, because they are one thing — an object URL pins the file until revoked, and the caller runs the revoke on destroy and before every replacement.
