# Media, and following the clock

Design doc: `docs/reading-mode.md` (the follow view; §7 is what is still left out).

- `src/lib/media/` — **playing the recording a text was subtitled from.** Stateless on the same seam as `$lib/reading` and `$lib/conversation`: **nothing here imports `$lib/db`**, and nothing here is a fact about the learner. One idea holds the area together — **the player is a seam.** `Player` (`player.ts`) is five verbs and a clock (`currentTime`, `seek`, `play`, `pause`, `paused`, `onTime`, `destroy`); `videoPlayer` (`video.ts`) is that over a `<video>` element, and YouTube's iframe will be the second implementation of the same interface. The reader is written against the interface and never learns which one it got, which is what keeps the next slice a new file rather than a rewrite of the page. Audio files go through `videoPlayer` too — `<video>` plays one without complaint and a second element would be a second set of listeners for no behavioural difference.

- **Milliseconds everywhere above `video.ts`, seconds only inside it.** `ReadingSentence.start`/`end` are milliseconds because a subtitle file's are; a media element's `currentTime` is seconds because the DOM's is. That conversion lives at exactly one boundary and appears nowhere else — a player that hands out seconds is a bug the follow logic cannot see, because both numbers are plausible.

- **`follow.ts` is pure and holds everything that could be subtly wrong**, in the house style: no element, no clock of its own, sentences and a position in, an index out — so a test can hold the clock still. Four rules, each forced by the shape of a real subtitle file. **A gap stays on the last line that started**: cues do not tile a recording, and a highlight that blinked off in every silence would flicker through a whole conversation, so `end` never decides *which* line — only whether one is over. **`start` is inclusive**, because a player asked to seek to a line reports that number straight back and landing one line early is the first bug a learner would see. **A sentence with no timings is skipped and never landed on** (the importer gives both offsets or neither, and a prose sentence spliced into a transcript must not swallow its neighbours). **Before the first timed sentence there is no current line** — `-1`, which is also the answer for a text with no timings at all. `crossedEnd(sentences, i, prevMs, ms)` is the auto-pause question and is asked **between two samples** rather than against the present: `timeupdate` fires every 200-odd milliseconds, so "is the clock past the end" is true for every sample until the next line starts and would pause again the instant the learner pressed play, while a boundary falls between two samples exactly once. `nextTimed`/`prevTimed`/`firstTimed`/`startOf` are the same skipping walk the line controls need.

- **`video.ts` is thin on purpose and stays untested beyond `pnpm check`** — node has no media element, and everything worth testing was moved into `follow.ts`. Its one non-obvious piece is *which* events feed `onTime`: `timeupdate` alone fires only while playing, so `seeking`/`seeked`, `play`, `pause` and `ratechange` are listened to as well and the callback fires the moment the position becomes something else, whatever caused it. `onTime` also fires once on subscribe, so a subscriber never renders a frame against a position it has not been told. `play()` swallows its rejection (autoplay policy, teardown mid-promise): the learner still has the native controls, which is why those are left on.

- **Nothing but a file's *name* is ever stored.** A recording is routinely hundreds of megabytes; the events log syncs to every paired device and OPFS is the learner's own quota, so a video belongs in neither and `ReadingMedia` (`$lib/types`) is a *reference* — a YouTube id, or a local file's name and MIME type. Both variants are defined although only `file` is played, so the shape is settled before the second one lands and a `youtube` text falls back to the paged reader rather than erroring. The consequence is that the `File` handle can only ever come from a picker the learner clicked, and `files.ts` closes the one gap that would make that feel broken: a module-level `Map` remembers the file across the *one* navigation from the composer to the reader, so the open straight after an import does not ask for a file chosen two seconds ago. A session cache and not persistence — it is a plain in-memory map, it dies with the tab, and every later open shows the picker. Deliberately not `sessionStorage` (a `File` does not serialise) and deliberately not the store. `takeFile` **reads without removing**, because the reader mounts more than once for one text. A chosen file whose name differs from the stored one is **accepted anyway**: the learner may have renamed or re-encoded it, and refusing would be the app being certain about the one thing it deliberately did not keep. `objectUrl` returns the url and its `revoke` together, because they are one thing — an object URL pins the file until revoked, and the caller runs the revoke on destroy and before every replacement.
