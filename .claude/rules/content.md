# Romanization and speech

- `src/lib/romanize/` — **local, per-language romanization, no LLM**. The registry (`index.ts`) is keyed by BCP-47 primary subtag (resolved from the free-text `targetLanguage` via `$lib/tts/languages`' `bcp47For`; currently `zh` only — Cantonese maps to `yue` and is deliberately excluded, jyutping ≠ pinyin). `loadRomanizer` dynamic-imports the implementation so pinyin-pro's ~287KB dictionary is a lazy chunk only Chinese learners fetch; `romanizerFor` is the sync accessor once loaded. `zh.ts`'s correctness invariant: the **whole string** goes through pinyin-pro and readings are sliced per char — context is what resolves polyphones (银行 háng vs 自行车 xíng), so never romanize a term in isolation. `tokenize(text, terms)` groups characters around the learner's vocabulary `terms` so a tracked word comes back as one token whose `text` equals its item term. Consumption: `planReadings` (`$lib/session/romanization`, rolled once at serve) yields a `ReadingPlan` — `sentence` for flat stored readings, `byTerm` for per-word adaptive fading — and `rubyFor` in `$lib/challenges/props` is the one composition every challenge component calls; `$lib/ui/RubyText.svelte` renders the tokens and stays dumb (hidden readings arrive already nulled by `applyPlan`). A `null` tokenizer (no local romanizer, or its chunk not landed yet) falls every slot back to the stored LLM `…Romanization` strings gated by `readings.sentence` — exactly the pre-ruby behavior, which is why the wire format keeps emitting readings: they are the fallback for every other language and feed the romanized `acceptedAnswers`. **A word on its own** (the garden, `/words`) goes through `itemReadingTokens` (`item.ts`) instead — **always shown, whatever the romanization preference says**: that preference fades a crutch during play, while a reference list states a fact about the word — and there the **stored `romanization` is authoritative**: it is the only thing that tells two same-spelled cards apart, so the local romanizer may split an *agreeing* reading per character with tone marks (`readingFold` decides agreement) but a disagreeing one is shown as stored, over the whole term. The one sanctioned isolation call is `Romanizer.unambiguousReading` (zh: multi-character terms via the word dictionary, single characters only when pinyin-pro lists one reading); `localReadings` uses it to backfill missing readings for free and leaves every polyphone for the model (`fillRomanizations`), which is the `readings` task's local-first, model-second order (`$lib/tasks/kinds/readings.ts` — the settings page works out the two lists for its own copy and starts the task; the def owns the writes and the one call, free readings landing before the model is asked). The voice model download is the `tts-model` task in the same way, wrapping `preloadKokoro` unchanged, and the recognizer's is `asr-model` over `preloadDictationModel`; both fold their host's progress into one bar through `$lib/tasks/kinds/model-download`, which is where that arithmetic lives now.

- `src/lib/tts/` — public API `speak(text, lang)`; zh+en use Kokoro v1.1, everything else Web Speech. **The worker is plain JS at `static/tts/sherpa-worker.js`, deliberately outside Vite** (a bundled TS worker diverged between dev and build); config reaches it via the init message from `sherpa.ts`, with `models.ts` the single source of truth for artifact URLs/sizes. Model files (~439MB fp32) are runtime-fetched from a pinned mirror commit and cached in Cache Storage; the int8 variant is a known upstream NaN/silence bug **in the WASM build** — don't "optimize" back to it (it is fine natively, which is a fact about that build and not a reason to change this one). **There is a third engine, and it is the same Kokoro**: inside the Tauri desktop shell `tts.ts` routes `'kokoro'` to `native.ts` — sherpa-onnx compiled natively in `crates/sapling-desktop`, the only way that model runs on WebKitGTK — behind the same `KokoroProvider` shape, with the same speaker ids, so `speak`, the preference values and everything above the seam are unchanged (`desktop.md`). **A Tauri host may lend synthesis without playback, or neither**: so the router asks the *host* and not the platform — one memoised `tts_status` probe, and a host that cannot answer it at all gets a provider whose every call fails, which is the path `speak` and `warmSpeech` already took to the browser voice. `inTauri()` stays the only platform test; `voiceDownloadBytes()` answers 0 on a voiceless host rather than rejecting, because Settings does not await it. **On the *desktop* host the playback is the host's too**, and for a separate measured reason: WebKitGTK builds a fresh GStreamer pipeline per `<audio>` clip so a spoken word starts about a second late, and its Web Audio output plays noise or silence, so `playClip` sends the bytes back over `tts_play` and rodio plays them on one output stream the host holds open. The element path stays as that host's fallback (latched for the session when there is no output device, per clip when the host refuses one), and is still exactly what the web build does. **The Android build of that same shell synthesizes identically and does not play**: its WebView is Chromium, an `<audio>` element over a blob is the ordinary path there, and `tts_play`/`tts_stop` are not compiled at all — so `tts_status` carries a `playback` flag and a host that answers `false` goes straight to the element path, with no per-clip attempt, no warning and nothing latched. **The install is one bar, and that host crosses it twice**: it fetches an archive and then unpacks it, reporting both halves against the archive's own size, so `voiceInstallPasses()` says how many times the events cross the model and `$lib/tasks/kinds/tts-model` divides by it — fixing the denominator at what the install announced before it moved a byte, because summing the two keys was a bar that reached 100%, dropped to half of a doubled total and climbed again. Audio failures must degrade silently to fallback; sound never blocks gameplay.

- `src/lib/asr/` — dictation, `speak`'s mirror: public API `listen(lang, handlers)` behind the same `bcp47For` routing, and **two backends now**, picked per call the way `speak` picks Kokoro. **The transcript lands in the composer, never in the send** — `appendDictation` splices it into the page's `input` and the learner presses Send, so a misheard word is a typo they fix rather than a mistake the teacher corrects them for, and `conversation/diff.ts` keeps aligning against a message they endorsed. That is what makes ASR's habit of silently repairing homophones harmless here, and it is the invariant to preserve: no path may send a transcript unread. The join is `spanGap`'s, borrowed from `conversation/diff` rather than re-derived, because a dictated 我想要 sits flush and a dictated `please` does not. Unlike synthesis, **recognition is not universal** (no Firefox, no WebKitGTK, no Android WebView), so `dictationAvailable(lang)` gates whether the control renders at all — the fallback is typing, not another engine. `listen` returning `undefined` means no handler will ever fire; a returned session always ends in exactly one `onEnd`. `no-speech` and `aborted` are ordinary stops and must stay silent (`micErrorMessage`) — only a microphone the learner can still fix earns UI, and `native.ts` maps `getUserMedia`'s `DOMException` names onto that same vocabulary rather than writing new sentences.

- **The second backend is the host's** (`native.ts`, `desktop.md`): sherpa-onnx running SenseVoice natively in a Tauri shell, which is the only recognizer either of those webviews has at all. The router asks the *host*, never the platform — `inTauri()` says only that there may be one to ask, and one memoised `asr_status` probe answers whether the commands exist, whether the model is downloaded, and **which languages it covers**; the language list comes from the host so swapping the model is a `ModelSpec` change in the crate and nothing here. Matching is on the BCP-47 primary subtag, so `zh-CN` and `zh-Hans` are `zh` while `yue` stays its own language. `dictationAvailable` is therefore **async and takes the language**, and it is also what *warms* the probe — `listen` stays synchronous because that is what its callers are written against, and reads the settled answer; a caller that never awaited `dictationAvailable` simply gets Web Speech. **The audio is captured in the window on both hosts**: `getUserMedia` plus an `AudioWorklet` (`static/asr/pcm-worklet.js`, plain JS outside Vite for the reason `sherpa-worker.js` is), 16 kHz mono, framed to 16-bit LE PCM by `pcm.ts` and sent as a raw IPC body exactly as `tts_play`'s clip is. The worklet node has **`numberOfOutputs: 0`** and nothing is ever connected to `AudioContext.destination` — Web Audio *output* on the desktop host plays noise or silence, and a recorder that had to reach the speakers to be pulled is the one shape that could make a sound while the learner is talking. **The "nothing was said" gate is `pcm.ts`'s and belongs there**: SenseVoice answers digital silence with `嗯。` rather than declining, the host stays honest and reports what the model said, and the contract that `no-speech` ends silently is this layer's — so an utterance under 0.2 s or quieter than a muted microphone never crosses. It is a gate, not a VAD, and phase one has no VAD and no partial transcripts: one `onTranscript(text, true)`, then `onEnd()`.
