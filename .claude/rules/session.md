# Practice

The practice stream, generation and every play-time DB write.

- `src/lib/session/engine.ts` — the orchestrator: it asks Rust for the decisions (`streamHead` and `nextPick` over it, `lowWaterMark`, `matchRound`, `isEarlyChallenge`, `planTopUp`, `topUpCoverage`, through `$lib/challenges/core`; they are `crates/sapling-challenges`' `stream.rs` and `topup.rs`) and owns everything around them — generation (`generateChallenges` → `getBatch` → `addToPool`), all DB writes during play (`applyResult`, `amendResult`, `applyOverturn`, `reportChallenge`), the start screen's read (`practiceOverview`) and accounting (`sessionSummary`). `stream.ts` is the stream's memory between picks and its reads; `serving.ts` what a pick is made against. Components emit answer events; they don't write.

**Practice is pure FSRS review of the vocabulary the learner already has, and generation never introduces a word.** The whole collection participates — a word added yesterday and never reviewed is due work like any other — so there is no mode, no filter and no `reviewOnly` option anywhere. New vocabulary arrives explicitly, through `add_words` in `$lib/assistant` and `$lib/conversation`. That is why `generateChallenges` makes no item write at all, why `getBatch` returns challenges only, and why the learn screen's answer to an empty collection is a link to `/converse` and `/chat` rather than a Generate button: with no words, there is nothing to write a lesson about.

## Sessions & challenge lifecycle

**Generation and play are decoupled.** Every challenge ever generated lives in a persistent *pool*, the `challenges` table (`ChallengeRow` = `Challenge` + `generatedAt`/`timesServed`/`lastServedAt`/`reported`/`topic?`/`correction?` — the last the difficulty model's learned correction for the row — generated from `sapling-challenges`' `PoolRow`), populated by `challengeAdded` events and materialised per `crates/sapling-db/src/materialize.rs`. Answering a challenge does not consume it — `applyResult` calls `recordServe`, which only stamps it. Serve-stamping at *answer* time is what makes stopping self-cleaning: a challenge shown but never answered was never stamped, so it comes back in the next stream for free.

**Practice is one stream that runs until the learner stops** (`docs/challenge-difficulty.md` §11; `stream.rs`, deterministic and tested there). There is no plan: `src/routes/learn/session/+page.svelte` asks `$lib/session/stream`'s `PracticeStream.next()` for one challenge at a time, after the last answer's writes have landed, and the stream reads the pool, the words, the learned parts and the profile fresh for each pick — so each pick sees the review, the skill and the serve stamp the last answer wrote. **One list, one predicate.** `upcoming` (`stream.rs`) is the next words in urgency order — FSRS-due words first, most overdue first, then the words not yet due, soonest first, id breaking a tie; only words with a term and a meaning, since nothing can be written about the rest — each with the row it would be served, if any is **available**. `available` is the one predicate, and the only one: *playable* (not reported, all `itemIds` still resolve — `pool.rs`' `is_playable`), an active kind, **not served this stream** (`served` — which also keeps a word FSRS re-queues within minutes after a miss from getting the same sentence back), *rested* (never served or `RESERVE_GAP` = 3 days since) **or merely resting when the word is due** (otherwise a fast first two days serve-stamps the whole pool and leaves words due with nothing), and **fits** (below). Among a word's available rows, rested ones before resting ones, then the one whose best help level sits closest to the aim, then never served (newest first) before served (longest ago first). **The next pick** (`head`/`next_pick`, the engine's `streamHead(pool, items, now, { serving, served })` and `nextPick` over it) is the head of that list and nothing else: it answers the head word and, unless it has nothing, a position into the pool with its help level (`{word, next?: {at, shown, chance, due}}`), so what plays is the row as stored, minus its bookkeeping (`challengeOf`), and a row this build cannot parse keeps its place and is simply never picked. **Serving never skips the head**: while the most urgent word has nothing available, `next()` answers `blocked` and the screen waits for a refill to write for it — so the words the schedule owes can never be passed over for words ahead with rows of their own. Due-first is load-bearing: a global freshness weight would let every new batch crowd out due reviews and quietly kill spaced repetition; and because the list carries on past the due words into review-ahead, there is no separate practice mode. **Stopping is always clean**: every answer is written as it happens, and a challenge never answered was never stamped, so the stop ✕ goes straight to the summary with no confirmation.

**Refill is the stream's to ask for, and it runs as a task.** It reads the same list: `plan_top_up` with a `limit` writes for exactly the words among the first `limit` of `upcoming` that have nothing available, and the stream's `limit` is the **low-water mark** (`low_water_mark`: the batch's time over the learner's pace plus two, within 4–20 — the stream keeps the median of its last ten answer times and times each batch it started from the task record, `startedAt` → `finishedAt`), so a batch comes back before the learner reaches the words it is for. After the first pick and after each answer lands, when the learner *can* write (a key and a connection) and no top-up is running, the page claims one with `PracticeStream.refill()` — the `{served, asked, limit}` a top-up should write for, or `null` when none of those words wants anything — and starts `startTask('top-up', { profile, served, asked, limit })` itself: `$lib/session` never imports `$lib/tasks`, the task input carries what the stream has shown so the planner judges rows exactly as serving does, and single flight is the runner's (`serial`). **A word is asked for once**: the stream keeps the words its refills asked for (`asked`, beside `served`, passed to the planner, where such a word wants nothing) until a row of theirs is served — so rows that came back not fitting, a word a batch dropped and a failed batch all end at one request instead of re-firing after every answer, while a word that was served and later runs out (a miss that re-queues it with rows it no longer fits) may be asked for again. The page keeps only the ids it started, never task state. When the head is **blocked** (`next()` answers `{kind: 'blocked', asked}`): a batch on its way means **waiting** (a spinner and a Stop, the tray saying the rest; a batch the learn screen started wakes it too), then picking again when it settles; otherwise, if the head was not asked for yet, a batch for it is claimed and waited for; and when no batch can help — the head was already asked for, a batch failed or was cancelled, no key (mock mode), no connection — the stream stops and says why, with a **Try again** beside Back to Practice, which starts a fresh `asked` (`resetAsked`). Because the writer solves the very check serving applies (below), and a written row is judged at the length it was asked for (`challenges.md`), a batch written as asked always gives the head something. Mock mode never refills on its own: the doc's "no key" case, and the learn screen's Write-a-lesson button still writes a mock batch on request.

What the start screen shows is `practiceOverview()` — the due count, the first pick the stream would make, and **coverage** (`PracticeOverview.topUp`, `coverage` in `topup.rs`), read off the same list over the whole collection. A word is **covered** when it has a row available — the very predicate serving picks by. Its two numbers answer deliberately different questions. The **figure** is about the session in front of the learner — `covered / upcoming`, where `upcoming` is *every* due word when the schedule owes any and otherwise the next `UPCOMING` (20) soonest-due ones; `due: boolean` says which, and changes nothing but the word on the label ("Due words with fresh challenges" / "Next words with fresh challenges"). The **count** (`wants`) is about the button, which plans with no `limit`, so it spans the whole list and can be positive while every due word is covered — the press then buys the words further down the collection. The Generate button's label is "Write N new challenges", and the `notice` nudges (and the card is `urged`) **only in practice mode** — mock, no key, where the stream cannot write by itself — when the first word has nothing or at most half of the figure's words are covered; all of them read the one list, so the card can never nudge towards a button that would refuse. With a key and a connection the stream fills those gaps itself, so the card is framed as optional and never urged: what only a press does is write ahead before going offline, or carry a topic. Offline, neither can write, and a start screen with nothing to practise says so. **At zero wants the button is disabled and reads "Everything's covered"**, which happens only once the learner's whole collection is covered. There is no "write more anyway" mode, and a topic colours the lesson and adds no wants of its own.

**Difficulty is one check, `fits`, on one learned scale** (`docs/challenge-difficulty.md`; the model is `crates/sapling-challenges`' `model.rs`, its numbers derived data the core keeps, `data.md`). **Each number has one job**: FSRS memory decides *which word* (the list's order), and a row is judged only by the chance *given the word is remembered*, `sigmoid(skill − difficulty)` — skill the words' learned skill (their average), difficulty the kind and help level's learned base plus the kind's slope times the row's length plus the row's own learned correction. Memory enters only prediction (`chance_of`, `memory × sigmoid(…)`), calibration and learning. A row **fits** when that chance sits inside the window around the learner's aim (profile `aim`: easier/normal/harder → 0.97/0.89/0.78, which at FSRS's 0.9 memory is the 88/80/70% a learner experiences; the window −17 to +4 points), **widened per skill just far enough to take in the nearest row a writer can produce** (`window_for`) — so a word too weak for the easiest kind at its shortest still fits that, and one too strong for the hardest still fits that: every word always has something writable that serving accepts, and that is what lets serving wait on the head without ever deadlocking. What a pick is made against besides the pool and the words is one `Serving` (`$lib/session/serving`): the learned shared numbers (`getDifficultyParts`), the aim, the readings setting and whether listening is possible — the last two bounding which help levels exist (`fits.rs`' `help_levels`), read from this device's preferences by `deviceServing`. `practiceOverview()` and every pick read pool, items, the learned parts and the profile; starting never touches the network, so it is instant, always. "Start practising" is live when a first pick exists, or when the first word has nothing yet but a batch could be written (a key, a connection, and wants) — the stream then opens waiting on it.

**The free match rounds are a pacing rule on the stream, confined to early material.** A challenge about a word whose strength bar is under `EARLY_STRENGTH` (0.3) counts (`is_early`; answered, and only a reviewing type); after every `MATCH_PAIRS_EVERY`th (4) such challenge the stream's next step is one locally built `match-pairs` round (`match_round` over `match_pairs.rs`: pairs drawn from the early words only, every tile label unique, five pairs, three at least), and only when a pick exists to follow it — the stream never ends on free filler. Matching pairs is a recognition warm-up; once a word is mature the stream reads as uninterrupted work. That is the one place strength steers practice, and it is pacing, not difficulty. A `seed` replays the rounds. Audio is warmed per challenge as it is shown (a round's tiles included), fire-and-forget, one clip at a time — sound never blocks play.

**Every serve-time presentation decision is the pick's help level, turned into a screen in one place, `serve.rs`, and handed down as one prop.** A cloze's `translationHint`, a word-order's `prompt` and a spot-error's `meaning` are always written by generation (the model emits content, never presentation) and always on the row; a cloze's/multi-cloze's word bank and a word-order's distractor tiles are likewise always written in full, and so are the readings. A help level is a view of that row (`challenges.md`): `presentationFor(challenge, shown)` (`$lib/challenges/serve`) answers the one `Presentation` — hint, bank size, distractor tiles, the reading shown or hidden as a whole, `listening`, and `shown` itself; the practice screen computes it once per shown challenge from the pick's `shown` (a match round is `plain`) and hands it to `ChallengeHost` through `ChallengeProps.presentation`, and every component resolves it with `resolvedPresentation` — absent (a bare render, tests) means "show everything stored, hint on, every reading on, not heard first", the one default that helper owns. Listening is decided here too, once, not inside `MultipleChoice.svelte`: a failed or silent clip still reveals the text there, so sound never blocks play. The same object travels further: `applyResult` records its `shown` on the answer (`ChallengeResult.shown`, what the difficulty model learns from), the learn screen captures it onto `Feedback.presentation` the instant a challenge is answered (so a later challenge swap can't change it), `FeedbackBanner` takes it as an optional prop, and `ask()` forwards it to `getEscalation` as `EscalationArgs.presentation` (`llm.md`) — a dispute is judged against what the learner's screen actually showed, not the full stored row. `visibleBank`/`visibleTiles` then pick *which* stored entries show at that size, deterministic from the row's own stored order (already shuffled once, at resolve time) — the answer(s) first, keeping their stored position, then the first surviving distractors in stored order, never reshuffled again; `Cloze.svelte`, `MultiCloze.svelte` and `WordOrder.svelte` render the `visible*` subset, and grading still runs against `acceptedAnswers`/`answerTokens`, never bank or tile indices, so a trimmed bank or tray cannot break it. Serve time rather than generation time because a row outlives how its word stood when it was written: one row serves a weak word at `pick-4` and, weeks later, the same word at `typed`. Some rows written by an earlier build lack the hint or the bank altogether; `steps_of` offers them only the steps they can show, and they stay playable.

Generating runs **as a background task** — when the stream's words ahead want rows (above), or when the learner asks from the learn screen (`generateChallenges` either way, the learner's press with an optional topic) — `startTask('top-up', …)` in `$lib/tasks`, which owns the ledger, the cancel and the error; the learn screen reads `taskStore.latestOf('top-up')` and re-reads its overview in an `$effect` when one settles `done`, and the practice screen watches the records it started; practice can already run from existing material, and the new challenges simply land in the pool, where the next pick finds them. The start screen shows only the button's running state and one line of outcome (the task's `summary`, or its `error` with a Try-again) — the step ledger lives in the task tray, not on the page. `generateChallenges` itself knows nothing about tasks. **What gets written is what the list is missing, and nothing else.** `plan_top_up` (`topup.rs`; the engine's `planTopUp(pool, items, now, { serving, served, asked, limit, seed })`; in Rust a `Scope`) is the whole brief: it reads `upcoming` — the stream's list, with `served`, `asked` and `limit` for a stream's refill, or the learner's **whole collection** for a press — and a word with nothing available wants `WANT_PER_WORD` (2) rows written, each a **want** `{item, kind, length}`. The kinds are those `length_for` answers for: some length in the kind's range (`data/kinds.json`) at which a freshly written row, at one of the steps it is written with, fits the word. Among them a kind the word has *never* had a playable row of wins, and a draw breaks the tie (a `seed` replays it); a word never gets the same kind twice in one top-up. **The writer is the judge run backwards**: the length is solved from the same remembered chance and the same widened window `fits` uses — the one closest to putting the word at the aim at the kind's middle help level, among the lengths that fit — so a row written as asked fits its word by construction — the more so as it is judged at the length asked for, whatever length the model wrote — and written in the middle it still fits when the word weakens (an easier help level) or strengthens (a harder one). **A covered word emits nothing and is simply stepped over**, and the list is capped at `MAX_TOPUP_WANTS` (24), cutting the least urgent words — which still want afterwards, so the next one starts with them. **There is no accuracy dial and no recent-mistake list, on purpose**: every answer already moves the word's skill and the row's correction, which is what the next pick and the next length are read from — one mechanism, not two that had to be kept agreeing. So a press with the whole collection covered has nothing to ask for, and `generateChallenges` says so (a plain `Error`, rendered inline like an `LlmError`) before spending anything; `GenerateInfo.failedRequests` says how many requests came back empty, since their wants are simply still wanting. `planRefill(pool, items, profile, now, opts)` is the thin wrapper that puts those wants into `BatchArgs` beside the profile, `topic` and `knownItems`; the LLM layer plans nothing. `knownItems` (the whole vocabulary; only the terms reach the prompt, with a `romanization` riding along so the prompt can tell two same-spelled cards apart) is what the model builds sentences *out of*, and a challenge may cite one of those words by term; the resolver drops any challenge whose references resolve to neither a known id nor a known term, which is the only enforcement needed, since nothing can mint an item. So **prompt/schema changes only reach the pool via newly generated batches** — old rows keep playing as they were generated, which is a recurring source of "bug" reports. The learner can flag a bad challenge from the feedback banner; `reported` rows are excluded from `getPool()` forever.
