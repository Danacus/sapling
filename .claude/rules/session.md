# Sessions

Planning, generation and every play-time DB write.

- `src/lib/session/engine.ts` — the orchestrator: owns session planning (`planSession` — pure, tested), generation (`generateChallenges` → `getBatch` → `addToPool`), all DB writes during play (`applyResult`, `applyOverturn`, `reportChallenge`) and session accounting (`sessionSummary`). Components emit answer events; they don't write.

**A drill session is pure FSRS review of the vocabulary the learner already has, and generation never introduces a word.** The whole collection participates — a word added yesterday and never reviewed is due work like any other — so there is no mode, no filter and no `reviewOnly` option anywhere. New vocabulary arrives explicitly, through `add_words` in `$lib/assistant` and `$lib/conversation`. That is why `generateChallenges` makes no item write at all, why `getBatch` returns challenges only, and why the learn screen's answer to an empty collection is a link to `/converse` and `/chat` rather than a Generate button: with no words, there is nothing to write a lesson about.

## Sessions & challenge lifecycle

**Generation and play are decoupled.** Every challenge ever generated lives in a persistent IndexedDB *pool* (`ChallengeRow` = `Challenge` + `generatedAt`/`timesServed`/`lastServedAt`/`reported`/`topic?`; Dexie `version(2)`, migrated from the v1 queue by the pure `poolRowFromLegacy`). Answering a challenge does not consume it — `applyResult` calls `recordServe`, which only stamps it. Serve-stamping at *answer* time is what makes an early quit self-cleaning: unplayed picks were never stamped, so they come back in the next plan for free.

`planSession(pool, items, now)` (pure, deterministic, tested) assembles a session behind two gates, only one of them firm: *playable* (not reported, all `itemIds` still resolve) is absolute, *rested* (never served or `RESERVE_GAP` = 3 days since) is a preference. Then **due-first** — each FSRS-due item, most overdue first, claims the best challenge covering it, and freshness only breaks ties and fills leftover slots. That ordering is load-bearing: a global freshness weight would let every new batch crowd out due reviews and quietly kill spaced repetition. The rest gap yields to it exactly once: a due word with no rested challenge takes its least-recently-served resting one in the first pass (otherwise a fast first two days serve-stamps the whole pool and leaves words due with nothing playable), while the second-angle pass and the freshness filler stay rested-only. **Then the same two passes run over the words that are *not* due yet** (soonest-due first, gap never spent in the walk), and the very last filler finally reaches into resting material — so a plan is empty only when the pool genuinely has nothing playable, and "Start session" is always live. That tail is why there is no separate practice planner or second button: early review is native to FSRS (a review is graded whenever it happens, just a smaller stability gain), so a session simply degrades from due-work into review-ahead. What tells the learner to generate is `poolLow` (**fewer than `POOL_LOW_THRESHOLD` *rested* challenges** — plan length no longer means anything, since the plan is never short), surfaced as the start card's one `notice`. A third preference rides *inside* that structure: **bearability** (`$lib/session/progression`) — wherever the planner takes "the first unpicked candidate" out of an item's rested or resting list it now takes "the first unpicked *bearable* one, else the first unpicked", so a word gets recognition while it is new and production once `wordStrength` clears the tier's floor (`CONSTRAINED_PRODUCTION_FLOOR` ≈ one successful review, `FREE_PRODUCTION_FLOOR` ≈ three). Because the rule only reorders *within* a bucket it can never cost a review or bend the rest gap. `maturityOf` reads the same floors for `planRefill`'s `reviewItems`, so the generation prompt writes the types the planner would actually serve. `startSession()` reads pool + items and plans; session start never touches the network, so it is instant, always.

Generating is an explicit user action (`generateChallenges`, no threshold) that the learn screen runs **in the background** while a session can already be played from existing material; the new batch simply lands in the pool. `planRefill` decides what it is *about*: `selectSessionItems` takes the due words most-overdue-first, then tops the list up to `maxItems` with the soonest-due ones that are not due yet — the same degradation `planSession` performs on the play side, one layer earlier, so a caught-up learner still gets a lesson instead of an empty batch. `knownItems` (the whole vocabulary, terms only) is what the model builds sentences *out of*, and a challenge may cite one of those words by term; `resolveBatch` drops any challenge whose references resolve to neither a known id nor a known term, which is the only enforcement needed now that nothing can mint an item. A topic still shapes what the review challenges are about. So **prompt/schema changes only reach the pool via newly generated batches** — old rows keep playing as they were generated, which is a recurring source of "bug" reports. The learner can flag a bad challenge from the feedback banner; `reported` rows are excluded from `getPool()` forever.
