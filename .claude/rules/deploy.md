# Deploying

**Two targets, deployed separately on purpose.** The app is Cloudflare Pages (below). The sync backend is a *Worker* — `worker/`, `wrangler.jsonc` — deployed either by **Workers Builds** (the Workers equivalent of Pages' git integration: connect the repo under the Worker's Settings → Builds, deploy command `npx wrangler deploy`, and the Worker's name must match `wrangler.jsonc`'s `sapling-sync` or the build fails) or by hand with `pnpm sync:deploy`.

**The Worker is a sequencer, nothing else.** `worker/` (`wrangler.jsonc`) assigns every event a `seq` and hands events back in that order; it never merges and never reads a payload — every merge rule lives in `crates/sapling-core/src/materialize.rs`. The pairing phrase travels as an `Authorization: Bearer` header, normalised and hashed to name the Durable Object room. `worker/` imports `src/lib/sync/phrase.ts` from the client on purpose, so the two normalisations can never drift apart — which means **Workers Builds *build watch paths* must include `src/lib/sync/*`, not just `worker/*`**, or a new client can ship against a stale Worker; the symptom is a second device opening an empty library, which reads as lost data rather than a version skew. Leaving watch paths empty (rebuild on every push) is the safe default. The app finds the Worker through `VITE_SYNC_URL`, a build-time variable set in the Pages project's environment; unset, the build simply has no sync. `pnpm check` typechecks the Worker too (`tsc -p worker`), since svelte-check's tsconfig only covers `src/**`. See `docs/sync.md`.

Cloudflare Pages, **built by GitHub Actions, uploaded by wrangler** — `.github/workflows/deploy.yml`. `pnpm build` needs more than node: it runs `pnpm core:wasm` first, which wants `cargo` with the `wasm32-unknown-unknown` std, `lld` and a `wasm-bindgen-cli` of exactly the pinned version. The flake provides all of that and the Pages build image ships none of it (its languages are Go, Node, Bun, Python, Ruby), so **the Pages git integration is switched off** and the workflow is the one build flow: every step runs under `nix develop -c`, so CI and a laptop use the same pinned toolchain, and the deploy step is the repo's own `wrangler pages deploy build`, run only for a push to `main` after every gate has passed. Pull requests run the gates and the build without deploying. The workflow reads two secrets (`CLOUDFLARE_API_TOKEN` with Pages edit rights, `CLOUDFLARE_ACCOUNT_ID`) and two variables (`CLOUDFLARE_PAGES_PROJECT`, the Pages project name; `VITE_SYNC_URL`, which used to live in the Pages project's environment and now lives in the GitHub repository's). The nix store, the pnpm store and cargo's registry and `target/` are cached between runs, keyed on the lockfiles.

`static/_headers` sets immutable caching for `/_app/immutable/*`, and sets **no** COOP/COEP — because nothing needs cross-origin isolation, not because it would break anything. That second half corrects an earlier belief (2026-08-29): isolation was thought to break the TTS model-mirror fetches, and measurement says it does not, because those fetches are `cors`-mode against a mirror sending `access-control-allow-origin: *` and COEP only imposes CORP on *no-cors* subresources. Treat isolation as available-if-needed rather than ruled out — but it is no longer free: the reading follow view frames YouTube's player, and a cross-origin frame is blocked under `COEP: require-corp` unless it sends CORP or COEP itself, which YouTube does not. **No CSP is set either, and that is now load-bearing**: the same view loads `https://www.youtube.com/iframe_api` and frames `https://www.youtube-nocookie.com`, so a policy added later has to name both in `script-src`/`frame-src` or the player fails with nothing in the console to say why. `static/_redirects` routes everything else to the `index.html` SPA shell (`fallback: 'index.html'`) *except* `/_app/immutable/*`, which gets a real `static/404.html` on a miss instead — a missing hashed chunk must 404, not silently succeed as HTML, or a single stale-client request for a dead chunk gets edge-cached under the immutable header and poisons that URL for everyone for up to a year (see the incident this fixed, 2026-08-24).

The app is an installable PWA (`static/manifest.webmanifest` + `src/service-worker.ts`; SvelteKit auto-registers the worker in production builds only). Users install it from the browser's "Install app" control, or on iOS via Share → Add to Home Screen.
