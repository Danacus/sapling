# The companion browser extension

Runbook (build, load, env): `docs/extension.md`.

- **The extension never opens the database, and never could.** The store is SQLite in OPFS under the *app's* origin behind an exclusive SAH pool (one tab at a time, `BUSY_MESSAGE` in `src/lib/db/backend.ts`); an extension origin cannot reach it, and a second opener would lock the learner out of their own tab. So it bundles **no wasm core**, is **not a sync client**, and talks to an **open Sapling tab** over a bridge. Everything it knows about the learner's words is a cache of what that tab last answered.

- **`extension/` is its own build, like `embed/`** — a small Vite project (`extension/vite.config.ts`), output to the gitignored `extension/dist/`, typechecked by `tsc -p extension/tsconfig.json` inside `pnpm check`, its pure tests (`extension/*.test.ts`) in vitest's include. Each script is built **as one IIFE file per run** (`SAPLING_EXTENSION_ENTRY=background|bridge|page`; `pnpm extension:build` runs all three, the background run emptying `dist/` and emitting `manifest.json` and `public/`), because a content script and an injected script can be neither modules nor share a chunk. `$lib` is the app's source: the tokenizer (`$lib/reading/tokenize`), the romanizer registry (`$lib/romanize`, pinyin-pro inlined into `page.js` for Chinese), the sentence cut (`$lib/reading/pages`' `sentenceAt`) and the protocol are the app's own, never copies. Import those leaf modules by path, never `$lib/reading`'s or `$lib/db`'s index — those pull in the wasm core.

- **Firefox MV3 first.** Background is an event page (`background.scripts`), `browser_specific_settings.gecko.id` is `companion@sapling.vanoverloop.xyz`, minimum Firefox 140 (the Custom Highlight API). Chrome-portable where it costs nothing — `api` is `browser ?? chrome`, every listener answers through `sendResponse` + `return true`, `caretRangeFromPoint` backs `caretPositionFromPoint` — but there is no Chrome build (it would need `background.service_worker`). The WebExtension types are hand-written in `extension/webext.d.ts`, only what is called.

- **Origins are build-time.** `ORIGINS` in `extension/vite.config.ts` — `https://sapling.vanoverloop.xyz` and `http://localhost:5173` for `pnpm dev`; the manifest's `matches` and `host_permissions` are their **hosts without the port** (`http://localhost/*`), because Firefox matches no URL against a pattern with a port (`tabs.query({url})` and content scripts both came back empty), so the exact origin is checked in code: `__SAPLING_ORIGINS__`, which the bridge requires of `location.origin` before relaying, and the background requires of every sender and of the tabs it asks.

- **The bridge contract** (`src/lib/extension/protocol.ts`, pure and tested). Firefox has no `externally_connectable`, so `extension/bridge.ts` — a content script at `document_start` on the app's origins — relays between `runtime` messages and the page over `window.postMessage`. Every window message carries `EXTENSION_PROTOCOL` (`sapling/extension@1`: **bumped, never extended**) and a `to` (`app` | `extension`), because both ends hear every post in the window; both ends accept only `event.source === window` and `event.origin === location.origin`, post with the page's own origin as `targetOrigin`, and run `parseWindowMessage`, which refuses a request addressed to the side that does not answer it. Requests: **to the app** `{kind: 'terms'}` → `TermList` (the profile's target tag, its name, and every garden word as `{term, reading?, meaning?, status}`, status `new`/`learning`/`known` from `maturityOf`'s `new`/`young`/`solid`, then the legacy known marks as `known`; `listTerms`); **to the extension** `{kind: 'inbox'}` → `{entries}` and `{kind: 'remove', ids}` → `{removed}`. Replies and errors echo the request's `id`; the app also posts a `{notice: 'ready'}` when it installs. `src/lib/extension/bridge.ts` is the app's end, installed by the root layout once the database has opened, and it **reads through the repositories** (`getProfile`, `getAllItems`, `getKnownTerms`) — never SQL. An app ask that no extension answers in 1.5 s resolves `undefined`, which is how the inbox page knows there is no extension.

- **The background is the only writer of `storage.local`**: `terms` (the cached `TermList` + `fetchedAt`) and `inbox` (`InboxEntry[]`, writes serialised in one promise chain). The term list is refreshed whenever a Sapling tab is reachable — the app's `ready`, every toolbar press (the first matching tab that answers), and after every `remove`. **The inbox lives only in the extension**, never in Sapling's database: an entry is `{id, term, reading?, sentence, pageTitle, url, language, collectedAt}`, and collecting a word again on the same page (URL without fragment) replaces it (`addToInbox`).

- **The page script is injected on demand, never declared**: the toolbar press (`activeTab` + `scripting`) inserts `page.css` and runs `page.js` in the current tab; the next press toggles it off. It **never rewrites the page's DOM**: underlines are the **CSS Custom Highlight API** (`sapling-new`, `-learning`, `-known`, `-collected`, styled in `page.css`), one `Range` per word in a text node, and the only element added is the card's host, with the card in a closed shadow root. Text nodes are tokenized with the romanizer's `tokenize` for the cached language, else `tokenizeByTerms`, with every listed and collected term as terms so they stay whole; **only listed words are underlined** by status (homographs picked by the token's reading), collected-but-unlisted ones get `collected`; what to mark is `extension/highlight.ts`, DOM-free and tested. One `click` listener: `caretPositionFromPoint` → the character under the point → the token holding it; **any word is clickable**, links and form controls are left to the page. The card shows the term, its reading (the token's in context, else the stored one), and then the listed word's meaning and status, "In your inbox", or **Collect**; the sentence travels with it, cut by `sentenceAround` over the text of the nearest non-inline ancestor with layout whitespace collapsed. A `MutationObserver` re-scans added and changed subtrees after 250 ms. **With no Sapling tab reachable the cache is used and collecting still works** (it is local); an empty cache says so in the card.

- **`/words/inbox`** (linked as *Inbox* from the Garden's header, `BackLink` to `/words`) pulls the inbox over the bridge, shows the active language's entries grouped by page (`groupInbox`: latest page first, a page with no title named by its host) and counts the rest, and files words through **`$lib/ui/WordHarvest.svelte`** — the same tick / *Find meanings* (`glossWords` with each sentence) / editable meanings / *Add* (`addWords`) list `/read/[id]/words` uses. A successful add asks the extension to `remove` the filed entries, and the extension's next term refresh underlines them as garden words; each entry can also be dismissed. With no extension it explains what the inbox is instead of showing an empty list.
