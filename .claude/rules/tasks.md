# Background tasks

One lifecycle for every long job, and one tray to watch them from.

- `src/lib/tasks/` — **the runner owns every task; pages never hold task state.** A page calls `startTask(kind, input)` and is free to go: the runner (`runner.ts`, a factory the tests drive with fake kinds and a fake clock; `singleton.ts` makes the app's instance) owns the `AbortController`, the status (`queued` → `running` → `done` | `failed` | `cancelled`), the **step ledger** (`ctx.step(id, label)` closes the previous step and opens the next; settling closes the last) and the **progress fraction** (`ctx.progress(done, total, unit?)`), all in module state that outlives any component. Components read through `store.svelte.ts` (`taskStore.tasks`, `.running`, `.latestOf(kind)`), a `$state.raw` mirror fed by one subscription, so a page that navigates away and back finds the same ledger — a page that kept its own `generating` flag would be wrong the moment it was remounted. `startTask` returns `{ id, done }` and **`done` never rejects**: it resolves a `TaskOutcome` (`done` with the result, `failed` with the message, `cancelled`), so a fire-and-forget page is never the thing an unhandled rejection is reported against, and a page that stayed reads the result out of it. A page reacting to a task it may not have started (the learn screen re-planning after a top-up) keys an `$effect` on the store instead of holding the promise. **A page shows button state and one line of outcome, nothing more**: its control is disabled with a running label while its kind runs (one short "details in the task tray" phrase where the wait is long), and afterwards it shows the latest task's `summary` or `error` — no ledger, no progress bar, no counters, no elapsed time. Every detail is the tray's, once, rather than each page's own copy.
- **The registry is the membership list, and `TaskKind` is derived from it.** `registry.ts` maps a name to a def; `TaskKind = keyof TASK_KINDS`, so a def written in `kinds/` but not listed is not a kind — `startTask('its-name', …)` fails `pnpm check` at the call site — and `registry.test.ts` checks every listed def has `title`, `run`, `summary` and titles a fake input. A def (`TaskKindDef<I, R>`, `types.ts`) is `title(input)`, `run(input, ctx)`, `summary(result)`, `serial`, and optional `retryable` / `cancellable`. Its input must be **complete**: the runner keeps it for Retry, so a def cannot reach back into the page that started it. **Adding a kind** is one module in `kinds/` and one line in the registry.
- **Serial per kind, concurrent across kinds.** A `serial` kind runs one task at a time and later ones wait as `queued` (two top-ups would ask for the same wants twice; two annotations would trip one rate limit); different kinds run together. **Cancel is immediate**: the signal fires, the record settles as `cancelled` now, a queued same-kind task starts, and a result that arrives later is dropped. Whether the job actually stops is the job's business — `$lib/llm` unwinds at its fetch; the voice download does not listen, so `tts-model` says `cancellable: false` and the tray words its button "Stop watching". Failure mapping: an `AbortError` or an aborted signal is a cancellation; any other throw is `failed` with the error's own `message`, which every `LlmError` already writes for a human. At most `MAX_KEPT_TASKS` (20) settled tasks stay listed, oldest dropped first.
- **In memory only.** A reload loses every record, deliberately: a request that dies with the tab can only be re-run, and what a job produces lands through the ordinary repositories the moment it finishes — the pool (`top-up`), the text (`read-generate`, `read-annotate`, which now **own the save** the pages used to do afterwards, so a text lands whether or not anyone is watching), the readings (`readings`, local fill first, model second), the model cache (`tts-model`). Nothing is lost but the ledger.
- **Import direction.** `$lib/tasks` reaches down into `$lib/session`, `$lib/reading`, `$lib/llm`, `$lib/tts`, `$lib/db`; nothing in those layers may import `$lib/tasks`. The wrapped operations are unchanged — `generateChallenges`, `annotateReadingText`, `preloadKokoro` know nothing about tasks and keep their own `signal`/`onProgress` options, which is what the defs translate.
- **The tray** (`src/lib/ui/TaskTray.svelte`, mounted once in `+layout.svelte`) renders nothing until there is a task, then a pill at the foot of the viewport on the right — spinner and "N running", or a check / a cross once everything has settled — and, on tap, the list: a sheet at the foot of a phone, a 24rem card in the same corner at ≥48rem. A row is title, status, `TaskLedger` (`src/lib/ui/TaskLedger.svelte` — the step ledger, used only here; it owns the ticking clock, the runner only stamps) for a stepped task or `ProgressBar` for a counting one, then summary or error, then Cancel / Retry / Dismiss. It sits at `z-index: 25`: above the route sheets at 20 (the feedback banner, the reader's word card), below a modal overlay at 30. A focused screen may ask it to stay away with `taskStore.setHidden(true)` — the session screen does while a challenge is on the table — and must let it back on leaving.
