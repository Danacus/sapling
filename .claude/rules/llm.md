# LLM generation

Stateless: data in, data out, never touches the DB. Every model call runs in Rust (`crates/sapling-llm`, see `core.md`) on the window thread, reached through `callLlm` (`core.ts`); there is no TypeScript chat client. The tool-calling methods take a `ToolContext` in `CallOptions` (`assistant.md`); this layer only declares it and bridges it to wasm. `LlmError` (`core.ts`, its `kind` the generated `ErrorKind`) is the one error class out of it, rebuilt from the error JSON Rust rejects with; `usage.ts` meters the generated `TokenUsage` a live call answers with. Mock mode (`mock.ts`: no key, or `ll.mockMode`; `isMockForced` is the flag alone, for a screen that would otherwise say "add a key") sends no endpoint, and Rust answers with fixtures through the same parser and resolver as a live reply; node tests are always in mock mode.

## The seam

**The planner decides, this layer writes.** Wants come from `sapling-challenges`' top-up planner; `getBatch` hands them to Rust and returns challenges, failures and usage. Kinds, wire schemas, resolvers, length ranges and lesson specs are owned by each registered challenge plugin under `sapling-challenges/src/types/<type>/`; explicit ranks preserve seeded order. A `local` kind (`cue-cloze`) never reaches `getBatch`: the session builds it (`local.rs`), and this crate iterates `llm_kinds()` alone. `getEscalation` receives the exact served `ChallengeScreen`. Local romanization stays TypeScript; a `TargetText` reading is content the resolver carries into stored reading fields.

`getBatch` returns **challenges and nothing else**: a lesson is written *about* the vocabulary it is given and introduces none. New words enter through `add_words`.

## A top-up (`lesson.rs`)

- **One request per wire type**, at most `REQUEST_ITEMS` (6) distinct words each, spilling into another request of the same type; `REQUEST_CONCURRENCY` (3) in flight (`buffered`), results in request order, brief order within each. A second want of one type for one word is dropped: replies are matched back by the word cited.
- **Prompts are data.** A type's system prompt is `prompts/lesson.txt` with that type's `promptSpec`, `paramsSpec` and `rulesSpec` spliced in (plus `lesson-instruction.txt` where its struct has an `instruction`), static and memoised so a prefix cache pays. It names no other type. Its schema (`batch_schema`, `lesson_<type>`) admits only that type: `schemars` from the wire struct, inlined, every key required, `format` stripped.
- **Difficulty is one count.** Each item is `{id, t, m, <length key>: n}` — the want's `length` under the type's `length` key (`words`, or `tiles` for a word-order), plus a multi-cloze's `gaps` from that length (`kinds.rs`' `gaps_for`: 2 up to eleven words, 3 up to fifteen, then 4). The length is the top-up planner's (`sapling-challenges`' `topup.rs`: the middle of the kind's range), so no per-item level, no "difficulty" key, no accuracy dial reaches the model. `lesson.rs`' `fill_request` stamps each challenge with the `length` its want asked for (the stored union's additive field), because a row is judged at that length, not at the one the model produced. Banks, trays and hints are always written full; a help level (`sapling-challenges`' `serve.rs`) sizes what a served row shows.
- **Payload key order is load-bearing**: native, target, level, topic, about (capped at `MAX_ABOUT_CHARS`), known, then `items` — everything identical across a top-up's requests comes before the first byte that differs.
- **The level is derived, never asked.** `level_for(word_count)` (`lib.rs`) reads it off the size of the learner's library — under `ELEMENTARY_WORDS` (150) beginner, under `INTERMEDIATE_WORDS` (600) elementary, under `ADVANCED_WORDS` (2000) intermediate, else advanced — and every prompt that names a level uses it: a top-up counts `knownItems` (the whole collection), the chat and a conversation turn the `ToolContext`'s word list, and the four calls that lend no list — `generateReadingText`, `lookUpWord`, `startConversation`, `wordBatch` — take a `wordCount` the host counts (the garden's size, not the reader's `vocabulary`, which also carries legacy known marks). `LearnerProfile` is the languages and `about` only: the stored `Profile.level` and `Profile.interests` are deprecated, kept for older builds on other devices, and no prompt reads either.
- **Known words travel as terms**, qualified `term (reading)` only where two cards share a spelling; `term_index` maps a citation back (wanted words claim a bare spelling first). An id is accepted only for a wanted word.
- **A reply is checked against its brief, not counted.** Entries of another type are ignored; each resolved challenge must read back (`kind_of`) as the requested type and cite an unfilled want's word; it fills the first open want it cites, at that want's length. Fewer than half filled → one corrective retry (`lesson-corrective.txt`); the best partial reply is kept.
- **A request that still fails is dropped**, counted in `failedRequests`; only all of them failing is a `bad-response`. Auth, rate-limit and network errors end the top-up: nothing queued is sent, and requests already in flight finish but are discarded. An aborted signal rejects `fetch`, so it lands there too, and `callLlm` rethrows the signal's reason. An empty brief fails before any step.
- **Progress** is one step per id — `build-prompt`, `request` (naming the model and the request count), `retry` once, `validate` — sent through the wasm `progress` callback; `select-items` and `save` are the session's.
- **The mock** answers each request with that type's own fixtures, one per want, `{item}` bound to the want's word and `{other}` to another word the learner has (a multi-cloze with no second word fills nothing). Spanish or Mandarin by target language. Ids and shuffles are random in both modes.

## Plugin resolvers (`sapling-challenges`)

**The model emits content, never presentation.** Nine wire types on one primitive, `TargetText = {text, reading}` (reading null for Latin scripts); every field is either target-language or native, never conditionally. The resolver picks direction from the type, shuffles options and computes `correctIndex`, places the cloze blank between `before` and `after`, numbers multi-cloze gaps, shuffles tiles, swaps the spot-error word in, and derives `acceptedAnswers` (text, reading, both diacritic-folded). A reading appears only where every piece has one, and a cloze's reading never includes the answer's. It drops a challenge only for a structural defect (no resolvable citation, wrong option count, both sides in one no-space script, a position outside the sentence, a multi-cloze gap without its own word or chip); anything cosmetic is trimmed. **The stored shape is `sapling-challenges`' `Challenge` union** (`challenges.md`) — additive optional fields only: the resolver's output is parsed into it and must pass `check_shape`, or the challenge is dropped like any other structural defect, and `lesson.rs`' mock test resolves every kind in both scenarios through that gate and reads each back as its kind.

## A word grid (`word_batch.rs`)

`wordBatch` (`$lib/llm`'s wrapper of the same name) proposes words for "Check what you know" (`docs/word-check.md`): `{term, meaning, romanization?}`, the term in dictionary form, the meaning in the native language, the reading under the same rule as a lookup's (null for a Latin script, so absent). One static prompt (`prompts/word-batch.txt`) for both modes; the payload is native, target, level, mode, `step` (check: `start`/`harder`/`same`/`easier`, absent reads as `start`) or `topic` (starter, capped at `MAX_TOPIC_CHARS`), about, `count` (clamped to `MAX_BATCH_WORDS`, 40; a check grid asks for all 40) and last `exclude` — **every term the learner has or has been shown**, the whole library oldest first, then the run, then the words earlier calls for the same grid listed, newest last, in both modes; trimmed, blanks dropped, each term once at its last place (`term_key`), and the newest `MAX_EXCLUDE_WORDS` (2,000) kept. The prompt says never to list a word in it nor another form of one, and reads the check step against its last thirty or so words, so a run over a non-empty library opens at `same` relative to the latest-added terms. **Parsed leniently**: an entry without a term or a meaning, or repeating an earlier term's key, is dropped, not the batch; only no usable word at all is a `bad-response`. **`exclude` is a hint, never the filter**: the caller drops anything already in the library or already shown (`src/routes/explore/check/check.ts`, by `sameCard`) and fetches again, up to three calls, until the grid is full. Nothing is stored; the tapped words go through `addWords`. The mock is a fixed easiest-first list per script (`fixtures/word-batch-{es,zh}.json`) read as a window that starts after the last word of `exclude` it has, five ahead for `harder` and five back for `easier` (into words already shown, which is what exercises the caller's filter), a starter at an offset its topic picks.

## Escalation (`escalation.rs`)

The only mid-session spend, user-initiated. `prompts/escalation.txt` with the `escalationSpec`s spliced in (registry order), the stored challenge plus `shown`, `{answer, overturn}` in reply; anything else is prose and never an overturn. When `shown.nativeLine` is false the overturn rule relaxes to "correct for what was shown". The mock never overturns.

## The model list (`models.ts`)

The one call this layer makes itself, and it is no model call: `fetchModels(baseUrl, apiKey?)` reads `GET {baseUrl}/models` (blank is OpenRouter's, which needs no key; a key goes as Bearer when there is one) for `$lib/ui/ModelPicker.svelte`, the model field on onboarding and Settings. The endpoint and key are arguments, never read here. Parsed leniently — `data[].id`, plus OpenRouter's `name`, `context_length` and `pricing` when present — memoised one promise per endpoint for the page's lifetime, and **a failure is an empty list**, forgotten so the next call retries, never an error in the UI. There is no hardcoded model list anywhere: a typed id is always usable (`searchModels` offers it as itself when no listed id is exactly it, and the picker keeps it on blur), so an endpoint without `/models`, or no network, leaves a free-text field.

## Connect OpenRouter (`openrouter-auth.ts`)

An optional way to get a key, beside the key field on onboarding's model step and in Settings' "Language model" card, shown only while the endpoint is blank or OpenRouter's (`isOpenRouterEndpoint`) — such a key means nothing to another endpoint. The module is pure: a 32-byte base64url verifier (`randomToken`, also the `state`), its S256 `challengeFor`, `authUrl` (`key_label=Sapling`; no `callback_url` is OpenRouter's headless mode, which shows the code to paste), and `exchangeCode(code, verifier, fetchFn?)`, which POSTs to `/api/v1/auth/keys` and **never throws**: the key, or `expired` (403 — a used, mistyped or ten-minute-old code), `invalid` (any other refusal, or no key in the reply) or `network`. `$lib/ui/OpenRouterConnect.svelte` is the one UI and hands the key to an `onkey` callback; Settings saves it at once and onboarding sets its `apiKey`.

**A browser opens a popup; a Tauri host opens the system browser.** The popup is opened before the first `await`, so it still counts as the click's, and is pointed at `authUrl` with `callback_url` = `static/openrouter-callback.html` on the app's origin and a fresh `state`. That page answers over a `BroadcastChannel` (`CALLBACK_CHANNEL`), not `opener.postMessage`: a sign-in that passes through a provider with COOP severs `window.opener`, while a same-origin channel survives it, and only a message with the expected `state` is exchanged. A Tauri window (desktop and Android), whose origin no callback can reach, calls the host's `oauth_listen` for a loopback port, listens for `oauth://callback`, and opens `authUrl` with `callback_url=http://localhost:<port>/callback` through `@tauri-apps/plugin-opener` (`desktop.md`); the same `state` check and exchange follow. A blocked popup, or a Tauri host whose listen or open fails, takes the headless flow: a link to the auth page (opened through the plugin in Tauri) and a field for the code.

**Adding a wire type** means extending its owning plugin's wire shape, `type.json` and lesson file — the `add-challenge-type` skill has the procedure; `prompt-tuning` covers content changes.
