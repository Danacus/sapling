# LLM generation

The stateless half: data in, data out, never touches the DB.

- `src/lib/llm/` — **stateless**: data in, data out, never touches the DB. `getBatch` returns **challenges and nothing else**: a batch is written *about* the vocabulary it is handed and never introduces any, so the caller has only the pool to persist. New words enter the collection through `add_words` (`$lib/assistant`, `$lib/conversation`), never through a lesson. **The known list travels as terms and is cited by term** — the ids stay local so the prompt stays cheap — and a term that names two cards travels *qualified*, `term (reading)`, rendered by `knownTermLabels` and indexed under that exact string by `knownTermIndex`, so a challenge citing `长 (zhǎng)` resolves onto that card. Unambiguous terms stay bare, so nothing about prompt size changes for a learner with no homographs; a *bare* citation of an ambiguous term resolves to the first-indexed card, deliberately, since a challenge that did not say which reading it meant only vaguely fits either and dropping a paid-for challenge costs more than the credit landing on the sibling. The OpenRouter client takes an injectable `fetch` — all LLM tests run against fakes, no network. The client also speaks OpenAI-style tool calling (`tools` option, `ChatMessage` union with assistant `toolCalls` and `tool` result messages, `toolCalls` on the result) — used by `$lib/assistant`, invisible to callers that don't pass tools.

## Token economy (the core design)

Generating a lesson (`src/lib/llm/generate.ts`) is a **handful of short, concurrent, single-type requests**, not one long completion. Everything needed to grade locally comes back with it: exhaustive `acceptedAnswers`, distractors, romanization variants. Play-time grading is free (`src/lib/validate` fuzzy matching + `src/lib/srs` FSRS). The only mid-session spend is the user-initiated *Explain/dispute* escalation (`src/lib/llm/escalation.ts`), which can genuinely overturn a "wrong" grade via its structured `{answer, overturn}` reply. `match-pairs` challenges are assembled locally at zero cost — and sized off the same ladder the paid types are: `makeMatchPairsChallenge(items, rng, {difficulty})` maps a rung to a pair count through `MATCH_PAIRS_LADDER` (3,4,5,6,6 — inside `match-pairs`' own stored `FEWEST_PAIRS` 2 / `MOST_PAIRS` 6 scale, so two top rungs do not peg to the same stored difficulty), declining only below the ladder's floor of three collision-free items and building the *smaller* round between that floor and the rung's count. With no `difficulty` it is the four-or-five random draw it always was, floor and all, so a caller with no vocabulary strength to read sees no change. Mock mode (no API key, or `ll.mockMode`) routes deterministic fixtures through the *real* parse/resolve path — the whole app is developable without spending tokens, and node tests are always in mock mode. The mock ignores the plan on purpose (as it ignores `level` and the difficulty rung): its job is to show every wire type at once, so it stays one synchronous, byte-identical assembly and keeps passing the *union* schema to `parseBatch`.

## Per-type generation (`slots.ts` + `generate.ts`)

**The plan is local; the model only fills it.** `planSlots` (`src/lib/llm/slots.ts`, pure, injectable `rng`) turns `BatchArgs` into an explicit list of slots `{itemId, term, type, difficulty, bank?}` — one per challenge. Every type-selection rule that used to be prose in the prompt lives there instead: the ladder floors (level 1 → recognition only; 2-3 add `word-order` and **banked** cloze; 4-5 add `translate-to-target` and bankless cloze — the same floors `difficultyLevelOf` gates *serving* on, read here at the old three-bucket resolution), the recognition/production mix, the `recentAccuracy` dial (`productionShare`: linear from 0.2 at ≤0.7 to 0.6 at ≥0.85, continuous rather than stepped), the extra slot a `recentMistakes` term earns in a format it has not had, and `'(skipped)'` → recognition. A cloze's word bank is a **type-level** decision and travels as `bank: true|false`; a banked cloze is **production, not recognition** — it reports demand 1 with a bank on the stored side, so planning one for a level-1 word would write a challenge the session planner then declines to serve for weeks. Two things bound a plan besides `count`: `MAX_BATCH_CHALLENGES`, and one slot per *distinct kind a word's level allows* (four at level 1, six at 2-3, eight at 4-5) — one review word and a count of fourteen comes back as eight slots, not as a second lap through the same eight questions. The production share is charged only against the slots that could ever be production, so four new words beside two mature ones no longer hands the mature two a 100%-production lesson. `PLANNABLE_KINDS` is the membership list that matters — a wire type in the registry but not there is prompted, exampled and never asked for, and `challenge-types/registry.test.ts` fails on it.

**Freshness for a word is absolute, and a lesson opens few kinds.** `pickKind` never gives one word the same kind twice: when the group it was dealt (recognition or production) is exhausted for that word it crosses to the other rather than repeating a format — which is what makes `capacityOf`'s count of *distinct* kinds the real ceiling, and what lets a request be a flat list of words with no duplicates in it. A `recognitionOnly` slot never crosses into production, since the skip it answers said that format was too much. Above that, once a lesson holds `MAX_LESSON_KINDS` (4) distinct kinds, `pickKind` prefers a kind already open — a kind *is* a request, so the number of kinds a plan names is the number of round trips it costs, and a twenty-challenge lesson that touched all eight paid eight prompts to ask two or three questions each. It lands at four or five requests of four to six now. Below the cap the picker is the old one (fresh for the word, drawn at random), so which kinds a lesson opens still varies between lessons.

`groupIntoRequests` then cuts the plan **by kind**: one request per `(type, bank)`, at most `REQUEST_ITEMS` (6) challenges each, a kind with more spilling into a second request of the same kind. Every entry keeps its `index` in the plan. `generateBatch` runs them with `REQUEST_CONCURRENCY` (3) in flight. **One request is one wire type**: its system prompt (`systemPromptFor(def)`, memoised, still a static string per type) explains that type and no other, its JSON schema (`batchJsonSchemaFor(def)`, named `lesson_<type>`) admits that type and no other, and its corrective retry (`correctiveInstructionFor(def)`) restates that type's required fields and no other. The model never sees the word "slot", a `difficulty` from 1 to 5, or the six types it is not writing — a saving that more than pays for the split, since a request used to carry all seven types' field lists, examples and rules to ask for four challenges of one of them. The prompt's shared preamble is only what names no type at all (JSON-only, the envelope, the `TargetText` reading rule, the `itemIds`/known citation rules, sides-never-swap, plausible wrong options, answerability, voice, `explanation`, "known is what you build with"), plus the `instruction` heading rule where the type has that field — decided by reading the def's own schema shape, so a type that grows one gets the rule. Anything narrower lives in the def's `rulesSpec`, **including a rule a second type also needs**: segmentation is spelled out in full in both `word-order` and `spot-error`, because a duplicated line only ever travels on its own type's calls.

The user payload's **key order is load-bearing**: everything identical across the lesson's requests first (profile, `topic`, `about`, then the whole `known` list, by far the largest block), and only then `items` — a prefix cache pays up to the first byte that differs. An entry is `{id, t, m, ...params}`. What no longer travels at all: `reviewItems` (the words *are* the brief), `slots`, `type`, `difficulty`, `level`, `recentAccuracy`, and **`recentMistakes`** — a just-missed word already earns an extra slot in a fresh format and a rung off every slot about it, and "write this one easier" on top of a length that already says how long to write it was two instructions for one decision. Each request carries its own corrective retry, fired when it fills fewer than half its entries.

**Difficulty travels as countable parameters, never as a rung.** Each wire def has `params(difficulty, kind)` — pure, monotone in the rung per key — and a one-line `paramsSpec` naming exactly those keys; `registry.test.ts` pins both, checks the ladders are monotone (lengths never fall, a word bank never grows), and checks a challenge shaped at rung 1 scores a lower stored `difficultyOf` than one shaped at rung 5. The ladders are aligned with the stored side's own scales (`primitives.ts`' 1..12-word `lengthKnob`, cloze's `SMALLEST_BANK` 3 / `LARGEST_BANK` 6, `MAX_WORD_ORDER_TILES`): `recognize-mc`/`produce-mc` `words` 1,3,5,8,11; the two translate types `words` 2,4,6,8,11; `cloze` `words` 3,5,7,9,11 and `bank` 6,5,4,3,3 (the answer counted in, so `distractorWords` gets `bank-1` — exactly the schema's 2-5) or 0 when the plan asked for a typed cloze; `word-order` `tiles` 3,4,5,7,8 and `distractors` 0,0,1,2,3; `spot-error` `words` 3,5,7,9,11. The rung itself is still planned exactly as before — the item's `level`, shifted by `accuracyShift` (-1 below `ACCURACY_FLOOR` 0.7, +1 at or above `ACCURACY_CEILING` 0.85, one band read two ways: continuously for the production *share*, in whole rungs for the difficulty) and pulled down one where `recentMistakes` says so, a wrong answer moving every slot about the word and a `'(skipped)'` only the recognition-only extra it earned. **Where the resolver can enforce a parameter, it does**: `ResolveContext.params` is optional and `ResolveOptions.paramsByItem` keys it by item (a word appears at most once in a request, so the first resolved id that map knows is unambiguously the entry a challenge answers); cloze trims its bank to `bank` entries and treats `bank: 0` as "typed", discarding distractors sent anyway, and word-order caps its distractors at `distractors`. With no params — the mock, a bare `resolveBatch` — every resolver behaves exactly as it did before. What stays prose is the judgement no number expresses: how close a distractor should sit, how subtle a planted error should be, stated once per def with no rung attached.

**A request's reply is checked against its brief, not counted.** A reply of the right length can be the wrong lesson — six banked clozes answered as six multiple-choice questions, or one word given all six — and counting cannot see either. So `parseBatch(raw, def.schema)` validates each entry against *this request's* member schema (the union default is the mock's), and `fillRequest` matches the resolved challenges against the entries: the stored `{type, direction}` the def declares (that is what tells `recognize-mc` from `produce-mc`, and the two translate types apart), `bank` against the word bank that survived resolution, and the challenge must cite that entry's own item. Each entry is filled at most once, so **a request can never return more than it was asked for** — an over-producing one used to push the later ones out of the `MAX_BATCH_CHALLENGES` slice. Whatever matches nothing is dropped rather than kept as a bonus: the retry re-asks for the real one, and a lesson padded with what the model felt like writing is exactly what this design exists to stop.

**The merge is in plan order** — not request order, and certainly not completion order. Every filled entry carries its plan `index` and the lesson is sorted by it at the end. This is the guarantee grouping by type puts at risk: a plan is a round-robin over the lesson's words, and letting the transport decision reach the learner would serve them every cloze in a row.

**A request that fails is dropped, not fatal.** Four fifths of a lesson is a lesson: the merged total has to clear `MIN_BATCH_CHALLENGES`, and only then does `generateBatch` throw `LlmError('bad-response')` — with a message saying how much survived and how many requests failed, counting one as failed only when *nothing* of it was merged (one whose best partial reply was kept is in the lesson, not a casualty). Only `bad-response` is droppable; auth, rate-limit, network and abort sink the lesson **immediately and literally**: a shared `fatal` plus an internal `AbortController` chained off the caller's signal, so the first fatal failure cancels the siblings still in flight and every request the pool has not dispatched returns without a call — a five-request lesson on a rate-limited key costs `REQUEST_CONCURRENCY` requests, not five. A lesson with no review items to write about throws before any progress step and says so, rather than announcing a `request` and then blaming the model for a call nobody made. `usage` sums across every call including retries. Progress stays **one step per id** however many requests there are: `request` (labelled with the number in flight), `retry` the first time any is re-asked, `validate` once they have all settled — the learn screen times each step from its event to the next, so a step per request would be a flicker rather than a timeline.

**The model emits content, never presentation.** The generation wire format (`src/lib/llm/schemas.ts`) is seven direction-specific types (`recognize-mc`, `produce-mc`, `cloze`, `translate-to-target`, `translate-to-native`, `word-order`, `spot-error`) built on one primitive, `TargetText = {text, reading}` — target-language text carrying its own Latin reading, `reading: null` for Latin scripts. Every slot is unconditionally either a `TargetText` or a native string, so no field's language depends on a flag. `resolveBatch` then assembles the stored `Challenge`: it picks `direction` from the type, shuffles the options and computes `correctIndex` (injectable `rng`), joins `before + '___' + after` for cloze, and derives diacritic-folded `acceptedAnswers`. Whole bug classes — answer-spoiling romanizations, misaligned readings, correct-answer-always-in-slot-A — are unexpressible rather than guarded against.

There is no single `SYSTEM_PROMPT` any more. `systemPromptFor(def)` composes one per wire type — memoised, and still a **static string per type**, which is what keeps prompt caching paying across a lesson's requests of one kind and across sessions. It carries load-bearing rule blocks (voice/anti-blandness, the one-line `TargetText` reading rule, answerability, `explanation`), and it does **not** say which type to write, which accuracy band the lesson is in, or how hard on any scale: type choice is `slots.ts`'s job, the type is the whole subject of the prompt, and difficulty is the parameters on each item. Its counterpart rule is "one `<type>` challenge per entry in `items`, in the same order, about that entry's word, at the size that entry gives", plus "treat every size as a target to hit, not a maximum". Prompt edits are the fix of first resort for content-quality bugs; `resolveBatch` degrades cosmetic defects silently (a partial reading is dropped, never the challenge) and drops only structural failures.

All per-wire-type knowledge lives in `src/lib/llm/challenge-types/` — one module per type bundling its zod `schema`, `stored` (the `{type, direction}` its resolver always writes, which is what lets `generate.ts` check a reply against the brief it asked for — pinned against the def's own fixtures in `registry.test.ts`), `promptSpec` (its field list and example), `params` + `paramsSpec` (how hard a copy of it is written, as counts), `correctiveSpec` (retry fragment), `resolve` function, `fixtures` (its canned examples per mock scenario, ordered by `order` so the assembled practice lesson keeps lesson order rather than registry order), and optional `rulesSpec` / `escalationSpec`. The ordered `WIRE_TYPE_DEFS` registry in `challenge-types/index.ts` is then the single source of membership: `generatedChallengeSchema` is *projected* from it (`SchemasOf`, a tuple-preserving mapped type — `.map()` would widen the members and defeat zod's inference), `generate.ts` composes each type's own prompt, schema and corrective retry from it and dispatches `resolveBatch` from it, `escalation.ts` composes its stored-shape gloss sentence from the `escalationSpec`s, and `mock.ts` assembles both scenario batches from the `fixtures` (each of which cites its subject **by term** — a scenario cannot know the learner's ids, so `mock.ts` binds those terms onto the review items it was handed, and with no review items the canned half resolves to nothing, exactly as the paid path does). Registry order is union order and escalation-gloss order; it is no longer prompt order, since no prompt lists more than one type. Import direction is strictly `primitives.ts` (shared zod pieces) ← def modules ← `index.ts` ← `schemas.ts` ← `generate.ts`; **def modules must never import `schemas.ts`**, which is now only a re-exporting façade for both halves of the union (the one-array `generatedBatchSchema`/`looseBatchSchema` envelope, `batchJsonSchemaFor()`/`batchSchemaNameFor()` and the composed `challengeSchema` are still written there; the stored-side members come from `$lib/challenges/types`). A def sizes itself by `DifficultyRung` and `SizingKind` declared in `def.ts`, not by importing `slots.ts` — `slots.ts` names wire types, so the arrow has to point that way, and `SlotDifficulty` is an alias of `DifficultyRung`. Defs use `satisfies WireTypeDef<T>` rather than a type annotation so each keeps its precise schema type — hence `OptionalSpecs`, intersected in by `index.ts` so `rulesSpec`/`escalationSpec` stay readable across the union. **Adding a wire type** is three edits (def module + registration + a `SlotKind` in `slots.ts`) — the `add-challenge-type` skill has the procedure and the failure modes.
