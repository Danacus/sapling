# LLM generation

The stateless half: data in, data out, never touches the DB.

- `src/lib/llm/` — **stateless**: data in, data out, never touches the DB. `getBatch` returns **challenges and nothing else**: a batch is written *about* the vocabulary it is handed and never introduces any, so the caller has only the pool to persist. New words enter the collection through `add_words` (`$lib/assistant`, `$lib/conversation`), never through a lesson. **The known list travels as terms and is cited by term** — the ids stay local so the prompt stays cheap — and a term that names two cards travels *qualified*, `term (reading)`, rendered by `knownTermLabels` and indexed under that exact string by `knownTermIndex`, so a challenge citing `长 (zhǎng)` resolves onto that card. Unambiguous terms stay bare, so nothing about prompt size changes for a learner with no homographs; a *bare* citation of an ambiguous term resolves to the first-indexed card, deliberately, since a challenge that did not say which reading it meant only vaguely fits either and dropping a paid-for challenge costs more than the credit landing on the sibling. The OpenRouter client takes an injectable `fetch` — all LLM tests run against fakes, no network. The client also speaks OpenAI-style tool calling (`tools` option, `ChatMessage` union with assistant `toolCalls` and `tool` result messages, `toolCalls` on the result) — used by `$lib/assistant`, invisible to callers that don't pass tools.

## Token economy (the core design)

Generating a lesson (`src/lib/llm/generate.ts`) is a **handful of short, concurrent, slot-scoped requests**, not one long completion. Everything needed to grade locally comes back with it: exhaustive `acceptedAnswers`, distractors, romanization variants. Play-time grading is free (`src/lib/validate` fuzzy matching + `src/lib/srs` FSRS). The only mid-session spend is the user-initiated *Explain/dispute* escalation (`src/lib/llm/escalation.ts`), which can genuinely overturn a "wrong" grade via its structured `{answer, overturn}` reply. `match-pairs` challenges are assembled locally at zero cost. Mock mode (no API key, or `ll.mockMode`) routes deterministic fixtures through the *real* parse/resolve path — the whole app is developable without spending tokens, and node tests are always in mock mode. The mock ignores the slot plan on purpose (as it ignores `level` and `difficulty`): its job is to show every wire type at once, so it stays one synchronous, byte-identical assembly.

## Chunked generation (`slots.ts` + `generate.ts`)

**The plan is local; the model only fills it.** `planSlots` (`src/lib/llm/slots.ts`, pure, injectable `rng`) turns `BatchArgs` into an explicit list of slots `{itemId, term, type, difficulty, bank?}` — one per challenge. Every type-selection rule that used to be prose in the prompt lives there instead: the ladder floors (level 1 → recognition only; 2-3 add `word-order`; 4-5 add `translate-to-target` and bankless cloze — the same floors `difficultyLevelOf` gates *serving* on, read here at the old three-bucket resolution), the recognition/production mix, the `recentAccuracy` dial (`productionShare`: linear from 0.2 at ≤0.7 to 0.6 at ≥0.85, continuous rather than stepped), the extra slot a `recentMistakes` term earns in a format it has not had, and `'(skipped)'` → recognition. A cloze's word bank is a **type-level** decision and travels as `bank: true|false`. `PLANNABLE_KINDS` is the membership list that matters — a wire type in the registry but not there is prompted, exampled and never asked for, and `challenge-types/registry.test.ts` fails on it.

`chunkSlots` then cuts the plan into requests of at most `CHUNK_SLOTS` (5) slots about at most `CHUNK_ITEMS` (3) review items, **grouping by word** so a word's slots stay in one brief (only a word that alone outgrows a chunk is split). `generateBatch` runs the chunks with `CHUNK_CONCURRENCY` (3) in flight, each with the **same static `SYSTEM_PROMPT`** — that is what keeps prompt caching paying across chunks — and a short user payload (profile/topic/about/known, the chunk's `reviewItems`, its `slots`, and only the `recentMistakes` that name one of its words; neither `level` nor `recentAccuracy` travels at all — both only ever fed local decisions). Each chunk carries its own corrective retry, fired when fewer than half its slots come back usable.

**Difficulty is a continuous per-slot number now, not a prompt-wide cliff.** Every slot carries `difficulty` (1..5, same axis as `$lib/session/progression`'s five-rung `DifficultyLevel`): `planSlots` starts from the item's own `level`, applies a whole-lesson `accuracyShift` (-1/0/+1, linear between the same two bounds `productionShare` reads — the old "below 0.7"/"above 0.85" prompt cliffs, made local and continuous) and pulls every slot about a word named in `recentMistakes` down one rung, whether or not it was `'(skipped)'` — not only the extra slot that word earns. `SYSTEM_PROMPT`'s `Difficulty calibration:` block is one shared ladder line (`"difficulty" 1-5 on each slot, 1 easiest`) plus the still-content-only "write it EASIER than last time" rule for `recentMistakes`; *how* to realize a level is per type — each wire def's own `rulesSpec` states its gradient in observable, countable terms only (shown-text length, tile count, bank size, sentence length, distractor closeness — never `instruction` presence, which is a heading, not scaffolding).

**A chunk that fails is dropped, not fatal.** Four fifths of a lesson is a lesson: the merged total has to clear `MIN_BATCH_CHALLENGES`, and only then does `generateBatch` throw `LlmError('bad-response')` — with a message saying how much survived and how many requests failed. Only `bad-response` is droppable; auth, rate-limit, network and abort sink the lesson immediately, since every other chunk would hit the same wall. `usage` sums across every call including retries, and the merge follows **chunk-then-slot order, never completion order**. Progress stays **one step per id** however many chunks there are: `request` (labelled with the number in flight), `retry` the first time any chunk is re-asked, `validate` once they have all settled — the learn screen times each step from its event to the next, so a step per chunk would be a flicker rather than a timeline.

**The model emits content, never presentation.** The generation wire format (`src/lib/llm/schemas.ts`) is seven direction-specific types (`recognize-mc`, `produce-mc`, `cloze`, `translate-to-target`, `translate-to-native`, `word-order`, `spot-error`) built on one primitive, `TargetText = {text, reading}` — target-language text carrying its own Latin reading, `reading: null` for Latin scripts. Every slot is unconditionally either a `TargetText` or a native string, so no field's language depends on a flag. `resolveBatch` then assembles the stored `Challenge`: it picks `direction` from the type, shuffles the options and computes `correctIndex` (injectable `rng`), joins `before + '___' + after` for cloze, and derives diacritic-folded `acceptedAnswers`. Whole bug classes — answer-spoiling romanizations, misaligned readings, correct-answer-always-in-slot-A — are unexpressible rather than guarded against.

The `SYSTEM_PROMPT` in `generate.ts` is deliberately token-budgeted and static (prompt-cache friendly) — and must stay a static string, now that every chunk of every lesson quotes it. It carries load-bearing rule blocks (voice/anti-blandness, the one-line `TargetText` reading rule, answerability, and difficulty calibration from each slot's own `difficulty` plus `recentMistakes` — which calibrates *content*: answer length, sentence difficulty, "easier than last time"). It does **not** say which type to write, or which accuracy band the lesson is in: both are `slots.ts`'s job now, and the prompt's counterpart is two rules ("one challenge object per slot, in the same order, of that slot's type" and the one shared difficulty-ladder line — every type-specific *how* lives in that type's own `rulesSpec`). Prompt edits are the fix of first resort for content-quality bugs; `resolveBatch` degrades cosmetic defects silently (a partial reading is dropped, never the challenge) and drops only structural failures.

All per-wire-type knowledge lives in `src/lib/llm/challenge-types/` — one module per type bundling its zod `schema`, `promptSpec` (its `Types:` line), `correctiveSpec` (retry fragment), `resolve` function, `fixtures` (its canned examples per mock scenario, ordered by `order` so the assembled practice lesson keeps lesson order rather than registry order), and optional `rulesSpec` / `escalationSpec`. The ordered `WIRE_TYPE_DEFS` registry in `challenge-types/index.ts` is then the single source of membership: `generatedChallengeSchema` is *projected* from it (`SchemasOf`, a tuple-preserving mapped type — `.map()` would widen the members and defeat zod's inference), `generate.ts` composes `SYSTEM_PROMPT`'s `Types:` block and `CORRECTIVE_INSTRUCTION` and dispatches `resolveBatch` from it, `escalation.ts` composes its stored-shape gloss sentence from the `escalationSpec`s, and `mock.ts` assembles both scenario batches from the `fixtures` (each of which cites its subject **by term** — a scenario cannot know the learner's ids, so `mock.ts` binds those terms onto the review items it was handed, and with no review items the canned half resolves to nothing, exactly as the paid path does). Order = prompt order = union order; the composed prompts are still static strings, so nothing about prompt caching changes. Import direction is strictly `primitives.ts` (shared zod pieces) ← def modules ← `index.ts` ← `schemas.ts` ← `generate.ts`; **def modules must never import `schemas.ts`**, which is now only a re-exporting façade for both halves of the union (the one-array `generatedBatchSchema`/`looseBatchSchema` envelope, `batchJsonSchema()` and the composed `challengeSchema` are still written there; the stored-side members come from `$lib/challenges/types`). Defs use `satisfies WireTypeDef<T>` rather than a type annotation so each keeps its precise schema type — hence `OptionalSpecs`, intersected in by `index.ts` so `rulesSpec`/`escalationSpec` stay readable across the union. **Adding a wire type** is three edits (def module + registration + a `SlotKind` in `slots.ts`) — the `add-challenge-type` skill has the procedure and the failure modes. The only hand-edited cross-type prompt text left is `generate.ts`'s `Rules:` block (the slot rule, segmentation, sides-never-swap, content calibration) — rules that by definition name more than one type.
