# LLM generation

The stateless half: data in, data out, never touches the DB.

- `src/lib/llm/` — **stateless**: data in, data out, never touches the DB. `getBatch` returns **challenges and nothing else**: a batch is written *about* the vocabulary it is handed and never introduces any, so the caller has only the pool to persist. New words enter the collection through `add_words` (`$lib/assistant`, `$lib/conversation`), never through a lesson. **The known list travels as terms and is cited by term** — the ids stay local so the prompt stays cheap — and a term that names two cards travels *qualified*, `term (reading)`, rendered by `knownTermLabels` and indexed under that exact string by `knownTermIndex`, so a challenge citing `长 (zhǎng)` resolves onto that card. Unambiguous terms stay bare, so nothing about prompt size changes for a learner with no homographs; a *bare* citation of an ambiguous term resolves to the first-indexed card, deliberately, since a challenge that did not say which reading it meant only vaguely fits either and dropping a paid-for challenge costs more than the credit landing on the sibling. The OpenRouter client takes an injectable `fetch` — all LLM tests run against fakes, no network. The client also speaks OpenAI-style tool calling (`tools` option, `ChatMessage` union with assistant `toolCalls` and `tool` result messages, `toolCalls` on the result) — used by `$lib/assistant`, invisible to callers that don't pass tools.

## Token economy (the core design)

Generating a lesson (`src/lib/llm/generate.ts`) is a **handful of short, concurrent, single-type requests**, not one long completion. Everything needed to grade locally comes back with it: exhaustive `acceptedAnswers`, distractors, romanization variants. Play-time grading is free (`src/lib/validate` fuzzy matching + `src/lib/srs` FSRS). The only mid-session spend is the user-initiated *Explain/dispute* escalation (`src/lib/llm/escalation.ts`), which can genuinely overturn a "wrong" grade via its structured `{answer, overturn}` reply. `match-pairs` challenges are assembled locally at zero cost — and sized off the same ladder the paid types are: `makeMatchPairsChallenge(items, rng, {difficulty})` maps a rung to a pair count through `MATCH_PAIRS_LADDER` (3,4,5,6,6 — inside `match-pairs`' own stored `FEWEST_PAIRS` 2 / `MOST_PAIRS` 6 scale, so two top rungs do not peg to the same stored difficulty), declining only below the ladder's floor of three collision-free items and building the *smaller* round between that floor and the rung's count. With no `difficulty` it is a four-or-five random draw with a floor of four. Mock mode (no API key, or `ll.mockMode`) routes deterministic fixtures through the *real* parse/resolve path — the whole app is developable without spending tokens, and node tests are always in mock mode. The mock ignores the wants' kinds and rungs on purpose: its job is to show every wire type at once, so it stays one synchronous, byte-identical assembly and keeps passing the *union* schema to `parseBatch`.

## Per-type generation (`requests.ts` + `generate.ts`)

**This layer plans nothing.** `BatchArgs` is `{profile, wants, knownItems?, topic?}`, and `wants` is the whole brief: a list of `{item: {id, term, meaning}, kind, difficulty}`, one per challenge to write, decided by the session against what its pool already holds (`$lib/session/topup` — see `session.md`). Nothing about how the learner has been doing travels in: no `recentAccuracy`, no `recentMistakes`, no `count`, no `level`. A missed word's strength has already fallen, so its rung — and so every size computed from it — fell with it. `requests.ts` is what this layer knows about kinds: a `ChallengeKind` is a wire type plus, for cloze, whether a word bank is wanted (`bank: true|false` — two exercises for two stages of a word, decided by whoever asks and told to the model, never guessed); `PLANNABLE_KINDS` lists every kind the session may ask for **with the stored demand tier its resolved challenge reports** (0 recognition, 1 constrained, 2 free — a banked cloze is 1, a bankless one 2, which is why cloze appears twice), so the session can gate a want on a word's bearable tier without building a challenge; `kindKey` is a kind's identity; `kindOf(challenge)` reads a stored row back as the kind it *is* (stored `{type, direction}` from each def's `stored`, plus whether a bank survived) — the session counts pool coverage with it and `generate.ts` checks a reply with it. `challenge-types/registry.test.ts` pins `PLANNABLE_KINDS` against the registry (a wire type no kind names is one the model could be told about and never asked for) and pins every kind's `demand` and its `kindOf` round trip against that def's own resolved fixtures.

`groupIntoRequests(wants)` cuts the list **by kind**: one request per `(type, bank)`, at most `REQUEST_ITEMS` (6) wants each, a kind with more spilling into a second request of the same kind, in first-appearance order. A second want of the same kind for the same word is dropped there rather than asked for — a reply is matched back to its brief by the word each challenge cites, so it could never be told from the first. `generateBatch` runs the requests with `REQUEST_CONCURRENCY` (3) in flight. **One request is one wire type**: its system prompt (`systemPromptFor(def)`, memoised, still a static string per type) explains that type and no other, its JSON schema (`batchJsonSchemaFor(def)`, named `lesson_<type>`) admits that type and no other, and its corrective retry (`correctiveInstructionFor(def)`) restates that type's required fields and no other. The model never sees the word "want", a `difficulty` from 1 to 5, or the six types it is not writing. The prompt's shared preamble is only what names no type at all (JSON-only, the envelope, the `TargetText` reading rule, the `itemIds`/known citation rules, sides-never-swap, plausible wrong options, answerability, voice, `explanation`, "known is what you build with"), plus the `instruction` heading rule where the type has that field — decided by reading the def's own schema shape, so a type that grows one gets the rule. Anything narrower lives in the def's `rulesSpec`, **including a rule a second type also needs**: segmentation is spelled out in full in both `word-order` and `spot-error`, because a duplicated line only ever travels on its own type's calls.

The user payload's **key order is load-bearing**: everything identical across the top-up's requests first (profile, `topic`, `about`, then the whole `known` list, by far the largest block), and only then `items` — a prefix cache pays up to the first byte that differs. An entry is `{id, t, m, ...params}`: the want's word and meaning beside its id, and this type's parameters for the want's rung. Each request carries its own corrective retry, fired when it fills fewer than half its entries.

**Difficulty travels as countable parameters, never as a rung.** Each wire def has `params(difficulty, kind)` — pure, monotone in the rung per key — and a one-line `paramsSpec` naming exactly those keys; `registry.test.ts` pins both, checks the ladders are monotone (lengths never fall, a word bank never grows), and checks a challenge shaped at rung 1 scores a lower stored `difficultyOf` than one shaped at rung 5. The ladders are aligned with the stored side's own scales (`primitives.ts`' 1..12-word `lengthKnob`, cloze's `SMALLEST_BANK` 3 / `LARGEST_BANK` 6, `MAX_WORD_ORDER_TILES`): `recognize-mc`/`produce-mc` `words` 1,3,5,8,11; the two translate types `words` 2,4,6,8,11; `cloze` `words` 3,5,7,9,11 and `bank` 6,5,4,3,3 (the answer counted in, so `distractorWords` gets `bank-1` — exactly the schema's 2-5) or 0 when the want asked for a typed cloze; `word-order` `tiles` 3,4,5,7,8 and `distractors` 0,0,1,2,3; `spot-error` `words` 3,5,7,9,11. The rung itself is the word's `difficultyLevelOf`, unshifted — the session writes it onto the want. **Where the resolver can enforce a parameter, it does**: `ResolveContext.params` is optional and `ResolveOptions.paramsByItem` keys it by item (a word appears at most once in a request, so the first resolved id that map knows is unambiguously the entry a challenge answers); cloze trims its bank to `bank` entries and treats `bank: 0` as "typed", discarding distractors sent anyway, and word-order caps its distractors at `distractors`. With no params — the mock, a bare `resolveBatch` — nothing is enforced. What stays prose is the judgement no number expresses: how close a distractor should sit, how subtle a planted error should be, stated once per def with no rung attached.

**A request's reply is checked against its brief, not counted.** A reply of the right length can be the wrong thing — six banked clozes answered as six multiple-choice questions, or one word given all six — and counting cannot see either. So `parseBatch(raw, def.schema)` validates each entry against *this request's* member schema (the union default is the mock's), and `fillRequest` reads each resolved challenge back through `kindOf` (which is what tells `recognize-mc` from `produce-mc`, the two translate types apart, and a banked cloze from one whose bank did not survive resolution) and requires it to cite that entry's own word. Each entry is filled at most once, so **a request can never return more than it was asked for**. Whatever matches nothing is dropped rather than kept as a bonus: the retry re-asks for the real one, and a pool padded with what the model felt like writing is exactly what this design exists to stop.

**The result is in request order**, brief order within each — never completion order (`runPooled` returns outcomes in job order whatever order they settled). The pool it is written into has no order of its own to preserve; the session plans what to play out of the whole of it.

**A request that fails is dropped, not fatal, and the result says so.** Its wants are simply still wanting — the next top-up asks for them again — so `BatchResult.failedRequests` counts the requests that contributed nothing even after their retry (one whose best partial reply was kept is not a casualty), and only when *nothing* came back does `generateBatch` throw `LlmError('bad-response')`, with a message saying how many requests failed. There is no minimum to clear: one want filled is one challenge the pool did not have. Only `bad-response` is droppable; auth, rate-limit, network and abort sink the top-up **immediately and literally**: a shared `fatal` plus an internal `AbortController` chained off the caller's signal, so the first fatal failure cancels the siblings still in flight and every request the pool has not dispatched returns without a call — a five-request top-up on a rate-limited key costs `REQUEST_CONCURRENCY` requests, not five. An empty `wants` throws before any progress step and says so, rather than announcing a `request` and then blaming the model for a call nobody made (the session engine says something friendlier first, see `session.md`). `usage` sums across every call including retries. Progress stays **one step per id** however many requests there are: `request` (labelled with the number in flight), `retry` the first time any is re-asked, `validate` once they have all settled — the learn screen times each step from its event to the next, so a step per request would be a flicker rather than a timeline.

**The model emits content, never presentation.** The generation wire format (`src/lib/llm/schemas.ts`) is seven direction-specific types (`recognize-mc`, `produce-mc`, `cloze`, `translate-to-target`, `translate-to-native`, `word-order`, `spot-error`) built on one primitive, `TargetText = {text, reading}` — target-language text carrying its own Latin reading, `reading: null` for Latin scripts. Every field is unconditionally either a `TargetText` or a native string, so no field's language depends on a flag. `resolveBatch` then assembles the stored `Challenge`: it picks `direction` from the type, shuffles the options and computes `correctIndex` (injectable `rng`), joins `before + '___' + after` for cloze, and derives diacritic-folded `acceptedAnswers`. Whole bug classes — answer-spoiling romanizations, misaligned readings, correct-answer-always-in-slot-A — are unexpressible rather than guarded against.

`systemPromptFor(def)` composes one system prompt per wire type — memoised, and still a **static string per type**, which is what keeps prompt caching paying across a top-up's requests of one kind and across sessions. It carries load-bearing rule blocks (voice/anti-blandness, the one-line `TargetText` reading rule, answerability, `explanation`), and it does **not** say which type to write, how the learner is doing, or how hard on any scale: the type is the whole subject of the prompt, and difficulty is the parameters on each item. Its counterpart rule is "one `<type>` challenge per entry in `items`, in the same order, about that entry's word, at the size that entry gives", plus "treat every size as a target to hit, not a maximum". Prompt edits are the fix of first resort for content-quality bugs; `resolveBatch` degrades cosmetic defects silently (a partial reading is dropped, never the challenge) and drops only structural failures.

All per-wire-type knowledge lives in `src/lib/llm/challenge-types/` — one module per type bundling its zod `schema`, `stored` (the `{type, direction}` its resolver always writes — what `kindOf` inverts, pinned against the def's own fixtures in `registry.test.ts`), `promptSpec` (its field list and example), `params` + `paramsSpec` (how hard a copy of it is written, as counts), `correctiveSpec` (retry fragment), `resolve` function, `fixtures` (its canned examples per mock scenario, ordered by `order` so the assembled practice lesson keeps lesson order rather than registry order), and optional `rulesSpec` / `escalationSpec`. The ordered `WIRE_TYPE_DEFS` registry in `challenge-types/index.ts` is then the single source of membership: `generatedChallengeSchema` is *projected* from it (`SchemasOf`, a tuple-preserving mapped type — `.map()` would widen the members and defeat zod's inference), `generate.ts` composes each type's own prompt, schema and corrective retry from it and dispatches `resolveBatch` from it, `escalation.ts` composes its stored-shape gloss sentence from the `escalationSpec`s, and `mock.ts` assembles both scenario batches from the `fixtures` (each of which cites its subject **by term** — a scenario cannot know the learner's ids, so `mock.ts` binds those terms onto the words the wants are about, and with no wants the canned half resolves to nothing, exactly as the paid path writes nothing). Registry order is union order and escalation-gloss order; it is not prompt order, since no prompt lists more than one type. Import direction is strictly `primitives.ts` (shared zod pieces) ← def modules ← `index.ts` ← `schemas.ts` ← `generate.ts`, with `requests.ts` beside `schemas.ts` (it imports the registry, and `generate.ts` imports it); **def modules must never import `schemas.ts`**, which is only a re-exporting façade for both halves of the union (the one-array `generatedBatchSchema`/`looseBatchSchema` envelope, `batchJsonSchemaFor()`/`batchSchemaNameFor()` and the composed `challengeSchema` are still written there; the stored-side members come from `$lib/challenges/types`). A def sizes itself by `DifficultyRung` and `SizingKind` declared in `def.ts`, not by importing `requests.ts` — `requests.ts` names wire types, so the arrow has to point that way. Defs use `satisfies WireTypeDef<T>` rather than a type annotation so each keeps its precise schema type — hence `OptionalSpecs`, intersected in by `index.ts` so `rulesSpec`/`escalationSpec` stay readable across the union. **Adding a wire type** is three edits (def module + registration + a `PlannableKind` with its demand in `requests.ts`) — the `add-challenge-type` skill has the procedure and the failure modes.
