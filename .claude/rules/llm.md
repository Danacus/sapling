# LLM generation

The stateless half: data in, data out, never touches the DB.

- `src/lib/llm/` — **stateless**: data in, data out, never touches the DB. `getBatch` returns **challenges and nothing else**: a batch is written *about* the vocabulary it is handed and never introduces any, so the caller has only the pool to persist. New words enter the collection through `add_words` (`$lib/assistant`, `$lib/conversation`), never through a lesson. The OpenRouter client takes an injectable `fetch` — all LLM tests run against fakes, no network. The client also speaks OpenAI-style tool calling (`tools` option, `ChatMessage` union with assistant `toolCalls` and `tool` result messages, `toolCalls` on the result) — used by `$lib/assistant`, invisible to callers that don't pass tools.

## Token economy (the core design)

One batched LLM call (`src/lib/llm/generate.ts`) writes a whole lesson (~20 challenges, ~2.5k tokens) including everything needed to grade locally: exhaustive `acceptedAnswers`, distractors, romanization variants. Play-time grading is free (`src/lib/validate` fuzzy matching + `src/lib/srs` FSRS). The only mid-session spend is the user-initiated *Explain/dispute* escalation (`src/lib/llm/escalation.ts`), which can genuinely overturn a "wrong" grade via its structured `{answer, overturn}` reply. `match-pairs` challenges are assembled locally at zero cost. Mock mode (no API key, or `ll.mockMode`) routes deterministic fixtures through the *real* parse/resolve path — the whole app is developable without spending tokens, and node tests are always in mock mode.

**The model emits content, never presentation.** The generation wire format (`src/lib/llm/schemas.ts`) is seven direction-specific types (`recognize-mc`, `produce-mc`, `cloze`, `translate-to-target`, `translate-to-native`, `word-order`, `spot-error`) built on one primitive, `TargetText = {text, reading}` — target-language text carrying its own Latin reading, `reading: null` for Latin scripts. Every slot is unconditionally either a `TargetText` or a native string, so no field's language depends on a flag. `resolveBatch` then assembles the stored `Challenge`: it picks `direction` from the type, shuffles the options and computes `correctIndex` (injectable `rng`), joins `before + '___' + after` for cloze, and derives diacritic-folded `acceptedAnswers`. Whole bug classes — answer-spoiling romanizations, misaligned readings, correct-answer-always-in-slot-A — are unexpressible rather than guarded against.

The `SYSTEM_PROMPT` in `generate.ts` is deliberately token-budgeted and static (prompt-cache friendly). It carries load-bearing rule blocks (voice/anti-blandness, the one-line `TargetText` reading rule, answerability, difficulty calibration from `recentAccuracy`/`recentMistakes`). Prompt edits are the fix of first resort for content-quality bugs; `resolveBatch` degrades cosmetic defects silently (a partial reading is dropped, never the challenge) and drops only structural failures.

All per-wire-type knowledge lives in `src/lib/llm/challenge-types/` — one module per type bundling its zod `schema`, `promptSpec` (its `Types:` line), `correctiveSpec` (retry fragment), `resolve` function, `fixtures` (its canned examples per mock scenario, ordered by `order` so the assembled practice lesson keeps lesson order rather than registry order), and optional `rulesSpec` / `escalationSpec`. The ordered `WIRE_TYPE_DEFS` registry in `challenge-types/index.ts` is then the single source of membership: `generatedChallengeSchema` is *projected* from it (`SchemasOf`, a tuple-preserving mapped type — `.map()` would widen the members and defeat zod's inference), `generate.ts` composes `SYSTEM_PROMPT`'s `Types:` block and `CORRECTIVE_INSTRUCTION` and dispatches `resolveBatch` from it, `escalation.ts` composes its stored-shape gloss sentence from the `escalationSpec`s, and `mock.ts` assembles both scenario batches from the `fixtures` (each of which cites its subject **by term** — a scenario cannot know the learner's ids, so `mock.ts` binds those terms onto the review items it was handed, and with no review items the canned half resolves to nothing, exactly as the paid path does). Order = prompt order = union order; the composed prompts are still static strings, so nothing about prompt caching changes. Import direction is strictly `primitives.ts` (shared zod pieces) ← def modules ← `index.ts` ← `schemas.ts` ← `generate.ts`; **def modules must never import `schemas.ts`**, which is now only a re-exporting façade for both halves of the union (the one-array `generatedBatchSchema`/`looseBatchSchema` envelope, `batchJsonSchema()` and the composed `challengeSchema` are still written there; the stored-side members come from `$lib/challenges/types`). Defs use `satisfies WireTypeDef<T>` rather than a type annotation so each keeps its precise schema type — hence `OptionalSpecs`, intersected in by `index.ts` so `rulesSpec`/`escalationSpec` stay readable across the union. **Adding a wire type** is two edits (def module + registration) — the `add-challenge-type` skill has the procedure and the failure modes. The only hand-edited cross-type prompt text left is `generate.ts`'s `Rules:` block (segmentation, sides-never-swap, difficulty calibration) — rules that by definition name more than one type.
