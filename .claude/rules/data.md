# Domain types, SRS and persistence

- `src/lib/types.ts` — shared domain types, **all generated from Rust**: every type that crosses a boundary (`Profile` — whose optional `aim`, easier/normal/harder, is the success rate the difficulty model picks for, `normal` when absent, and whose `level` and `interests` are **deprecated: never read, written only so an older build on another device still parses the profile** (a new profile writes `beginner` and `[]`, an edit spreads the stored values through; the level a prompt uses is derived, `llm.md`) — `KnowledgeItem`, `ReadingText`, the conversation shapes, `FsrsCardState`, …) is a struct in `crates/sapling-domain` or `crates/sapling-srs`, and the stored challenge union (`Challenge`, one struct per member, `Direction`, `MatchPair`, `MultiClozeGap`) is `crates/sapling-challenges`' `challenge.rs`; `pnpm core:types` writes each declaration into the gitignored `src/lib/db/generated/` at build time (every `pnpm` gate runs it after `core:wasm`), and `types.ts` re-exports it under the same name. Changing one means changing the struct — doc comments included, they travel. An optional field is `#[ts(optional)]` beside its serde attributes, so it reads `field?: T`. The challenge union's stored shape is **additive optional fields only**, because every pooled row ever written must keep parsing — the Rust structs read leniently (`challenges.md`), and a freshly resolved row is held to `check_shape` instead. What stays hand-written in `types.ts` is TypeScript-only helpers over the generated types (`ChallengeType`, `StoredConversationTurn`); `ChallengeRow` in `database.ts` is the generated `PoolRow`.

- `src/lib/srs/` — **the frontend runs no FSRS.** The one implementation is `crates/sapling-srs`; this module is the vocabulary for talking to it (`Grade`, `gradeFromResult`, `CardState`), the accessors that read what the core derived (`dueAt`, `isDue`, `strengthOf`, `retrievabilityOf`), and `selectSessionItems`. `FsrsCardState` is kept as a type only — the stored shape, generated from `sapling-srs`, opaque, read inside by the words ledger alone (whose `CardState` narrows the wire's `state: number`). A review is filed as `{at, grade}` and the card comes back from the store, so nothing here can predict one and disagree with what was written.

  **Every `Backend` read that returns items attaches `srs: { due, retrievability, strength }`**, computed by the core against its clock as the row is fetched (`ItemSrs`, generated from `sapling-srs`; an optional field — absent on an item built by hand). `isDue` stays a frontend comparison, `due <= now`, because that is a date comparison and the session's explicit `now` has to be the one it answers against. The rest is a **snapshot**: a page held open across a due date shows the schedule as of its last read, and only a refetch moves it — the word list and the home page refetch on navigation. Because the instant is chosen at read time, the functions built on these numbers (`sapling-challenges`' `fits` — which reads `retrievability` as a word's memory — `$lib/challenges/serve`'s `maturityOf`, `$lib/reading/annotate`) take no `now` at all.

  `selectSessionItems` is pure selection over `srs.due` and `now`: a short focus list, due first (most overdue first, capped at `maxItems`), then topped up with the soonest-due items that are not due yet, so a learner who is caught up still has something the model can build around. Its one caller is the **reading composer** (`src/routes/read/+page.svelte`), where the prompt only has room for a handful of focus words. The challenge top-up used to call it too and no longer does — a twelve-word window over thirty due words meant every press wrote another row about the same twelve, so the top-up planner (`sapling-challenges`' `topup.rs`) walks the whole collection in the same order and skips what it has already covered. There is no trailing-accuracy dial anywhere: what a word's challenges look like follows from that word's learned `skill` and its memory, which every answer moves. **Strength is display only** — the strength bar, the garden's maturity, the reader's reading ramp — and decides nothing served.

- **An event payload struct must name every optional field of the type it carries.** Serde *strips* what it is not told about (as zod did before it), and `parse_event` in `crates/sapling-domain/src/events.rs` is the gate everything off sync or out of a backup file passes through *into the merge rules* — while a local `commit` does not parse at all. A row that gate turns away is still logged, pushed and exported (below); what the struct strips is what the *materialized* copy of an understood payload loses. A field the struct forgets therefore works perfectly on the device that wrote it and vanishes on the device it arrives at, which is the worst shape a bug can have. `textAdded` is the one that has already been caught by this (`Segment.start`/`end` and `ReadingText.media`), and three tests pin it: `events.rs`'s `parse_event(raw) == raw` over one full payload per type, `merge.test.ts`'s gate cases through `applyRemote` and `exportData`, and every golden fixture's log round-trip. The converse is how a payload *changes shape* without a shim: `ReadingText.segments` carries `#[serde(alias = "sentences")]`, so every `textAdded` written before segments — `sentences` with a `reading`, a `translation` and a `glossary` beside them — still parses into the new struct, each old sentence a segment with its times and the rest stripped. The log keeps the old row verbatim; only the rebuilt read table (a `DERIVED_SCHEMA_VERSION` bump) holds the new shape. The TypeScript side of it is generated: `src/lib/db/events.ts` re-exports each payload (`<Name>Payload`) and `Payloads`, the map from event type to payload, from `generated/`, so a field the struct forgets is a field the TypeScript does not have either.

- **The difficulty model's numbers are derived data** (`crates/sapling-db/src/learned.rs`, over `sapling-challenges`' `replay.rs` and `model.rs`): each word's `skill` on its `items` row (attached to every item read, absent until an answer names the word), each pool row's `correction` (on its `ChallengeRow`), and the shared parts in `difficultyParts` (`base:<kind>/<help level>`, `slope:<kind>`; read with `getDifficultyParts`, a `Shared`). They are a function of the answers in `(at, id)` order, never arrival order, **each at the verdict it counts as**: a `resultOverturned` (an escalation won) names its answer by challenge and `at` and lands in `overturns`, where an answer arriving later finds it, and replay reads the answer at the overturned verdict — so an overturn is exactly an answer accepted on the spot. The `results` row keeps what was answered; an older build logs the event and skips it. The newest answer is learned on the spot; anything that could change an answer already folded — an older answer, a review older than the newest answer (it changes a memory), a challenge or word landing after answers that name it, a word deleted from under them, an overturn of an answer already in — marks `difficultyFold` dirty, and the transaction settles (`Materializer::settle`, called by `commit_all`, `apply_remote` and `rebuild`) with one full replay from the read tables. Both paths do the same arithmetic in the same order, so they agree bit for bit — which is also why `sapling-db`'s `serde_json` has `float_roundtrip` on: a stored number crossing from sqlite-wasm as JSON must read back to the same bits. `tests/learned.rs` holds every arrival order to the pure replay; changing the model, a rate, a starting value or what a row's length is read from is a `DERIVED_SCHEMA_VERSION` bump, never a reinterpretation.

- **Push and export carry log rows verbatim; only materialization interprets a payload, and a row it cannot read is skipped, never dropped from the log.** `pendingEvents` and `exportData` return the envelope as stored with the payload uninterpreted (`RawEvent` in the core, generated as `LogRow`, whose `type` is a plain string and not an `EventType`), and `applyRemote` logs a pulled row whose kind or payload this build does not know rather than discarding it — that is what lets a row a newer build wrote survive a round trip through an older device. It is also why `pendingEvents(limit)` is exactly the first `limit` unpushed rows with no gaps: the sync cycle (`sapling-sync`'s `push`) stops on a short page, so a filter that ran *after* the `LIMIT` would hand it a short page over a bad row and starve everything behind it. Because such a row now lives in the log, the materializer's own reads of `events` (`patches_of`, `refold_patches`) skip what they cannot parse rather than failing the transaction.

- `src/lib/db/` — repositories are the **only** store access, and every write is an event. The `events` table is the log — the only thing sync moves — and everything else (`items`, `reviews`, `challenges`, `results`, `tombstones`, `profile`) is an aggregate the materializer maintains; UI reads never touch `events` (or `reviews` in bulk — the FSRS card and counters live on the `items` row). **`getDailyActivity` is the one read folded at read time rather than kept**: a day is any local day on which something happened, and the core buckets `results` (by verdict), `reviews` (distinct words, **joined to `items`** — a review row for a word the log never added or whose tombstone arrived first is present by arrival order, and a read must not expose that), `lookups` and `items.introducedAt` into one `DailyActivity` row per day. A `daily` answers-per-day aggregate stood here before and is gone — four counters kept by four materializers would be four things to keep agreeing, and the base tables are small. Materializers apply once per event id — dedupe happens at the log — must be **total** (a rule that cannot apply returns, never throws), and resolve last-write-wins by `at`. Ids that cross devices derive from synced content, never from anything device-local. API key + prefs live in localStorage (`ll.*` keys via `db/settings.ts` and `ui/prefs.ts`), never in the store and never in the JSON export.

- **The window thread never speaks SQL.** `protocol.ts` is the boundary: the `Backend` interface — every repository function, the sync operations (`pendingEvents`, `markPushed`, `applyRemote`, the pull cursor; `crates/sapling-sync`'s cycle drives them through the `SyncHost` that `src/lib/sync/core.ts` builds over this interface, so sync is a `Backend` client like any other and needs no method of its own) and export/import — plus `BACKEND_METHODS`, the same names as a value. Both are generated (`generated/backend.ts`) from the method table in `crates/sapling-protocol`, the same `backend!` list its `dispatch` expands from, and `protocol.ts` re-exports them beside the transport's own types (`Direct`, `BackendRequest`, the Worker messages). The Rust core (`crates/sapling-db`, see `core.md`) implements it synchronously over its `Sql` seam and is the only code that writes SQL against the read tables; compiled to wasm it runs inside `sqlite.worker.ts` in the browser and in-process in node (`backend.testing.ts`), both through `host.ts`, so there is one implementation and the transport is the only difference. `client.ts` builds the window's `Backend` from `BACKEND_METHODS`, one `postMessage` per call; `repositories.ts` forwards each method under its old name so callers keep `import { getProfile } from '$lib/db'`. Adding a method is one entry in that table (see `core.md`); the interface, the list and the dispatch arm cannot disagree because they are one declaration. Arguments must be plain JSON-shaped data (no functions — `updateItemAfterReview` is `reviewItem` under its old name, `(itemId, {at, grade}, opts?)`, and answers `{existed, prior, card}`: the card is *read back* after the commit, because a caller that wants it has no FSRS to predict it with); the client runs every argument through `toPlain()`, which strips Svelte `$state` Proxies — structured clone throws `DataCloneError` on a bare one — so neither callers nor the core have to. The device id is a `localStorage` fact the Worker cannot read; the window sends it in the `init` message and `host.ts` hands it to the core as a constructor argument, never calling `getDeviceId()` in the Worker (that would mint a fresh id per boot, and the id is half of a review's identity). Every event that arrives from outside — a pulled page, an import file — is read by `parse_envelope` inside the core and typed by `typed_event` (the two halves of `parse_event`) before any merge rule sees it, never trusted from the window; `events.ts` on the TypeScript side is types only.

- **The merge rules are pinned by golden fixtures, not only by hand-written cases.** `src/lib/db/fixtures/<name>/events.json` is a log as it would arrive off sync; `expected.json` beside it is what every `Backend` read returns afterwards, and `golden.test.ts` replays each through `applyRemote` and diffs. The files are language-neutral on purpose — they are the conformance suite any implementation of the core has to pass, and today two runners read them: `tests/golden.rs` natively and `golden.test.ts` through the wasm build. A change to a rule or a read shows up as a diff in `expected.json`; rebless with `pnpm golden:update` only when the change was meant, and read the diff as the review. `openCore` takes a `clock` for this (the app passes nothing and gets `Date.now`), and the reads are taken under `TZ=UTC`. Two rules depend on log order — a serve or report before its `challengeAdded`, a `reviewAmended` before the review it replaces — so a fixture that exercises one says `orderFree: false`; the rest are also checked in reverse arrival order. `itemUpdated` is not one of them: patches fold per field from the log in `(at, device)` order, so one that arrives before its `itemAdded` waits, and an older one arriving late refolds rather than being dropped.
