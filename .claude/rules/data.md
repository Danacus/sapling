# Domain types, SRS and persistence

- `src/lib/types.ts` — shared domain types. Treat as frozen; extend with **additive optional fields only**. Zod mirrors live per type — generated-side in `src/lib/llm/challenge-types/<type>.ts`, stored-side in `src/lib/challenges/types/<type>.ts` — and reach the app through the `src/lib/llm/schemas.ts` façade: generated-side fields are `.nullish()` (models emit `null`), stored-side `.optional()`; the resolver normalizes null→absent.

- `src/lib/srs/` — **the frontend runs no FSRS.** The one implementation is `crates/sapling-core/src/srs.rs`; this module is the vocabulary for talking to it (`Grade`, `gradeFromResult`, `CardState`), the accessors that read what the core derived (`dueAt`, `isDue`, `strengthOf`, `retrievabilityOf`), and `selectSessionItems`. `FsrsCardState` is kept as a type only — the stored shape, opaque, read inside by the words ledger alone. A review is filed as `{at, grade}` and the card comes back from the store, so nothing here can predict one and disagree with what was written.

  **Every `Backend` read that returns items attaches `srs: { due, retrievability, strength }`**, computed by the core against its clock as the row is fetched (`types.ts`'s `ItemSrs`, an additive optional field — absent on an item built by hand). `isDue` stays a frontend comparison, `due <= now`, because that is a date comparison and the session's explicit `now` has to be the one it answers against. The rest is a **snapshot**: a page held open across a due date shows the schedule as of its last read, and only a refetch moves it — the word list and the home page refetch on navigation. Because the instant is chosen at read time, the functions built on strength (`$lib/session/progression`'s `difficultyLevelOf`/`maturityOf`/`bearable`, `$lib/session/romanization`, `$lib/reading/annotate`) take no `now` at all.

  `selectSessionItems` is pure selection over `srs.due` and `now`: the words a generated batch is written about, due first (most overdue first, capped at `maxItems`), then topped up with the soonest-due items that are not due yet — generation introduces no vocabulary, so a learner who is caught up must still have something for the model to write about. There is no trailing-accuracy dial: what a word's challenges look like follows from that word's own strength, which FSRS already moves on every answer.

- **An event payload struct must name every optional field of the type it carries.** Serde *strips* what it is not told about (as zod did before it), and `parse_event` in `crates/sapling-core/src/events.rs` is the gate everything off sync or out of a backup file passes through *into the merge rules* — while a local `commit` does not parse at all. A row that gate turns away is still logged, pushed and exported (below); what the struct strips is what the *materialized* copy of an understood payload loses. A field the struct forgets therefore works perfectly on the device that wrote it and vanishes on the device it arrives at, which is the worst shape a bug can have. `textAdded` is the one that has already been caught by this (`ReadingSentence.start`/`end` and `ReadingText.media`), and three tests pin it: `events.rs`'s `parse_event(raw) == raw` over one full payload per type, `merge.test.ts`'s gate cases through `applyRemote` and `exportData`, and every golden fixture's log round-trip. The TypeScript type in `src/lib/db/events.ts` must say the same as the struct, field for field.

- **Push and export carry log rows verbatim; only materialization interprets a payload, and a row it cannot read is skipped, never dropped from the log.** `pendingEvents` and `exportData` return the envelope as stored with the payload uninterpreted (`RawEvent` in the core, `LogRow` in `events.ts`, whose `type` is a plain string and not an `EventType`), and `applyRemote` logs a pulled row whose kind or payload this build does not know rather than discarding it — that is what lets a row a newer build wrote survive a round trip through an older device. It is also why `pendingEvents(limit)` is exactly the first `limit` unpushed rows with no gaps: the filter used to run *after* the `LIMIT`, so a page over a bad row came back short, `pushPending` stopped on it, and everything behind it starved. Because such a row now lives in the log, the materializer's own reads of `events` (`patches_of`, `refold_patches`) skip what they cannot parse rather than failing the transaction.

- `src/lib/db/` — repositories are the **only** store access, and every write is an event. The `events` table is the log — the only thing sync moves — and everything else (`items`, `reviews`, `challenges`, `results`, `daily`, `tombstones`, `profile`) is an aggregate the materializer maintains; UI reads never touch `events` (or `reviews` in bulk — the FSRS card and counters live on the `items` row). Materializers apply once per event id — dedupe happens at the log — must be **total** (a rule that cannot apply returns, never throws), and resolve last-write-wins by `at`. Ids that cross devices derive from synced content, never from anything device-local. API key + prefs live in localStorage (`ll.*` keys via `db/settings.ts` and `ui/prefs.ts`), never in the store and never in the JSON export.

- **The window thread never speaks SQL.** `protocol.ts` is the boundary: the `Backend` interface — every repository function, the sync operations (`pendingEvents`, `markPushed`, `applyRemote`, the pull cursor) and export/import — plus `BACKEND_METHODS`, the same names as a value. The Rust core (`crates/sapling-core`, see `core.md`) implements it synchronously over its `Sql` seam and is the only code that writes SQL against the read tables; compiled to wasm it runs inside `sqlite.worker.ts` in the browser and in-process in node (`backend.testing.ts`), both through `host.ts`, so there is one implementation and the transport is the only difference. `client.ts` builds the window's `Backend` from `BACKEND_METHODS`, one `postMessage` per call; `repositories.ts` forwards each method under its old name so callers keep `import { getProfile } from '$lib/db'`. Adding a method means the interface, the list **and** an arm in `dispatch.rs` — `_everyMethodListed` fails `pnpm check` when the list is short, and `cargo test` reads `protocol.ts` and fails when the Rust side disagrees. Arguments must be plain JSON-shaped data (no functions — `updateItemAfterReview` is `reviewItem` under its old name, `(itemId, {at, grade}, opts?)`, and answers `{existed, prior, card}`: the card is *read back* after the commit, because a caller that wants it has no FSRS to predict it with); the client runs every argument through `toPlain()`, which strips Svelte `$state` Proxies — structured clone throws `DataCloneError` on a bare one — so neither callers nor the core have to. The device id is a `localStorage` fact the Worker cannot read; the window sends it in the `init` message and `host.ts` hands it to the core as a constructor argument, never calling `getDeviceId()` in the Worker (that would mint a fresh id per boot, and the id is half of a review's identity). Every event that arrives from outside — a pulled page, an import file — is read by `parse_envelope` inside the core and typed by `typed_event` (the two halves of `parse_event`) before any merge rule sees it, never trusted from the window; `events.ts` on the TypeScript side is types only.

- **The merge rules are pinned by golden fixtures, not only by hand-written cases.** `src/lib/db/fixtures/<name>/events.json` is a log as it would arrive off sync; `expected.json` beside it is what every `Backend` read returns afterwards, and `golden.test.ts` replays each through `applyRemote` and diffs. The files are language-neutral on purpose — they are the conformance suite any implementation of the core has to pass, and today two runners read them: `tests/golden.rs` natively and `golden.test.ts` through the wasm build. A change to a rule or a read shows up as a diff in `expected.json`; rebless with `pnpm golden:update` only when the change was meant, and read the diff as the review. `openCore` takes a `clock` for this (the app passes nothing and gets `Date.now`), and the reads are taken under `TZ=UTC`. Two rules depend on log order — a serve or report before its `challengeAdded`, a `reviewAmended` before the review it replaces — so a fixture that exercises one says `orderFree: false`; the rest are also checked in reverse arrival order. `itemUpdated` is not one of them: patches fold per field from the log in `(at, device)` order, so one that arrives before its `itemAdded` waits, and an older one arriving late refolds rather than being dropped.
