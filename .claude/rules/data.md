# Domain types, SRS and persistence

- `src/lib/types.ts` — shared domain types, **all generated from Rust**. Domain and SRS shapes come from their crates; challenge stored, screen, answer and feedback unions come from `sapling-challenges`' compile-time registry in `types/mod.rs`. `pnpm core:types` writes declarations into gitignored `src/lib/db/generated/`, and `types.ts` re-exports them plus TypeScript-only narrowing helpers. Optional Rust fields use `#[ts(optional)]`. Stored challenge changes are additive optional fields only: old pooled rows must remain readable, while fresh generated rows also pass their plugin's strict `check_shape`.

- `src/lib/srs/` — **the frontend runs no FSRS.** The one implementation is `crates/sapling-srs`; this module is the vocabulary for talking to it (`Grade`, `CardState`), the accessors that read what the core derived (`dueAt`, `isDue`, `strengthOf`, `retrievabilityOf`), and `selectSessionItems`. `FsrsCardState` is kept as a type only — the stored shape, generated from `sapling-srs`, opaque, read inside by the words ledger alone (whose `CardState` narrows the wire's `state: number`). A review is filed as `{at, grade}` and the card comes back from the store, so nothing here can predict one and disagree with what was written. **An answer is filed as its verdict, not a grade**: `recordAnswer` (one `Backend` call, one transaction — a review per word still there, the `resultLogged`, and the `challengeServed` stamp when the pool holds the challenge; the same events `reviewItem` × N, `addResult` and `recordServe` used to write as N + 2 transactions) grades each word by `sapling-db`'s `grade_of` — wrong → Again, almost → Hard, correct → Good, a composite answer's word at its own gap's verdict (`itemVerdicts`), never Easy — and answers the words it reviewed. `Grade` stays here for the re-grades a caller files itself through `reviewItem` with `replaceLast` (an overturn's Good, the reader's lookups).

  **Every `Backend` read that returns items attaches `srs: { due, retrievability, strength, stability }`**, computed by the core against its clock as the row is fetched (`ItemSrs`, generated from `sapling-srs`; an optional field — absent on an item built by hand). `isDue` stays a frontend comparison, `due <= now`, because that is a date comparison and the session's explicit `now` has to be the one it answers against. The rest is a **snapshot**: a page held open across a due date shows the schedule as of its last read, and only a refetch moves it — the word list and the home page refetch on navigation. Because the instant is chosen at read time, the functions built on these numbers (`sapling-challenges`' ratings — which read `stability` as a word's side — `$lib/challenges/serve`'s `maturityOf`, `$lib/reading/annotate`) take no `now` at all.

  `selectSessionItems` is pure selection over `srs.due` and `now`: a short focus list, due first (most overdue first, capped at `maxItems`), then topped up with the soonest-due items that are not due yet, so a learner who is caught up still has something the model can build around. Its one caller is the **reading composer** (`src/routes/read/+page.svelte`), where the prompt only has room for a handful of focus words. The challenge top-up used to call it too and no longer does — a twelve-word window over thirty due words meant every press wrote another row about the same twelve, so the top-up planner (`sapling-challenges`' `topup.rs`) walks the whole collection in the same order and skips what it has already covered. There is no trailing-accuracy dial anywhere: what a word's challenges look like follows from the ratings and the word's FSRS stability, which every answer moves. **Strength is display only** — the strength bar, the garden's maturity, the reader's reading ramp — and decides nothing served.

- **An event payload struct must name every optional field of the type it carries.** Serde *strips* what it is not told about (as zod did before it), and `parse_event` in `crates/sapling-domain/src/events.rs` is the gate everything off sync or out of a backup file passes through *into the merge rules* — while a local `commit` does not parse at all. A row that gate turns away is still logged, pushed and exported (below); what the struct strips is what the *materialized* copy of an understood payload loses. A field the struct forgets therefore works perfectly on the device that wrote it and vanishes on the device it arrives at, which is the worst shape a bug can have. `textAdded` is the one that has already been caught by this (`Segment.start`/`end` and `ReadingText.media`), and three tests pin it — its payload is its own struct now, `events.rs`' `TextAdded`, no longer `ReadingText` (which stays what `addText` takes and every read returns, body resolved), carrying **exactly one** of `segments` (inline, as every older event does) or `content` (an object's hash), which `parse_payload` enforces after serde: `events.rs`'s `parse_event(raw) == raw` over one full payload per type, `merge.test.ts`'s gate cases through `applyRemote` and `exportData`, and every golden fixture's log round-trip. The converse is how a payload *changes shape* without a shim: `TextAdded.segments` (and `ReadingText.segments`) carries `#[serde(alias = "sentences")]`, so every `textAdded` written before segments — `sentences` with a `reading`, a `translation` and a `glossary` beside them — still parses into the new struct, each old sentence a segment with its times and the rest stripped. The log keeps the old row verbatim; only the rebuilt read table (a `DERIVED_SCHEMA_VERSION` bump) holds the new shape. The TypeScript side of it is generated: `src/lib/db/events.ts` re-exports each payload (`<Name>Payload`) and `Payloads`, the map from event type to payload, from `generated/`, so a field the struct forgets is a field the TypeScript does not have either.

- **The difficulty model's ratings are derived data** (`crates/sapling-db/src/learned.rs`, over `sapling-challenges`' `replay.rs` and `ratings.rs`): one row per rating in `difficultyParts` — `challenge:<kind>/<help level>`, `scale`, `base`, `slope:<kind>`, each with its `value`, `margin`, `startMargin`, `at` (last answer) and `answers` — read with `getRatings` (`StoredRating[]`) and handed to the planners as `ratings`; a rating not stored is at its start. Each answer's word side reads the card's stability as of the answer. They are a function of the answers in `(at, id)` order, never arrival order, **each at the verdict it counts as**: a `resultOverturned` (an escalation won) names its answer by challenge and `at` and lands in `overturns`, where an answer arriving later finds it, and replay reads the answer at the overturned verdict — so an overturn is exactly an answer accepted on the spot. The `results` row keeps what was answered; an older build logs the event and skips it. The newest answer is learned on the spot; anything that could change an answer already folded — an older answer, a review older than the newest answer (it changes a stability), a challenge or word landing after answers that name it, a word deleted from under them, an overturn of an answer already in — marks `difficultyFold` dirty, and the transaction settles (`Materializer::settle`, called by `commit_all`, `apply_remote` and `rebuild`) with one full replay from the read tables. Both paths do the same arithmetic in the same order, so they agree bit for bit — which is also why `sapling-db`'s `serde_json` has `float_roundtrip` on: a stored number crossing from sqlite-wasm as JSON must read back to the same bits. `tests/learned.rs` holds every arrival order to the pure replay; changing the model, a starting value or what a row's length is read from is a `DERIVED_SCHEMA_VERSION` bump, never a reinterpretation.

- **Push and export carry log rows verbatim; only materialization interprets a payload, and a row it cannot read is skipped, never dropped from the log.** `pendingEvents` and `exportData` return the envelope as stored with the payload uninterpreted (`RawEvent` in the core, generated as `LogRow`, whose `type` is a plain string and not an `EventType`), and `applyRemote` logs a pulled row whose kind or payload this build does not know rather than discarding it — that is what lets a row a newer build wrote survive a round trip through an older device. It is also why `pendingEvents(limit)` is exactly the first `limit` unpushed rows with no gaps: the sync cycle (`sapling-sync`'s `push`) stops on a short page, so a filter that ran *after* the `LIMIT` would hand it a short page over a bad row and starve everything behind it. Because such a row now lives in the log, the materializer's own reads of `events` (`patches_of`, `refold_patches`) skip what they cannot parse rather than failing the transaction.

- **A text's body is a content object** (`docs/content-objects.md`): immutable bytes named `sha256:<64 lowercase hex>` over exactly those bytes, held in the local `objects (hash, bytes)` table — which is **not an aggregate**: not in `DERIVED_TABLES`, derived from nothing, kept by every rebuild and cleared only by `resetData`. `addText` writes the object and a `textAdded { content }` in one transaction (and refuses a body over 1 MiB); `putObjects` keeps only an object whose name verifies and whose bytes are JSON; `getObjects` and `missingObjects` are what the sync cycle reads. A `texts` row records its body as it came, inline `segments` or a `content` hash; `textRevised` (last write by `(at, device, event id)`, kept in `textRevisions`, inert on a tombstoned text, waiting for one not added yet) replaces it. **Reads resolve the current body through `objects` (`schema.rs`' `READABLE_TEXTS`), and a text whose current object is absent is returned by no read** — `getTexts`, `getText`, `clipsFor`, `cuesFor` — until the object is stored, which needs no rebuild. The envelope fields the relay records (`owner`/`objects`/`retire`) are derived at push time and never written to `events`; export is unchanged (a v3 file carries the reference without the object until export v4).

- `src/lib/db/` — repositories are the **only** store access, and every write is an event. The `events` table is the log — the only thing sync moves — and everything else (`items`, `reviews`, `challenges`, `results`, `tombstones`, `profile`, `texts`, `textRevisions`, …) is an aggregate the materializer maintains, `objects` excepted (above); UI reads never touch `events` (or `reviews` in bulk — the FSRS card and counters live on the `items` row). **`getDailyActivity` is the one read folded at read time rather than kept**: a day is any local day on which something happened, and the core buckets `results` (by verdict), `reviews` (distinct words, **joined to `items`** — a review row for a word the log never added or whose tombstone arrived first is present by arrival order, and a read must not expose that), `lookups` and `items.introducedAt` into one `DailyActivity` row per day. A `daily` answers-per-day aggregate stood here before and is gone — four counters kept by four materializers would be four things to keep agreeing, and the base tables are small. **`studySessions(since)` is folded the same way, per local *hour***: one `StudySession { id, at, mode, minutes, answers }` per `(mode, hour)` with `id = "{mode}-{hour start ms}"` — identical on every synced device, so a receiver upserting by id never double-counts — where `input` is the `studied` spans (one per event, `[at, at + ms]`, cut at hour boundaries; kept when their text is deleted), `output` is runs of `conversationTurns` no more than five minutes apart, first to last plus a minute, cut the same way, and `practice` counts `results` with no minutes; hours whose minutes round (to 0.1) to nothing are left out. The hour is the host's (`LocalDay::local_hour`, beside `local_day`). **`clipsFor(terms, sentence?)` is the one read that searches inside a text**: SQL narrows `json_each` over each readable text's resolved `segments` (`READABLE_TEXTS`) to timed segments of YouTube texts whose lowercased text contains a term (`instr`) — newest text first, then cue order, at most 300, and deliberately *not* shortest first (that always played the same one-word fragment) — and `sapling-db`'s `clips.rs` ranks them, pure and deterministic: a cue that *is* the served `sentence` (lowercase, letters and digits only) first, then more distinct terms held as whole words, then `2 × overlap + fitness` (overlap: Jaccard with the sentence over word sets, or character bigrams for unspaced scripts; fitness: 3–14 words by `words_in` and 1–8 s, falling off in proportion outside). A whole word is the old boundary rule in spaced scripts; in an unspaced one an occurrence counts unless a *longer* term of the learner's own `items` covers it (行 is not heard in 银行 when 银行 is a word). It answers the **best tier** — tied with the best on the first two, within 0.15 of its score, best first, at most five, empty for none — and the page picks among it at random. `cuesFor(itemIds)` is the same search for the local cue builder (`sapling-challenges`' `local.rs`): one `instr` prefilter over every timed segment of any text (YouTube, file or no media; `videoId` only for YouTube), then per word the cues holding its term as a whole word by the same rule (`text::find_word`, which `clips.rs` calls too), newest text first, at most 30 each. A deleted text is already gone from `texts`, and one whose body has not arrived is not readable. Materializers apply once per event id — dedupe happens at the log — must be **total** (a rule that cannot apply returns, never throws), and resolve last-write-wins by `at`. Ids that cross devices derive from synced content, never from anything device-local. API key + prefs live in localStorage (`ll.*` keys via `db/settings.ts` and `$lib/prefs`), never in the store and never in the JSON export.

- **The window thread never speaks SQL.** `protocol.ts` is the boundary: the `Backend` interface — every repository function, the sync operations (`pendingEvents`, `markPushed`, `applyRemote`, the pull cursor, the content-object calls `getObjects`/`putObjects`/`missingObjects`, `followSyncRoom` — which clears every `seq` stamp and the cursor when the relay room they describe changes, `docs/sync.md`; `crates/sapling-sync`'s cycle drives them through the `SyncHost` that `src/lib/sync/core.ts` builds over this interface, so sync is a `Backend` client like any other and needs no method of its own) and export/import — plus `BACKEND_METHODS`, the same names as a value. Both are generated (`generated/backend.ts`) from the method table in `crates/sapling-protocol`, the same `backend!` list its `dispatch` expands from, and `protocol.ts` re-exports them beside the transport's own types (`Direct`, `BackendRequest`, the Worker messages). The Rust core (`crates/sapling-db`, see `core.md`) implements it synchronously over its `Sql` seam and is the only code that writes SQL against the read tables; compiled to wasm it runs inside `sqlite.worker.ts` in the browser and in-process in node (`backend.testing.ts`), both through `host.ts`, so there is one implementation and the transport is the only difference. `client.ts` builds the window's `Backend` from `BACKEND_METHODS`, one `postMessage` per call; `repositories.ts` forwards each method under its old name so callers keep `import { getProfile } from '$lib/db'`. Adding a method is one entry in that table (see `core.md`); the interface, the list and the dispatch arm cannot disagree because they are one declaration. Arguments must be plain JSON-shaped data (no functions — `updateItemAfterReview` is `reviewItem` under its old name, `(itemId, {at, grade}, opts?)`, and answers `{existed, prior, card}`: the card is *read back* after the commit, because a caller that wants it has no FSRS to predict it with); the client runs every argument through `toPlain()`, which strips Svelte `$state` Proxies — structured clone throws `DataCloneError` on a bare one — so neither callers nor the core have to. The device id is a `localStorage` fact the Worker cannot read; the window sends it in the `init` message and `host.ts` hands it to the core as a constructor argument, never calling `getDeviceId()` in the Worker (that would mint a fresh id per boot, and the id is half of a review's identity). Every event that arrives from outside — a pulled page, an import file — is read by `parse_envelope` inside the core and typed by `typed_event` (the two halves of `parse_event`) before any merge rule sees it, never trusted from the window; `events.ts` on the TypeScript side is types only.

- **The merge rules are pinned by golden fixtures, not only by hand-written cases.** `src/lib/db/fixtures/<name>/events.json` is a log as it would arrive off sync; `expected.json` beside it is what every `Backend` read returns afterwards, and `golden.test.ts` replays each through `applyRemote` (then stores the optional `objects.json` beside it with `putObjects`) and diffs. The files are language-neutral on purpose — they are the conformance suite any implementation of the core has to pass, and today two runners read them: `tests/golden.rs` natively and `golden.test.ts` through the wasm build. A change to a rule or a read shows up as a diff in `expected.json`; rebless with `pnpm golden:update` only when the change was meant, and read the diff as the review. `openCore` takes a `clock` for this (the app passes nothing and gets `Date.now`), and the reads are taken under `TZ=UTC`. Two rules depend on log order — a serve or report before its `challengeAdded`, a `reviewAmended` before the review it replaces — so a fixture that exercises one says `orderFree: false`; the rest are also checked in reverse arrival order. `itemUpdated` is not one of them: patches fold per field from the log in `(at, device)` order, so one that arrives before its `itemAdded` waits, and an older one arriving late refolds rather than being dropped.
