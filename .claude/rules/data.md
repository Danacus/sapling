# Domain types, SRS and persistence

- `src/lib/types.ts` — shared domain types. Treat as frozen; extend with **additive optional fields only**. Zod mirrors live per type — generated-side in `src/lib/llm/challenge-types/<type>.ts`, stored-side in `src/lib/challenges/types/<type>.ts` — and reach the app through the `src/lib/llm/schemas.ts` façade: generated-side fields are `.nullish()` (models emit `null`), stored-side `.optional()`; the resolver normalizes null→absent.

- `src/lib/srs/` — pure and deterministic: every function takes `now` (epoch ms); card state is a JSON-safe `FsrsCardState` (dates as numbers). `selectSessionItems` picks the words a generated batch is written about: due first (most overdue first, capped at `maxItems`), then topped up with the soonest-due items that are not due yet — generation introduces no vocabulary, so a learner who is caught up must still have something for the model to write about. There is no trailing-accuracy dial: what a word's challenges look like follows from that word's own `wordStrength`, which FSRS already moves on every answer.

- **An event payload schema must name every optional field of the type it carries.** Zod *strips* what it is not told about, and `parseEvent` is the gate everything off sync or out of a backup file passes through — while a local `commit` does not parse at all. A field the schema forgets therefore works perfectly on the device that wrote it and vanishes on the device it arrives at, which is the worst shape a bug can have. `textAdded` is the one that has already been caught by this (`ReadingSentence.start`/`end` and `ReadingText.media`), and `merge.test.ts` pins it: the test is `parseEvent(raw)` equalling `raw`, field for field.

- `src/lib/db/` — repositories are the **only** store access, and every write is an event. The `events` table is the log — the only thing sync moves — and everything else (`items`, `reviews`, `challenges`, `results`, `daily`, `tombstones`, `profile`) is an aggregate the materializer maintains; UI reads never touch `events` (or `reviews` in bulk — the FSRS card and counters live on the `items` row). Materializers apply once per event id — dedupe happens at the log — must be **total** (a rule that cannot apply returns, never throws), and resolve last-write-wins by `at`. Ids that cross devices derive from synced content, never from anything device-local. API key + prefs live in localStorage (`ll.*` keys via `db/settings.ts` and `ui/prefs.ts`), never in the store and never in the JSON export.

- **The window thread never speaks SQL.** `protocol.ts` is the boundary: the `Backend` interface — every repository function, the sync operations (`pendingEvents`, `markPushed`, `applyRemote`, the pull cursor) and export/import — plus `BACKEND_METHODS`, the same names as a value. `core.ts` implements it synchronously over the `Sql` handle and is the only module that writes SQL against the read tables; it runs inside `sqlite.worker.ts` in the browser and in-process in node (`backend.testing.ts`), so there is one implementation and the transport is the only difference. `client.ts` builds the window's `Backend` from `BACKEND_METHODS`, one `postMessage` per call; `repositories.ts` forwards each method under its old name so callers keep `import { getProfile } from '$lib/db'`. Adding a method means the interface **and** the list — `core.ts` fails `pnpm check` when it does not implement the former, `_everyMethodListed` when the latter is short. Arguments must be plain JSON-shaped data (no functions — `updateItemAfterReview` drops its unconsulted `nextCard` before forwarding); the client runs every argument through `toPlain()`, which strips Svelte `$state` Proxies — structured clone throws `DataCloneError` on a bare one — so neither callers nor the core have to. The device id is a `localStorage` fact the Worker cannot read; the window sends it in the `init` message and `core.ts` takes it as a constructor argument, never calling `getDeviceId()` itself (in a Worker that would mint a fresh id per boot, and the id is half of a review's identity). Every event that arrives from outside — a pulled page, an import file — is parsed by `parseEvent` inside the core, never trusted from the window.

- **The merge rules are pinned by golden fixtures, not only by hand-written cases.** `src/lib/db/fixtures/<name>/events.json` is a log as it would arrive off sync; `expected.json` beside it is what every `Backend` read returns afterwards, and `golden.test.ts` replays each through `applyRemote` and diffs. The files are language-neutral on purpose — they are the conformance suite a different implementation of `core.ts` has to pass. A change to a rule or a read shows up as a diff in `expected.json`; rebless with `pnpm golden:update` only when the change was meant, and read the diff as the review. `makeCore` takes a `clock` for this (the app passes nothing and gets `Date.now`), and the reads are taken under `TZ=UTC`. Two rules depend on log order — a serve or report before its `challengeAdded`, a `reviewAmended` before the review it replaces — so a fixture that exercises one says `orderFree: false`; the rest are also checked in reverse arrival order. `itemUpdated` is not one of them: patches fold per field from the log in `(at, device)` order, so one that arrives before its `itemAdded` waits, and an older one arriving late refolds rather than being dropped.
